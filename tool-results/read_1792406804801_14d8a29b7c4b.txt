    12→**Terminology.** *Host* — a process embedding the engine: Tauri shell, web page, CLI, control server, or test harness. *Session* — one open media instance owned by the engine (`SessionId`). *Generation* (`gen`) — a per-session counter that invalidates prior asynchronous work (MP §8). *Catalog* — the enumerated set of command and event IDs defined in this document. *Wire* — the serialized form crossing a host boundary (IPC message, wasm call, CLI/stdout line, control-server frame).

    16→## 1. Contract principles
    17→
    18→### 1.1 One command layer (Trace: MP §2 “Contract”, §3.5, §3.9)
    19→
    20→There is exactly one command layer. The desktop UI (Tauri IPC), the web UI (wasm binding), the CLI, the contract tests and the control server all consume the same catalog, the same envelope, the same request/response/event semantics, defined once in `crates/commands` and re-exported (never re-implemented) by every host.
    21→
    22→Consequences, all binding:
    23→
    24→1. **No host-specific commands.** If a host needs a new lever, the lever is added to the catalog (versioned, §6) and becomes available to all hosts, possibly feature-gated.
    25→2. **The UI imports engine types only through the generated command-layer types.** `ui/` must not depend on engine crates (`playback-engine`, `media-types`, …). Enforcement is automated (§7.4).
    26→3. **Shell-routed commands are still catalog commands.** A few commands (e.g. `video.set-fullscreen`) are executed by the shell/host rather than the engine core (§2.7); they remain in the catalog so that keymaps, menus, CLI and the control server address them uniformly. Each entry declares its `target`: `engine` or `shell`.
    27→4. **UI actions that are not engine concerns** (open-file dialog, toggle info panel, focus player) live in a separate, schema-validated **UI-action registry** (§8.4), never in the engine catalog. `[PROPOSAL]` — dual-namespace design; alternative is polluting the engine catalog with `ui.*` commands, rejected here.
    28→
    29→### 1.2 Typed and validated at the boundary (Trace: MP §3.9, §8, §12)
    30→
    31→Every request is deserialized into typed Rust structures at the host boundary, before any engine work, with these mandatory rules:
    32→
    33→- **V1 — Closed shapes.** Deserialization uses `deny_unknown_fields`; unknown fields, unknown enum variants, and unknown command/event IDs are rejected with `invalid-argument`, never ignored.
    34→- **V2 — Ranges validated before dispatch.** Scalar ranges (volume, rate, zoom, scale, delays, indexes) are checked against the values declared in this catalog and the settings schema; violations return `out-of-range` with the allowed range in `details`.
    35→- **V3 — No sentinel values.** Missing durations, unknown positions and absent tracks are explicit enum variants (`Duration::Unknown`, `Option<TrackId>`), never `-1` or `0` magic numbers (MP §8).
    36→- **V4 — Checked numeric conversions.** All narrowing conversions use `try_from`; there are no `as` casts on the request path (workspace lints already deny the usual foot-guns).
    37→- **V5 — Reference validity checked at execution, not just parse.** Track IDs and playlist item IDs are validated against live session state when the command executes. Because the list can change concurrently, a race degrades to a typed `not-found` error at execution time — parse-time validation is advisory only.
    38→- **V6 — Size caps.** Strings ≤ 4 096 bytes (paths) / 1 024 bytes (names), playlist arrays ≤ `playlist.max-items` (config, default 10 000), nested depth ≤ 8. Violations are `resource-limit` / `invalid-argument`. `[PROPOSAL]` — exact numbers.
    39→- **V7 — Untrusted input stance.** All strings from media, playlists, subtitles and network origins that appear in results/events are treated as untrusted data: length-capped, UTF-8-validated, and rendered by the UI as text, never markup.
    40→- **V8 — Redaction.** Error messages and `system.log` events are built from redaction-safe templates: URLs have credentials stripped, tokens/secrets never appear, absolute paths may be shown to a local user but are never emitted over the control server to unauthenticated peers (MP §12).
    41→
    42→### 1.3 Results are correlated to requests (Trace: MP §3.9)
    43→
    44→Every command response carries the `request_id` of the request it answers. Every event carries a global `seq`, an optional `session`, an optional `gen`, and — when the event is the completion of a specific pending request — an `origin: request_id`. The three identifiers (request_id, gen, seq) are the complete correlation machinery; their exact semantics are specified in §4.
    45→
    46→### 1.4 The truthful-UI rule: Accepted ≠ Completed (Trace: MP §2 “Truthful UI”)
    47→
    48→This is a **hard contract**, not a guideline.
    49→
    50→**Definitions.**
    51→
    52→- **Accepted** — the engine has validated and queued/started the operation. The request’s response is `CommandOutcome::Accepted { session, gen }`. Nothing about the media has observably changed yet.
    53→- **Completed** — the engine confirms the operation happened. Evidence is either (a) a synchronous `CommandOutcome::Completed(result)` response, or (b) a completion event whose `gen` (and `origin` where present) matches the `Accepted` response.
    54→- **Failed** — a typed `CommandError` in the response, or a terminal failure event (`seek-failed`, fatal `error` event) matching the request.
    55→
    56→**Rules (normative, C1–C8).**
    57→
    58→- **C1** — The UI may render *pending* affordances from `Accepted` immediately (spinner, detached scrub thumb, dimmed control). It MUST NOT render success before completion evidence.
    59→- **C2** — For synchronous-complete commands (class S, §1.5), the response **is** the completion evidence; no event is required.
    60→- **C3** — For async-observed commands (class A), the UI MUST wait for the completion event. `state_changed`/`seek_completed`/`track_changed`/`device_changed`/`screenshot_saved` are the only acceptable proof for their respective commands.
    61→- **C4** — Playback state in the UI comes **only** from `session.state-changed` events (or a state snapshot query). The UI never keeps an optimistic “playing” flag.
    62→- **C5** — Errors MUST surface to the user (redacted message + typed stage/code), or be explicitly and audibly ignored by user choice (e.g. a non-fatal decode error counter). Silently swallowing a failure is a contract violation.
    63→- **C6** — Stale evidence is not evidence. A completion event whose `gen` is older than the newest `gen` the host has observed for that session is dropped (§4.2).
    64→- **C7** — **Scrubbing pattern.** While dragging, the UI shows a *ghost* position (clearly uncommitted, e.g. a detached thumb). The committed position updates only on `seek-completed`. This is the one sanctioned transient divergence, and it must be visually distinguishable. `[PROPOSAL]` — exact visual treatment follows the Figma exports.
    65→- **C8** — Idempotent confirmations. If a class-A command finds the engine already in the target state (e.g. `pause` while paused), the engine still emits the completion event as a self-transition (`from == to`). This keeps C3 uniform with no special cases in the UI.
    66→
    67→### 1.5 Completion classes: which commands are S, which are A
    68→
    69→| Class | Meaning | Budget | Examples |
    70→|---|---|---|---|
    71→| **S** (synchronous-complete) | Pure queries; atomic mutations of engine model/config/renderer params with bounded work and **no pipeline invalidation, no unbounded I/O** | Responds within a bounded, small time (target ≤ 50 ms; `[PROPOSAL]` budget, measured in Phase 2) | `set_volume`, `set_rate`, `set_mute`, `set_aspect_ratio`, all `get_*`/`list_*`, playlist model edits, settings |
    72→| **A** (async-observed) | Anything that reconfigures the decode pipeline, performs unbounded I/O, can fail asynchronously, or whose *effect* is only observable through engine state | Returns `Accepted` immediately; completion via a named event | `session.open`, `play`/`pause`/`stop`, `seek`/`set_position`/`set_chapter`/`step_frame`, video/audio track switch, `set_audio_device`, `take_screenshot`, `subtitle.add-file`, `playlist.play-item`/`next`/`prev`/`skip` |
    73→
    74→Classification policy (for future entries): default to **A** unless the operation is provably atomic and bounded. When in doubt, A — an unnecessary event is cheap; a false “success” is a truth violation.

    76→### 1.6 Envelope — type sketches
    77→
    78→```rust
    79→// crates/commands — authoritative sketch (wire forms in §5 use serde with
    80→// camelCase field names, internally-tagged enums, kebab-case variant names)
    81→
    82→pub struct RequestId(pub u64);     // monotonic per host connection, §4.1
    83→pub struct SessionId(pub u64);     // engine-assigned, §4.1
    84→pub struct Generation(pub u64);    // per-session pipeline generation, §4.2
    85→
    86→pub struct CommandRequest {
    87→    pub request_id: RequestId,
    88→    pub command: Command,          // tagged enum, one variant per catalog entry
    89→}
    90→
    91→pub enum CommandOutcome {
    92→    /// Class A: queued/started. `gen` is the generation under which the
    93→    /// completion event will arrive (new gen for gen-bumping commands).
    94→    Accepted { session: Option<SessionId>, gen: Generation },
    95→    /// Class S: the engine confirms completion *in this response*.
    96→    Completed(CommandResult),
    97→}
    98→
    99→pub struct CommandResponse {
   100→    pub request_id: RequestId,             // echoed, always
   101→    pub session: Option<SessionId>,        // session context at handling time
   102→    pub gen: Generation,                   // session gen at handling time
   103→    pub result: Result<CommandOutcome, CommandError>,
   104→}
   105→
   106→pub struct CommandError {
   107→    pub stage: Stage,          // where it failed
   108→    pub code: ErrorCode,       // typed failure class
   109→    pub message: String,       // redacted, display-safe
   110→    pub details: BTreeMap<String, String>, // machine-readable hints
   111→}
   112→
   113→pub struct Event {
   114→    pub seq: u64,                       // engine-global, strictly increasing
   115→    pub session: Option<SessionId>,     // None for session-less events
   116→    pub gen: Option<Generation>,        // present for pipeline-scoped events
   117→    pub origin: Option<RequestId>,      // present when caused by a command
   118→    pub kind: EventKind,                // tagged enum, one variant per event
   119→}
   120→// Wire note: `kind` is the envelope tag carrying the event ID. Payload field
   121→// names are chosen to never collide with it (hence `seekKind`, `trackKind`).
   122→```
   123→
   124→The full error taxonomy (`Stage`, `ErrorCode`) is in §2.13. The state machine referenced below is §3.3.

   128→## 2. Command catalog v1
   129→
   130→### 2.1 Command IDs: stable kebab-case strings ↔ Rust variants
   131→
   132→An ID is `<area>.<verb-noun>` — an area token, a dot, then one or more kebab-case tokens. The Rust mapping is mechanical: split on `.` and `-`, Pascal-case each token, concatenate.
   133→
   134→| Wire ID | Rust variant |
   135→|---|---|
   136→| `session.open` | `CommandId::SessionOpen` |
   137→| `playback.toggle-play-pause` | `CommandId::PlaybackTogglePlayPause` |
   138→| `audio.set-volume` | `CommandId::AudioSetVolume` |
   139→| `tracks.set-subtitle-track` | `CommandId::TracksSetSubtitleTrack` |
   140→
   141→IDs are **stable forever within major version 1** (§6). The enum is `#[non_exhaustive]`; hosts must match with a catch-all that maps unknown IDs to `invalid-argument` (senders) or a generic no-op with a logged warning (event receivers).
   142→

   180→### 2.2 Common parameter and result types
   181→
   182→```rust
   183→pub struct Timestamp(pub i64);            // microseconds since media start; can be negative only in Relative
   184→pub enum Duration { Known(Timestamp), Unknown, Infinite } // never a sentinel
   185→
   186→pub type Volume = f32;                    // 0.0..=audio.max_volume (config, default 1.25) [PROPOSAL]
   187→pub type Rate = f32;                      // (0.0, playback.max-rate] (config, default 16.0) [PROPOSAL]
   188→
   189→pub struct TrackId(pub u32);              // stable within one session, never reused inside it
   190→pub struct PlaylistItemId(pub u64);       // stable within the playlist lifetime, never reused
   191→
   192→pub enum TrackKind { Video, Audio, Subtitle, Data }
   193→
   194→pub enum TrackSelector { Id(TrackId), None, Auto } // Auto is meaningful for subtitles only
   195→
   196→pub struct TrackInfo {
   197→    pub id: TrackId,
   198→    pub kind: TrackKind,
   199→    pub name: Option<String>,             // from container metadata (untrusted text, V7)
   200→    pub language: Option<String>,         // BCP-47 tag when present
   201→    pub codec: CodecDescriptor,           // { fourcc, description, profile, level }
   202→    pub is_default: bool,
   203→    pub is_selected: bool,
   204→    pub origin: TrackOrigin,              // Stream | ExternalSubtitle
   205→    pub video: Option<VideoTrackInfo>,    // width, height, frame_rate, bit_depth, hdr
   206→    pub audio: Option<AudioTrackInfo>,    // channels, sample_rate, bit_depth, codec_params
   207→}
   208→
   209→pub enum SeekTarget {
   210→    Absolute { time: Timestamp },         // µs from media start; clamped when duration known
   211→    Relative { delta_ms: i64 },           // negative rewinds
   212→    Percent { fraction: f32 },            // 0.0..=1.0 of duration (requires known duration)
   213→    Chapter { index: u32 },               // jump to chapter start
   214→}
   215→
   216→pub enum SourceSpec {                     // clean-room source description (no libvlc types)
   217→    File { path: PathBuf },

   220→}

   224→
   225→| ID | Params | Class | Result / Completion | Errors (specific) | Notes |
   226→|---|---|---|---|---|---|
   227→| `session.open` | `source: SourceSpec`, `options: OpenOptions` | A | `Accepted { session, gen: 0 }`; completes on `session.state-changed → playing` (or `paused` if `options.start_paused`); fails via fatal `playback.error { origin }` | `inaccessible`, `unsupported`, `network`, `corrupt`, `resource-limit`, `feature-not-exposed`, `unsupported-for-host` | Replaces any current session (implicit close). Emits `opening` → (`opening-progress`) → `buffering` → `playing` and `tracks.list-ready`, `media.info-ready` before completion. `OpenOptions`: `start_time`, `start_paused`, `rate`, `no_video`, `no_audio`, `track` selectors, `forced_subtitle_only` — schema-validated, unknown option = `invalid-argument`. |
   228→| `session.close` | — | S | `Completed(Unit)` | — | Idempotent; closing a closed/absent session is still `Unit`. Bumps `gen` (terminal), frees decoder threads with a bounded join deadline (2 s `[PROPOSAL]`), destroys the session.    285→### 2.9 Playlist commands
   286→
   287→The playlist is a model owned by the engine; model edits are class S. Two edits have **engine-initiated side effects** that are class A lifecycles of their own: removing/clearing the *playing* item and replacing the list while playing trigger the normal advance/stop state events with `origin: None`. The S response covers only the model edit (documented so the UI is not surprised by following events).

   336→### 2.13 Common error set and redaction (Trace: MP §8, §12)
   337→
   338→Every command can fail with any of these; the catalog tables above list only additions.
   339→
   340→```rust
   341→pub enum Stage { Session, Input, Probe, Demux, Decode, AudioOutput, VideoOutput,
   342→                 Subtitle, Renderer, Playlist, Config, Plugin, Control }
   343→
   344→pub enum ErrorCode {
   345→    // media/engine failures (MP §8 — the seven canonical classes)
   346→    Unsupported,        // no demuxer/decoder/filter for this data
   347→    Corrupt,            // malformed bitstream/container
   348→    Inaccessible,       // unreadable file, permission, auth failure
   349→    Network,            // connection, DNS, TLS, timeout
   350→    Decoder,            // decode failure after selection
   351→    Device,             // audio/video device failure
   352→    ResourceLimit,      // bounded memory/queue/probe limits hit
   353→    // command-layer failures (this document)

   360→}

   367→## 3. Event catalog v1
   368→
   369→### 3.1 Envelope, delivery, ordering (summary; details §4)
   370→
   371→Events are engine→host notifications. Each carries `seq` (global, strictly increasing), optional `session`, optional `gen`, optional `origin` (the `request_id` of the command that caused it, when attributable). Within one host connection, events and command responses share a single ordered delivery channel — a response is causally positioned exactly between the events emitted before and after it (§4.3).
   372→
   373→### 3.2 Event table

   404→
   405→### 3.3 Playback state machine (Trace: MP §8 “bounded, observable recovery”)
   406→
   407→```rust
   408→pub enum PlaybackState { Idle, Opening, Buffering, Playing, Paused, Stopped, Ended, Error }
   409→// wire: "idle" | "opening" | "buffering" | "playing" | "paused" | "stopped" | "ended" | "error"
   410→```
   411→
   412→Valid transitions (conformance-tested): `idle→opening` (open), `opening→{buffering, error, idle}` (early probe failure exits via `error` then `idle` on close), `buffering→{playing, error}`, `playing↔paused`, `playing→buffering` (rebuffer), `playing/paused→{stopped, ended, error}`, `stopped/ended/error→idle` (close/replace), plus self-transitions for idempotent confirmations (C8). Any other sequence is a conformance failure. Every session-lifecycle event after `session.open`’s `Accepted` carries that session’s current `gen`; `state-changed → error` is always accompanied by a fatal `playback.error` (ordering: `playback.error` first, then `state-changed`).
   413→
   414→### 3.4 Throttling rules (summary)
   415→
   416→1. `time-tick` is the only continuous stream; its interval is config-driven (default 250 ms, floor 50 ms) and it is **never queued** — at most one tick in flight per session; a newer tick replaces an undelivered older one.
   417→2. Progress events (`buffering`, `opening-progress`) are monotonic within one episode and coalesced to their rate cap.
   418→3. All other events are discrete and unthrottled, bounded naturally by the operations that cause them.
   419→4. The engine guarantees a burst bound: no more than 1 000 events/s sustained to any host connection; beyond that `system.log` is dropped first (with a final aggregate line). `[PROPOSAL]` — number to be validated against the UI budget in Phase 2.

   423→## 4. Correlation and ordering
   424→
   425→### 4.1 `request_id` — monotonic per host connection
   426→
   427→- `u64`, assigned by the **sender** (UI, CLI, control client), starting at 1, strictly monotonic within one connection. Reuse is forbidden; hosts that reload (webview refresh) restart at 1 — safe because the engine never compares ids across connections.
   428→- The engine **echoes** `request_id` in every response and in `origin` on attributable events. It does not interpret ids (except the control server, which enforces monotonicity per connection as an anti-replay measure, §5.4).
   429→- The typed clients (§5) expose promise-based APIs: `client.seek(target)` allocates the id, sends, and resolves on the matching response (`Accepted` for class A) — completion is awaited via the event API (`client.waitFor("seek-completed", { gen })`) or a convenience `seekAndComplete()` that does both and enforces C1–C6 internally, so application code cannot accidentally violate the truth rule.
   430→
   431→### 4.2 Generation IDs (Trace: MP §8 “generation IDs or cancellation tokens”)
   432→
   433→- Per-session `gen: u64`, starting at 0 at open. The engine increments it **atomically at accept time** of any gen-bumping command: `playback.seek`, `playback.set-position`, `playback.step-frame`, `media.set-chapter`, `playback.stop`, `tracks.set-video-track`, `tracks.set-audio-track`, `session.close` (terminal), plus engine-initiated invalidations (end-of-media restart). `[03]` governs how the engine propagates cancellation internally; on the wire only `gen` is visible.
   434→- **Reconciliation with [03] §5 (two-level epochs).** 03 defines a *session epoch* (minted on open/source replacement) and a *pipeline generation* (bumped on seek/switch/stop). Wire mapping: `SessionId` ↔ 03 session epoch; `gen` ↔ 03 pipeline generation. 03’s internal event names map to wire IDs: `StateChanged` → `session.state-changed`, `TracksChanged` → `tracks.list-ready`, `Seeked` → `timing.seek-completed`, `Buffering` → `session.buffering`, `SessionClosed` → (absorbed: `session.close` response + session filtering), `FirstFrame` → internal trigger of the `playing` transition, no separate v1 wire event. Any further 03-internal events are engine-private and must not leak onto the wire.
   435→- `Accepted` responses to gen-bumping commands carry the **new** gen; non-bumping async commands carry the current gen.
   436→- **Staleness rule (hosts):** ignore any pipeline-scoped event whose `gen` is lower than the highest gen observed for that session (via `Accepted` responses or events). The typed clients implement this once; hand-rolled consumers are a contract-test target (§7.3).
   437→- **Staleness rule (engine):** a superseded seek emits **no** terminal event — seek A canceled by seek B is silent; only B’s lifecycle is observable. This prevents error flashes and makes “exactly zero or one terminal seek event per gen” a testable invariant.
   438→- A gen-bumping command raced against a pending class-A command of an older gen implicitly cancels it: the older command’s completion either arrives before the bump (valid) or is suppressed as stale. There is no “zombie success”.
   439→
   440→### 4.3 Ordering guarantees
   441→
   442→1. `seq` is engine-global, `u64`, strictly increasing, assigned at emission. A host observes a strictly increasing `seq` stream (per connection); gaps indicate filtered events (subscriptions, §4.4) or dropped `system.log` lines — never reordering.
   443→2. Events and responses travel one ordered channel per host connection: the engine emits `Accepted` for request R before any event caused by R; delivery preserves that causal order end-to-end in every binding (Tauri event + invoke ordering caveat noted in §5.1).
   444→3. Per session, events are totally ordered by `seq`; cross-session order is unspecified (concurrent sessions are not a v1 UI concern, but the control server may see them interleaved).
   445→4. Terminal invariants (conformance-tested): exactly one terminal seek event per completed seek gen; `state-changed → error` always preceded by its fatal `playback.error`; `tracks.list-ready` is delivered before the first `state-changed → playing` of a session; `duration-known` is delivered before any `time-tick` that assumes it.
   446→
   447→### 4.4 Subscription model
   448→
   449→- **In-process hosts** (Tauri, wasm, CLI): all events are delivered to the host; filtering happens client-side (typed client exposes `on(eventId, filter)`).
   450→- **Control server:** explicit `subscribe { topics }` / `unsubscribe` protocol messages. Topic syntax: exact ID, `area.*` (single level), `area.>` (multi-level, MQTT-style). `[PROPOSAL]` Default subscription after `hello`: nothing (deny-by-default); clients subscribe explicitly. Sensitive topics are none today because no event payload carries secrets (V8) — the rule exists so future events must justify inclusion.
   451→- **Reconnect/hydration:** late joiners and reconnecting clients call `system.get-state-snapshot`, then subscribe; `seq` lets them detect anything missed in between (gap = re-snapshot). `[PROPOSAL]`

   455→## 5. Bindings — four hosts, one catalog
   456→
   457→### 5.1 Tauri IPC (desktop) (Trace: MP §2 “Desktop shell: Tauri”)
   458→
   459→**One registered command.** The desktop shell registers a single Tauri command:
   460→
   461→```rust
   462→#[tauri::command]
   463→async fn lumen_dispatch(state: tauri::State<EngineHandle>,
   464→                        request: CommandRequest) -> Result<CommandResponse, CommandError>
   465→```
   466→
   467→Rationale: a generic entrypoint keeps the catalog data-driven (no per-command Rust glue to drift), exercises exactly one serde path, and makes the anti-bypass test trivial (§7.4 — the shell must register exactly one command). `CommandRequest`/`CommandResponse`/`Event` derive `Serialize`/`Deserialize` with `rename_all = "camelCase"`, internally-tagged enums (`"cmd"`, `"kind"`), and kebab-case variant names — e.g.:
   468→
   469→```json
   470→// UI → engine
   471→{ "requestId": 42, "cmd": "playback.seek", "args": { "target": { "kind": "relative", "deltaMs": -10000 } } }
   472→// engine → UI (response)
   473→{ "requestId": 42, "session": 7, "gen": 3, "result": { "accepted": { "session": 7, "gen": 4 } } }
   474→// engine → UI (event, via Tauri event channel "lumen://event")
   475→{ "seq": 1031, "session": 7, "gen": 4, "origin": 42, "kind": "timing.seek-completed",
   476→  "position": 63000000, "seekKind": "command" }
   477→```
   478→
   479→**Events.** The shell forwards every engine event with `app_handle.emit("lumen://event", &event)`. Ordering caveat: Tauri `invoke` responses and `emit` travel different JS-side microtask paths, so the shell **must** forward both through the same `tokio::mpsc` before touching the webview, preserving §4.3 guarantee 2; the conformance suite tests this on the Tauri mock host.
   480→
   481→**Shared types.** `[PROPOSAL]` **Schema-first codegen**: `crates/commands` derives `schemars::JsonSchema` for every wire type; `cargo xtask schema-gen` emits (a) `schemas/commands.schema.json` — the single machine description of the catalog; (b) `ui/packages/commands/src/types.ts` — the TS types the UI imports; (c) validation JSON Schemas reused by the control server and the keymap validator; (d) this document’s tables can later be generated from the same source. CI fails on drift between Rust types and generated artifacts. No TS type is ever hand-written.
   482→
   483→**Typed client.** `ui/packages/client` wraps `invoke("lumen_dispatch")` + `listen("lumen://event")` into the promise/event API of §4.1, implementing the staleness filter and C1–C6 once. The UI imports only `@lumen/client` and `@lumen/commands` types.
   484→
   485→### 5.2 WASM binding (web) (Trace: MP §2 “Web build”, §10)
   486→
   487→The engine compiles to `wasm32-unknown-unknown`; `apps/web` exposes it through a typed binding package `@lumen/wasm-client` with the same catalog, envelope and semantics.
   488→
   489→- **Single-threaded constraint (v1).** The engine’s internal scheduler is cooperatively chunked: `dispatch()` returns a `Promise`; heavy work (probe, demux, decode batches) runs in bounded slices and yields to the event loop so the page stays responsive; timers and I/O come from host shims (`Performance`, `fetch`). No blocking waits exist on this path.
   490→- **Worker-thread plan.** Per MP §10, the production web host runs the engine in a dedicated **Web Worker** with `postMessage` request/response and transferable frame buffers to the main-thread canvas; the typed client API is unchanged (it abstracts the worker channel). Threads inside wasm (`SharedArrayBuffer`, wasm threads) additionally require COOP/COEP headers — served by `apps/web` and recorded as a deploy requirement, not a fallback to native code.
   491→- **Rendering/audio.** WebGPU with WebGL fallback (MP §10); WebAudio output. These are host capabilities behind the same commands (`video.*`, `audio.*`).
   492→- **Capability gaps are typed, not silent.** Commands the web host cannot honor return `unsupported-for-host`: optical discs, capture, RTSP/UDP (no raw sockets), `audio.list-devices` beyond the single WebAudio device, local-filesystem paths in `session.open` (URLs and transferred `Blob`s only — the File System Access API may lift this later `[PROPOSAL]`). Feature-matrix web column tracks each gap with its reason.
   493→- **Param variants for web.** `subtitle.add-file` accepts a transferred `Blob`; `session.open` accepts `Url` sources and blobs. Same command IDs, schema-validated variant. `[PROPOSAL]`
   494→
   495→### 5.3 CLI (apps/cli) (Trace: MP §4 layout, §5 settings-driven help)
   496→
   497→The CLI is a headless host consuming the same catalog through an in-process channel. Two modes:
   498→
   499→- **Interactive/controller mode** (default when a media is given): opens the media, renders a minimal TUI/status line, applies subcommands, and exits on end-of-media or `q`.
   500→- **Machine mode**: `--json` emits every event as one NDJSON line on stdout; requests are accepted on stdin as NDJSON envelopes (`lumen --control-stdio`). `[PROPOSAL]` — this stdio control mode is also the transport used by the conformance suite’s `CliHost` (§7.2) and doubles as a scripting interface.

   535→### 5.4 Control server (apps/control-server + crates/control-protocol) (Trace: MP §3.5, §12)
   536→
   537→An optional local control surface for automation and remote-control-style UIs.
   538→
   539→- **Loopback-only bind.** Listens on `127.0.0.1` / `::1` only (default port from config, or `0` = ephemeral; `control-server.enabled` defaults to **false**). Any configuration that requests a non-loopback address is a **startup error**, not a warning — deny-by-default is structural, not advisory.
   540→- **Versioned protocol.** `[PROPOSAL]` Transport: WebSocket with JSON text frames (browser-reachable), defined in `crates/control-protocol` as typed serde enums reused by both ends — never hand-rolled on either side. Envelope: `{"v":1,"type":"hello"|"welcome"|"request"|"response"|"event"|"subscribe"|"unsubscribe"|"protocol-error"}`. Negotiation: client `hello` lists supported major versions; server picks the highest mutually supported major and answers `welcome { v, engineInfo, capabilities }`, otherwise closes with a protocol error code. One major per connection; serving two majors means two listeners/paths during migrations (§6.3).
   541→- **Authentication — token handshake.** `[PROPOSAL]` The server generates a 256-bit random token per start and (a) writes it to `<runtime-dir>/lumen/control-token` with mode 0600, or (b) inherits it via `--control-token-fd` from a launching wrapper, or (c) prints it to stdout with `--print-token`. The client presents the token in `hello`; comparison is constant-time. Failure closes the connection (WS close code 4401); 5 failures impose a 60 s lockout and a log entry. Without a valid token **no command is executed** — deny-by-default. An explicitly configured `read-only` mode admits unauthenticated clients to a fixed safe subset (`media.get-info`, `system.get-engine-info`, `tracks.list`, snapshot) and nothing else; `session.open` stays privileged because it touches the local filesystem.
   542→- **Request validation.** Every frame: max 1 MiB; schema-validated against `schemas/commands.schema.json` (same artifact as §5.1 — one schema, all hosts); unknown fields/IDs rejected; `request_id` monotonicity enforced per connection (anti-replay); per-connection concurrency cap (8 in-flight requests) and rate limit (100 req/s burst 200) `[PROPOSAL]` numbers. Non-negotiable: reflection, arbitrary path access and plugin installation are out of scope for v1 control.
   543→- **Origin check.** Browser WS clients present an `Origin`; the server rejects any origin not on the configured allowlist (default empty → non-browser clients only). `[PROPOSAL]`
   544→- **Redaction.** Tokens never logged; URLs credential-stripped before logging; error messages pass V8.

   548→## 6. Versioning and evolution (Trace: MP §5 “schema version and migrations”)
   549→
   550→### 6.1 The v1 namespace
   551→
   552→All IDs in §2–§3 live under implicit major **v1**. `CommandId` values, param shapes, result shapes, event payloads and error codes are frozen at v1 except for the additive rules below. The wire envelope carries an explicit version on hosts that negotiate (control server `v`; Tauri/wasm/CLI are same-build, so `system.get-engine-info → catalog_version` is the runtime check).
   553→
   554→### 6.2 Additive-change rules (within a major)
   555→
   556→**Allowed:** new command IDs; new event IDs; new *optional* params (serde default, never required); new optional result fields; new `ErrorCode`/`Stage` values (clients must degrade unknown codes to a generic failure with the message); new `CommandOutcome` shapes are **not** allowed; new `PlaybackState` variants only with a documented transition extension.
   557→
   558→**Forbidden:** removing, renaming, retyping, or re-semanticizing any ID, param, result, event, or error code; changing enum variant names; changing `Accepted`/`Completed` classification of an existing command (UI truth logic depends on it); changing generation or ordering semantics.
   559→
   560→**Rule of thumb:** a v1 client that ignores everything it does not recognize must keep working against any v1.x engine.
   561→
   562→### 6.3 Deprecation and major bumps
   563→
   564→Entries gain `deprecated_in` metadata (surfaced via `system.list-commands`); deprecated commands keep working for the entire major. Removal happens only at a major bump, announced in the release notes and in `welcome` capability flags. The control server negotiates majors per connection, so an engine supporting v1+v2 can serve old clients during a migration window. Catalog majors track the `commands` crate major version.
   565→
   566→### 6.4 Feature-gating by product.toml (Trace: MP §5 “Feature exposure lists only implementations that exist”)
   567→
   568→Each catalog entry declares the features it requires (e.g. `session.open` + `SourceSpec::Disc` → `optical-disc`; URL schemes → `streaming.http`, `streaming.rtsp`; `audio.list-devices` → `audio.device-enumeration`). Effective availability at runtime = engine build features ∩ `product.toml` feature exposure ∩ host capability (web). A command outside the effective set returns `feature-not-exposed` (config-off) or `unsupported-for-host` (host-incapable) with the missing feature named in `details`. UIs render menus from `system.list-commands` + `get-engine-info → features`, so unavailable entries grey out **from data**, never from hardcoded lists. Config can never enable a missing implementation (MP §5).

   572→## 7. Contract tests — the testkit conformance suite (Trace: MP §13)
   573→
   574→### 7.1 Design
   575→
   576→`crates/testkit` defines the host abstraction and one **data-driven conformance suite**; every host implements the abstraction and runs the same scenarios. A scenario file (`tests/contract/scenarios/*.toml`) is a list of steps:
   577→
   578→```toml
   579→[[scenario]]
   580→name = "seek-superseded"
   581→steps = [
   582→  { open = "fixture://sine-colorbars-30s.mkv", expect_state = "playing" },
   583→  { send = { cmd = "playback.seek", target = { kind = "absolute", time_us = 1000000 } },
   584→    expect = { accepted = { gen_bump = true } } },
   585→  { send = { cmd = "playback.seek", target = { kind = "absolute", time_us = 20000000 } },
   586→    expect = { accepted = { gen_bump = true } } },
   587→  { expect_events = [
   588→      { kind = "timing.seek-completed", gen = "latest", position_us = 20000000 },
   589→    ],
   590→    forbid_events = [ { kind = "timing.seek-completed", gen = "older" },
   591→                      { kind = "timing.seek-failed" } ] },
   592→]
   593→```
   594→
   595→Scenario categories (minimum): open→play→pause→stop happy paths; open of missing/corrupt/unsupported fixtures (`error` paths with exact stage/code); seek on unseekable live stream (`not-seekable`); **stale-generation races** (the case above; also seek-vs-stop, track-switch-vs-seek); idempotent self-transition echoes; event ordering invariants (§4.3.4); state-machine transition legality (§3.3); error redaction (no fixture path/URL leaks in `message`); subscription filtering and `seq` gap detection (control host); throttle conformance (`time-tick` rate, buffered coalescing). Fixtures come from `tests/fixtures` (legally distributable, plus generated malformed/truncated files, MP §13).
   596→
   597→### 7.2 The four hosts under test
   598→
   599→| Host | Implementation | Exercises |
   600→|---|---|---|
   601→| `TauriMockHost` | runs the real `lumen_dispatch` handler against a mock `AppHandle`, same serde path as IPC | serialization, shell routing, event forwarding order |
   602→| `WasmNodeHost` | `wasm-bindgen-test` in Node (jsdom for any DOM shims), engine compiled to wasm32 | wasm slicing/yielding, capability errors, blob param variants |
   603→| `CliHost` | spawns `apps/cli --control-stdio --json`, NDJSON over stdin/stdout | CLI arg mapping, machine-mode envelopes |
   604→| `ControlHost` | spawns `apps/control-server` on `127.0.0.1:0`, performs token handshake | auth (valid/invalid/lockout), negotiation, validation, rate limits |
   605→
   606→The suite is merge-blocking in CI and runs on Windows, Linux and macOS for the native hosts (MP §13); the wasm host runs in the web job.
   607→
   608→### 7.3 Truth-rule assertions
   609→
   610→Every scenario that contains a class-A command asserts the **no-early-success** property at the client level: the typed client must not resolve `andComplete()` before the terminal event, and mock-UI harnesses (a tiny scripted consumer using `@lumen/client`) assert that no “success” render callback fires before the completion event. This makes C1–C8 executable, not aspirational.
   611→
   612→### 7.4 Bypass prevention — “the UI never goes around the layer”
   613→
   614→1. **Import allowlist** (lint on `ui/`): engine-adjacent imports limited to `@lumen/commands`, `@lumen/client`; `dependency-cruiser`/ESLint `no-restricted-imports` fails CI on violations. `[PROPOSAL]`
   615→2. **ESLint bans** direct Tauri `invoke`/`listen` calls outside `@lumen/client` (`no-restricted-globals`/`no-restricted-properties` rules). `[PROPOSAL]`
   616→3. **Single-command check**: an architecture test reads the desktop shell’s `invoke_handler` registration and fails if any command other than `lumen_dispatch` is registered.
   617→4. **Web build**: only `@lumen/wasm-client` may import the wasm package (build-time module graph assertion). `[PROPOSAL]`
   618→5. **Cargo boundary check** (already mandated MP §3.8): `apps/*` and `ui` may depend on `crates/commands` types but never on engine internals; the testkit depends on production crates, never the reverse (MP §3.7).

   622→## 8. Keymaps and menus as data (Trace: MP §5 “Commands and keymaps are data”)
   623→
   624→### 8.1 Keymap format
   625→
   626→`config/keymaps/default.toml` (seed) with user-override layering identical to settings precedence (MP §5). Validated by `schemas/keymap.schema.json` and `cargo xtask config-validator`:
   627→
   628→```toml
   629→schema = "keymap.v1"
   630→[[binding]]
   631→id = "seek-forward-short"          # stable binding id (menus reference these)
   632→key = "Right"                       # canonical key name; modifiers: "Ctrl+Right", "MediaNext"
   633→command = "playback.seek"
   634→args = { target = { kind = "relative", delta_ms = 10000 } }
   635→mode = "player-focused"             # player-focused | global | always
   636→when = "has-media"                  # condition tokens: has-media, has-video, fullscreen, has-chapters
   637→```
   638→
   639→Validator failures are hard errors: unknown command ID, args that fail the command’s param schema, duplicate `key`+`mode` combos, and contradictory conditions. Menu accelerators reference binding **ids** (not raw keys), so a user rebinding updates every menu automatically. `[PROPOSAL]` — binding-id indirection.

   675→### 8.3 Menus as data
   676→
   677→`layouts/menus.toml` declares menu trees (MP §5 “which panels, menus… exist, and their order, come from layout config”): each leaf is `{ label_key, command | ui_action, args?, accelerator_binding? }`. Representative v1 menu→command map:
   678→
   679→| Menu | Item → target |
   680→|---|---|
   681→| Media | Open File… (ui-action), Open URL… (ui-action), Save Playlist… (`playlist.save`), Quit (shell) |

   683→| Audio | Volume ▸ (`audio.set-volume`), Mute (`audio.set-mute`), Audio Device ▸ (dynamic → `audio.set-device`), Audio Track ▸ (dynamic → `tracks.set-audio-track`), Stereo Mode (feature-gated filter, later) |
   684→| Video | Fullscreen (`video.set-fullscreen`), Aspect Ratio ▸ (`video.set-aspect-ratio`), Crop ▸ (`video.set-crop`), Zoom ▸ (`video.set-zoom`), Video Track ▸ (dynamic → `tracks.set-video-track`), Take Snapshot (`video.take-screenshot`), Deinterlace (feature-gated, later) |
   685→| Subtitle | Add Subtitle File… (ui-action → `subtitle.add-file`), Subtitle Track ▸ (dynamic: auto/none/ids → `tracks.set-subtitle-track`), Sync −100 ms/+100 ms (`subtitle.set-sync`), Scale ▸ (`subtitle.set-scale`), Encoding ▸ (`subtitle.set-encoding`) |

   689→
   690→Menu items whose command is not in the effective feature set (§6.4) render disabled **from data** — consistent with the truthful-UI rule: never show a working-looking control for something the engine cannot do.
   691→
   692→### 8.4 UI-action registry `[PROPOSAL]`
   693→
   694→Engine-irrelevant actions (dialogs, panel toggles, focus management) are declared in `layouts/ui-actions.toml` (id, label_key, capability such as `file-dialog`). Keymap and menu entries reference either `command` or `ui_action` — never both. The registry is schema-validated so the CI “no hardcoded strings / no orphan references” checks (MP §5) cover it.
