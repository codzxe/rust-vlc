Note: both comments claim a whole 188-byte file is "accepted"/"the walk to judge" —
false; the code panics on valid single-packet TS input.

## F2 — MP4 trex +4 skew — CONFIRMED (S2)
Static: `crates/demux/src/mp4/mod.rs:936-946` reads trex payload at id@4 (correct),
duration@16, size@20, flags@24. ISO 14496-12 §8.8.2 layout (payload-relative, after
the 4 version/flags bytes): track_ID@4, desc_idx@8, default_duration@12,
default_size@16, default_flags@20. So duration<-default_sample_size, size<-
default_sample_flags, flags<-OOB (u32be None->0 on the 24-byte minimal payload).
Cross-check: `crates/demux/src/mp4/test_support.rs:414-420` builds trex at SPEC
offsets (track_id, desc, duration=1024@12, size=0@16, flags=0@20) — the fixture
values (0/0) plus trun flag 0x000_0F01 carrying every field explicitly
(test_support.rs:466) mean tests never consume trex defaults: the skew is invisible
to the suite. Real-world impact at mod.rs:1691-1706: a DASH-style trun without
per-sample duration/size/flags (0x100/0x200/0x400 unset) inherits garbage:
duration=default_sample_size, size=default_sample_flags (e.g. 0x02000000 -> every
sample 33 MiB), flags=0. u32be is bounds-checked (.get) so no panic; wrong values
only. S2 (wrong behavior on realistic fragmented MP4).

## F3 — MP4 stts/ctts unclamped entry-count loop — CONFIRMED (S2)
Static: `crates/demux/src/mp4/mod.rs:1253-1257`:
  let count = u32be(body, 4).unwrap_or(0) as usize;  // attacker u32
  for i in 0..count {                                 // NO clamp
      let run = u32be(body, 8 + i * 8).unwrap_or(0) ...
`ctts` identical at :1316-1317 (`for i in 0..count`), and both lack the
`count.min(MAX_SAMPLES)` clamp every sibling applies (stsz:1230, stco:1270,
co64:1280, stsc:1290, stss:1303). Only the inner materialization is clamped

on `lumen open` (reachable: probe names mp4 -> containers::mp4::open ->
