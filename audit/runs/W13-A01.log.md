## THE DOMAIN TRACE — where exactly does an MP4 fall out?

### (1) Who is supposed to pump the engine in interactive mode, and why it doesn't happen

- The engine advances ONLY when the host pumps it. `apps/cli/src/run.rs:14-18` (module doc, verbatim): "Between commands nothing pumps; the explicit `advance [ticks]` host verb is the run-to-end driver (deterministic, no wall-clock sleeps anywhere). Continuous wall-time pumping joins with the session-thread card (3.B3)."
- The REPL loop (`run.rs:220-287`) reads stdin lines; pumping happens (a) via `host.settle()` after class-A commands — **pipeline-only pumps, NO time advance** (host.rs:440-446: "NO time advance, NO tail play-out — the between-commands pacing primitive"), and (b) via `host.advance(ticks)` for the explicit `advance` verb (`run.rs:252`).
- The `interactive` flag (main.rs:15 `stdin().is_terminal()`) is passed into `repl_mode` and then **explicitly discarded** (`run.rs:219: let _ = interactive;`) — the very signal that should arm real-time pacing.
- A complete, unit-tested real-time pump EXISTS one file away: `CliHost::pump_wallclock` (host.rs:523-536, "the GUI session thread's tick … made real", wall-bounded render: "renders only the quanta the device is owed by wall time"). **rg over all of apps/cli: its only callers are `#[cfg(test)]` (host.rs:1892-1933).** No thread, no ticker, no production caller. Card 3.B3 (the session thread) never landed in the CLI.
- Consequence (W00 baseline, `audit/runs/baseline/mp4-smoke3-stdout.txt`): `lumen open sample-h264-aac.mp4` → tracks parsed (2), duration known, `state-changed Buffering → Playing`, then `ok: time 0.000000s (0.0%)` forever; the one-shot smoke (`mp4-smoke.txt`) timed out (`exit=124`) because the REPL blocks on stdin while the session sits frozen. `advance-test.txt` proves the same freeze for the WORKING MJPEG AVI vertical until `advance` — this is container-independent.
- Clock mechanics: an audio-bearing session (h264+aac MP4 qualifies — mp4.rs:200-203 harvests the mp4a geometry pair, so the AAC limb wires) runs `MediaClock::audio_master` over the null-sink counter (pipeline_host.rs:1605-1609); the counter moves ONLY on renders, renders happen ONLY in `advance_time` (host.rs:703-740), which ONLY `advance` calls. Hence 0.000000s. Video-only sessions would run a system-monotonic clock (`wall_clock`, pipeline_host.rs:1629-1635) — a different failure shape.

### (3) Is "voe" language metadata a parsing bug? YES — off-by-one in mdhd unpacking

- `crates/demux/src/mp4/mod.rs:534-539` (verbatim):
```rust
/// Unpack the mdhd 3×5-bit language code; `None` for "und".
fn unpack_language(packed: u16) -> Option<String> {
    let c = |shift: u32| -> char { (b'a' + ((packed >> shift) & 0x1F) as u8) as char };
    let tag: String = [c(10), c(5), c(0)].iter().collect();
    if tag == "und" { None } else { Some(tag) }
}
```
- ISO/IEC 14496-12 packs each char as `0x60 + value` (0x60='`'); this code adds `b'a'` (0x61) — **one too many**. "und" packs as (u=21, n=14, d=4) → 0x55C4; decoded with +0x61 it yields (22, 15, 5) = **"voe"** — exactly the `language: Some("voe")` W00's mp4-smoke3-stdout.txt showed on BOTH tracks of sample-h264-aac.mp4.
- Double damage: every real language code is corrupted ("eng" → "foh") AND the `tag == "und"` filter can never fire (the correct "und" is unreachable), so undetermined tracks advertise a bogus language instead of None.
- File ownership: crates/demux/src/mp4/mod.rs belongs to the demux wave — recorded here for Wave 20 A01-A03 re-verification with full evidence; severity S2 (wrong behavior on every MP4, metadata-only blast radius).
