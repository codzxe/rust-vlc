## XTASK PARITY-REPORT TRACE (domain hostile question — READ-ONLY analysis of tools/xtask/src/cmd/parity_report.rs, 325 lines; not an assigned audit file, no audit file written for it)

Q1: "Trace the code that computes 'parity' and state exactly what a row
must have to count."

Entry: `cargo xtask parity-report` (alias: .cargo/config.toml:15) →
`parity_report::run` (parity_report.rs:56) → reads docs/feature-matrix.toml
(default, :58) → `toml_lite::parse` (:100) → `compute_table(&doc)` (:108).

The counting rule (parity_report.rs:143-148, verified sed):
```rust
            if value == "implemented" || value == "verified" {
                stats.imp_ver[idx] += 1;
            }
            if value == "verified" {
                stats.verified[idx] += 1;
            }
```
A row counts toward a platform's parity numerator IFF:
(a) it is a `[[feature]]` array-of-tables entry (denominator: every such
row, `stats.rows += 1` at :126 — 252 today);
(b) its `status` inline table contains that platform key with the EXACT
string `implemented` or `verified`. The strict second table counts ONLY
exact `verified`. Case/typo variants match nothing and are silently
skipped (no error in parity-report itself; see Q3 backstop). Missing
platform keys are skipped (`continue`, :140-142); missing `status` table
→ row still in denominator (:127-134). Category missing → "?" bucket
(:118-124).
