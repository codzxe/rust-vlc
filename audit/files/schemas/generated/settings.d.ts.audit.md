What is wrong: "the typed settings surface for the UI" — the UI imports none of it (verified: zero references to this file or its exported types outside the generator, its tests, and xtask docs). So the one artifact whose entire purpose is typed UI settings keys delivers its types to nobody, and the UI ships stringly-typed keys.
Why it matters: this is the exact drift class the hostile focus asked about — not byte drift (none) but CONSUMER drift: two parallel pipelines emit the same 121 entries, one typed-but-dead, one live-but-untyped. A key renamed in settings.toml silently changes the dead union (CI-green) while the live UI keeps compiling against the string; nothing fails until runtime.
What correct looks like: either wire the UI to import `SettingKey` from this file (tsconfig path mapping to schemas/generated, or copy it in gen-tokens-style bridge with a sha pin), or delete G1 and let the npm generator emit the union type.
