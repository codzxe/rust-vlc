## 1. One-paragraph verdict
The repo root ships a broken npm lockfile: it contains committed, unresolved git
merge-conflict markers (`<<<<<<< HEAD` / `=======` / `>>>>>>> wip/p4-f2`), so it is not
parseable JSON (python3 `json.load` fails at line 2); it locks nothing (`"packages":
{}`); it names workstream branches ("p4-e4", "p4-f2") instead of any product; and it
is orphaned — no root package.json exists. It was born when two workstream branches
each accidentally created a root lockfile, then merge commit 66fc455b committed the
conflict unresolved. Nothing in CI, tooling, or docs reads it, so it breaks no in-repo
pipeline — it is pure pollution that (a) proves merges get committed with conflicts,
and (b) will confuse any external scanner (Dependabot is configured to look at `/`,
with its own broken config, F-003).

## 2. What actually works (verified)
Nothing. The file has no valid content and no consumer. (The REAL npm lockfile of this
repo is ui/package-lock.json — exercised by baseline #21 `npm ci` OK and #22-24
build/test/tokens PASS, all in ui/.)

## 3. Findings

### F-001 [S3] Committed unresolved merge conflict — file is invalid JSON
Where: package-lock.json:2-6 (cross-evidence: merge commit 66fc455b; python3
JSONDecodeError)
Code:
```
<<<<<<< HEAD
  "name": "p4-e4",
=======
  "name": "p4-f2",
>>>>>>> wip/p4-f2
```
What is wrong: git conflict markers are committed: `git show HEAD:package-lock.json`
starts `{ \n < < < < < < < HEAD` — the markers are in the object at HEAD, not a
working-tree artifact (`git status package-lock.json` clean). The merge commit
66fc455b "merge(p4-f2): see branch log" added exactly these 4 lines alongside real
PlayerScreen changes, i.e. the conflict was committed unnoticed. Parse proof:
`python3 -c "import json; json.load(open('package-lock.json'))"` →
`JSONDecodeError: Expecting property name enclosed in double quotes: line 2 column 1`.
`git grep -l "^<<<<<<< " HEAD` → this is the ONLY tracked file with conflict markers.
Why it matters: a merge was completed while a conflict was unresolved — the process
that would catch this (review, CI) exists nowhere for root-level files; any JSON
consumer that walks the repo root (scanners, editors' npm integration) hits garbage.
What correct looks like: delete the file (F-002) and add a repo rule (or gitattribute
merge=ours) so stray root npm artifacts can't reappear; nothing needs resolving — the
content is worthless.
Confidence: HIGH — Verification: ran (python3 parse, git show/grep/log).

### F-002 [S3] Orphaned, empty lockfile referencing workstream branch names
Where: package-lock.json:3-9 (cross-evidence: `git ls-files`; origin commits 5ac4c131,
f21f407d)
Code:
```
  "lockfileVersion": 3,
  "requires": true,
  "packages": {}
}
```
What is wrong: three independent defects in one artifact: (1) no root package.json
exists (`git ls-files | rg package(-lock)?\.json$` → package-lock.json,
ui/package-lock.json, ui/package.json, ui/tools/eslint-plugin-local/package.json —
nothing for the root lock to lock); (2) `"packages": {}` — zero dependencies locked;
(3) the two conflicting "name" values ("p4-e4", "p4-f2") are workstream ids from
commit subjects 5ac4c131 "feat(ui): 4.E4 settings group 3 ..." and f21f407d "4.F2:
player variants ...", proving two branches each ran a stray root-level npm command and
the junk collided. No doc mentions it (rg over AGENTS.md/README.md/docs → empty).
Why it matters: dead, misleading artifact at the repo's front door; it implies a root
npm project that does not exist and hides the real one's location (ui/).
What correct looks like: `git rm package-lock.json` — the file has no reason to exist.
Confidence: HIGH — Verification: read + git ls-files + git log.

### F-003 [S4] Adjacent: Dependabot is configured to look exactly here — with a broken config
Where: package-lock.json:1 (cross-evidence: .github/dependabot.yml:7-9 — another
agent's assignment, cited as context)
Code (from .github/dependabot.yml):
```
updates:
  - package-ecosystem: "" # See documentation for possible values
    directory: "/" # Location of package manifests
```
What is wrong: the root-npm plane is broken end to end: Dependabot's config is the
unedited GitHub template (`package-ecosystem: ""` is invalid — the template's own
"you'll need to specify" comment is still present) pointing at `directory: "/"`,
where the only npm artifact is the invalid lockfile of F-001. Version updates for the
REAL npm project (ui/) are not configured at all.
Why it matters: the repo's npm dependency surface has zero automated update/audit
coverage; the config that exists points at garbage.
What correct looks like: `package-ecosystem: "npm", directory: "/ui"` (plus the cargo
ecosystem), and delete the root lockfile.
Confidence: HIGH — Verification: read both files.
