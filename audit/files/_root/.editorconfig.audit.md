## 1. One-paragraph verdict
A competent, boring editorconfig — exactly what it should be — for the Rust/TOML/YAML/JSON core: 4-space rs/toml, 2-space yml/json, md exempted from trailing-trim, LF + final-newline everywhere. Its defects are all at the edges: (1) the repo's entire web surface (ts/tsx/js/mjs/css/html — the whole `ui/` tree and the desktop prototype) gets NO indent rule from this file and has no other formatter configured (no prettier, eslint without stylistic rules); (2) it is advisory-only with zero CI enforcement, and the repo already contains a live violation of it (a trailing space in `.github/dependabot.yml:12`); (3) its LF mandate has no exclusion for the 30 tracked files whose CR bytes are deliberate (fuzz corpus, hostile subtitle fixtures, verbatim raw evidence) — the tree's own `.gitattributes` precedent protects exactly one such subtree and none of the others; (4) the docs that define this file call it `.ln`, a filename that does not exist in the tree.

## 2. What actually works (verified)
- Rust/TOML 4-space matches rustfmt defaults (no rustfmt.toml overrides — verified absent) and `cargo fmt --check` is the real enforcement for that half (baseline #7: fails on exactly one dirty rust file — enforcement exists for rs).
- LF/final-newline hold across the sampled live files (Cargo.toml, .editorconfig, crates/media-types/Cargo.toml, ui/package.json all end with \n).
- The md exception is coherent with the file's own comment ("Trailing double-space is a hard line break in Markdown") — and verified harmless: 0 of 458 md files currently carry trailing double-spaces.
- `root = true` stops editor-config lookup at the repo root (ui/ has no nested .editorconfig — verified).

## 3. Findings

### F-001 [S4]
Where: .editorconfig:10-16
Code:
```
[*.{rs,toml}]
indent_style = space
indent_size = 4

[*.{yml,yaml,json}]
indent_style = space
indent_size = 2
```
What is wrong: The only indent rules cover rs/toml/yml/yaml/json. The `[*]` fallback (lines 4-8) sets charset/eol/newline/trim but NO indent_style/indent_size — so every `.ts`, `.tsx`, `.js`, `.mjs`, `.css`, `.html` file in the repo (the entire `ui/` application, `apps/desktop/prototype/lumen-frames.mjs`, all playwright configs) has no configured indentation anywhere: no editorconfig rule, no prettier config (`ls ui/.prettierrc* .prettierrc*` → none), and `ui/eslint.config.js` carries no indent/stylistic rules (rg verified).
Why it matters: `ui/` is a shipped product surface (1705 tests, baseline #23) whose formatting rests on convention; editor drift between contributors is unpreventable and undetectable — the exact problem editorconfig exists to solve, unsolved for the biggest non-Rust tree.
What correct looks like: Add `[*.{ts,tsx,js,jsx,mjs,cjs,css,html}] indent_style = space, indent_size = 2` (matching the ui tree's de-facto 2-space style) or commit a prettier config.
Confidence: HIGH — Verification: read + exhaustive config absence checks.

### F-002 [S4]
Where: .editorconfig:4-8 (cross-ref: .github/dependabot.yml:12)
Code:
```
[*]
charset = utf-8
end_of_line = lf
insert_final_newline = true
trim_trailing_whitespace = true
```
What is wrong: The rule is advisory-only (no workflow or script references editorconfig — `rg -rln 'editorconfig' .github scripts tools` → 0 hits; full_gate.sh checks fmt/clippy/fuzz only), and the tree already violates it in a live CI file: `.github/dependabot.yml:12` is a line consisting of a single trailing space (`cat -A` shows ` $`). The only other trailing-space hit repo-wide is an intentional invalid-syntax fixture. Additionally, the `[*.md]` trim exception protects a hard-break convention that 0 of 458 md files use — dead protection.
Why it matters: A style contract with no enforcement and an existing violation in the repo's own CI config is a contract in name only; the CRLF corruption incident this project already lived through (root-commit e83e5bd3: a stray CR byte in 99_run_all.sh made every tier exit 2) shows line-ending hygiene here has real blast radius.
What correct looks like: A whitespace/eol check in full_gate.sh (one `git grep -In ' $'`-style pass, excluding fixtures/), then fix dependabot.yml:12.
Confidence: HIGH — Verification: read + git grep counts + workflow scan.

### F-003 [S4]
Where: .editorconfig:6 (cross-ref: 30 CR-bearing tracked files; tests/integration/first-vertical/.gitattributes:7)
Code:
```
end_of_line = lf
```
What is wrong: 30 tracked files contain CR bytes deliberately: `fuzz/corpus/fuzz_http_headers` (5), `crates/subtitles/tests/fixtures/{fuzz,canonical,vtt}` (11 — e.g. `crlf2.srt`, the CRLF hostile-input case itself), and verbatim machine captures under `docs/baselines/raw/{linux,macos,windows}`, `docs/packaging/evidence`, `docs/perf/raw*` (14). The editorconfig mandates LF for all of them with no exclusion, and there is no root `.gitattributes` to countermand (the only .gitattributes in the tree protects `tests/integration/first-vertical/evidence/**` with explicit `text eol=lf` + binary png — the pattern exists but was applied to one subtree only).
Why it matters: A contributor opening `crlf2.srt` or a `docs/baselines/raw/windows` capture in an editorconfig-honoring editor and hitting save silently converts the corpus entry/evidence capture to LF — neutering a fuzz case or destroying the byte-fidelity of recorded evidence. Nothing would flag the change except a digested-evidence gate that doesn't exist for docs/perf.
What correct looks like: `[*.{srt,vtt}]` / explicit `end_of_line = unset` (or binary marking) for fixture+corpus+raw-evidence paths, and a root `.gitattributes` marking those trees `-text` or `eol=lf` pinned for machine-written evidence.
Confidence: HIGH — Verification: read + `git grep -Il $'\r'` dir breakdown + .gitattributes read.
