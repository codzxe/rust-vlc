## 1. One-paragraph verdict
The generator is competent POSIX sh (syntax-verified; config-driven name/version
via required env; three tag/dry-run modes with explicit error handling; the
bullet-prefix sed; the truncated-body problem handled honestly at the
CONSUMER (release.yml:1146-1159 truncates at 120k chars with an honest
pointer — the script itself stays complete); full-history wiring verified —
fetch-depth: 0 at release.yml:1017). But its emitted "Known limits (honest)"
section still carries the wave-22 world view, and that text becomes the
PUBLISHED RELEASE BODY via `gh release create` (release.yml:1124,1131+):
it tells users "The desktop binary is the ADR-004 std-only composition-root
skeleton; the CLI is the real engine surface in this release" — FALSE since
w26-M (lumen-tauri, the real GUI shell, ships in every artifact) and w30.8
(the exit-86 skeleton was dropped from every user payload and is a CI-only
diagnostic). The curated, accurate skeleton
docs/release-notes/skeleton-v0.1.3.md says the exact opposite ("Two programs
ship in every artifact ... the placeholder stub binary is gone from every
download") — but the workflow does not consume the skeleton; it consumes this
script's stale text. Every v0.1.3+ release body generated by this path
misdescribes the payload to users. The script ALSO contradicts the repo's own
process doc: docs/RELEASE.md:23-28 states "Through v0.1.2 the payload was
three binaries ... From v0.1.3 the stub leaves every user payload (wave 30):
`lumen` + `lumen-tauri` ship" — and RELEASE.md even maintains a stale-line
strike-through discipline for this exact class of rot (:171 "(Stale since
w28 ...)") while the script's copy went un-updated.

## 3. Findings
F-001 [S0]
Where: scripts/release/release-notes.sh:86-88
Code:
```
    echo "- The desktop binary is the ADR-004 std-only composition-root skeleton;"
    echo "  the CLI is the real engine surface in this release."
```
What is wrong: the emitted text is FALSE for the current release state and is
published as the GitHub Release body (release.yml:1124 -> notes.md -> `gh
release create ... --notes-file` lane at :1131+; the curated
skeleton-v0.1.3.md is NOT consumed by the workflow — rg 'skeleton' in
release.yml hits only a comment). Reality since w26-M/w30.8: every user
payload ships `lumen` + `lumen-tauri` (the real GUI shell; release.yml:5-17,
verify-linux-artifacts.sh's stub-ban die at :160-162), and the exit-86
skeleton "is a CI-only diagnostic" dropped from every download. The generated
notes tell users the desktop binary IS the skeleton and the CLI is the real
surface — a false user-visible claim that also contradicts the repo's own
curated skeleton (docs/release-notes/skeleton-v0.1.3.md:109-110 "Two
programs ship in every artifact"). Why it matters: this is the most
user-visible doc the project emits; it misdescribes what users just
downloaded, in the section titled "(honest)". What correct looks like:
update the template stanza to the w30.8 payload truth (CLI + GUI shell, no
stub), or make the workflow consume the curated skeleton with the generated
Changes section spliced in. Confidence: HIGH — Verification: read + rg
wiring. UNVERIFIED: whether a v0.1.3 release body has actually been published
with this text (no network/GH access; the defect is in the tree regardless).
