## 1. One-paragraph verdict
This is the golden-file drift gate: regenerate the three artifacts in memory through the same `codegen` API the bin calls and compare against the committed files. It does exactly that, with a good first-difference reporter and actionable error messages — I ran it green, and it matches the CI gate (`cargo run -p xtask --locked -- codegen --check`, ci.yml:280). Two claims overstate the guarantee. First, the comparison is NOT "byte-for-byte" as the doc says twice: it is line-based (`str::lines()`), and I empirically proved the primitive blind spot — a committed artifact differing from regeneration by exactly the final trailing newline yields identical line vectors, so the test passes where the bin's byte-exact `check_against` (codegen.rs:170 `&committed != expected`) fails. Second, `regeneration_is_deterministic` proves only same-process stability; the precondition the doc states ("makes the byte-for-byte comparison meaningful") is actually cross-process stability, which this test cannot show — that half is supplied by the CI `--check` gate (and my own cross-process run). The known circularity (golden files generated by the code under test; a semantic emitter regression that is regenerated and committed stays green) is filed against the emitter as codegen.rs F-002 and is not double-counted here.

## 3. Findings
F-001 [S4]
Where: crates/commands/tests/catalog_drift.rs:6-7 and 57 (claims) vs 27-39 (implementation)
Code:
```
//! `commands::catalog::codegen` API the `catalog-gen` bin calls (so the
//! bin, the tests and `cargo xtask codegen` can never disagree about
//! what "regenerated" means) and compared byte-for-byte. A mismatch
```
and lines 28-29:
```
    let committed_lines: Vec<&str> = committed.lines().collect();
    let regenerated_lines: Vec<&str> = regenerated.lines().collect();
```
What is wrong: the doc says "compared byte-for-byte" (line 7) and "byte-identical" (line 57), but the comparison is over `str::lines()`, which makes the final line ending optional — I ran the primitive: `"abc\n".lines()` and `"abc".lines()` both yield `["abc"]` (equal: true). A committed artifact that differs from regeneration by exactly one trailing newline therefore passes this test while failing the bin's true byte compare (`check_against`, codegen.rs:168-176, uses `!=` on the whole strings). Why it matters: the repo has TWO drift gates with different sensitivity; the test lane's is the weaker one and claims the stronger guarantee. Nobody regenerates an artifact without its final newline today (all three committed files end with newline — verified by the passing `--check`), so blast radius is an edge case. What correct looks like: `if committed != *regenerated { find first_line_diff for the message }` — compare bytes, use the line scan only for diagnostics. Confidence: HIGH — Verification: ran (primitive proven with a scratch program; full-file mutation NOT executed — repo is read-only; reasoned from the proven primitive).
F-002 [S4]
Where: crates/commands/tests/catalog_drift.rs:89-91
Code:
```
/// Regeneration is deterministic: two independent runs agree byte for
/// byte (the precondition that makes the byte-for-byte comparison above
/// meaningful at all).
```
What is wrong: the two runs are in the SAME process; the golden comparison's actual precondition is cross-process/cross-machine stability (the committed file was produced by some earlier build; CI compares on every runner). Same-process agreement cannot falsify a process-seeded nondeterminism (PID- or address-derived ordering). In practice schemars emits BTreeMaps so this is theoretical, and the real cross-process anchor exists (CI `--check` gate; my own `catalog-gen --check` run) — but the doc credits this test with a guarantee it does not establish. What correct looks like: state the scope honestly, or have CI's `--check` step be the referenced precondition (it already exists). Confidence: HIGH — Verification: read + ran (both the test and the real cross-process check pass).
