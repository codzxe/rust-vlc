## 1. One-paragraph verdict
A strong acceptance suite, and I ran all of it: the test-side AVI/MP4 walkers are
pinned against the writer's per-frame sha256s, both parents are proven to carry
byte-identical frame essence, all 60 frames decode through the real codec-api

reference digests — plus a concealment lane (entropy truncation → mid-gray tail,

that cross-check is a recorded past run, not something the suite or I can
re-execute (no pixel-dump entry point exists; cargo-build-budget blocks writing

## 3. Findings
F-001 [S3]
Where: crates/codecs/tests/data/mjpeg_decode_reference.txt:13-28 (consumed at
fixtures_parent.rs:246-251 via `reference_digests()`)
Code:
# PROVENANCE (honesty rules, doc 03 sec.7 / AGENTS.md sec.3.4): the digests are
# Lumen's own decoder output, cross-checked against the ffmpeg 7.1.5 oracle
# (external, never a dependency) over all 60 frames:
#   - luma plane: BYTE-EXACT vs ffmpeg under both its default IDCT (-idct auto,
#     simple) and the reference integer IDCT (-idct int): 0 of 4,608,000 samples
#     differ.
...
#   The choice recorded in worklog 2.B4: the reference is OUR output because the
#   in-house IDCT is the exact algebraic inverse of the 2.A3 in-repo encoder's
#   fixed-point FDCT (same Q16 basis, same round-half-away-from-zero), which is
#   the stronger truth than matching ffmpeg's own approximation.
What is wrong: the acceptance suite's ground truth is generated by the code
under test. If the decoder were wrong in a way that also corrupted the
regeneration run, every test here still passes — the classic self-golden
circularity. The ffmpeg cross-check (luma 0/4,608,000 differ, chroma ±1 counts)
is documented in exhaustive detail, which is the correct mitigation, but it is a
RECORDED past run: nothing in the repo re-executes it (rg over tests/ finds no
pixel-dump path), and I could not either (no prebuilt binary emits decoded
pixels; building one exceeds the cargo budget). Why it matters: the strongest
sentence in this suite — "0 of 4,608,000 samples differ" — is unverifiable
today. What correct looks like: a `--dump-yuv` host verb or a test that shells
out to ffmpeg when present (the h264_sw_differential pattern, which DOES
re-verify live).
Confidence: HIGH (that it is a self-golden; the cross-check numbers themselves:
UNVERIFIED — reason: no pixel-dump entry point / cargo-build-budget).

F-002 [S4]
Where: crates/codecs/tests/fixtures_parent.rs:276-280
Code:
        assert_eq!(
            video.pts,
            Stamp::Present(Timestamp::new(index as i64 * 1_000_000 / 30, base)),
            "{container} frame {index}: pts passthrough"
        );
What is wrong: this recomputes the identical expression used to BUILD the
packet (frame_stamp, L80), so the assertion is an echo of the input arithmetic,
not an independent expectation; and `index * 1_000_000 / 30` truncates (frame 1
= 33333 µs, true value 33333.33 µs) — harmless here since both sides truncate
identically, but the "30 fps" comment silently means "truncated-µs 30 fps".
Confidence: HIGH — Verification: read.
