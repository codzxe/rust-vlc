## 1. One-paragraph verdict
This is the shared harness behind the DNxHD differential suite, and it is the real thing: lanes are regenerated by the current ffmpeg's own `dnxhd` encoder, pinned against the committed per-lane reference MD5s (which I confirmed match `tools/vta/dnx/evidence/lane-md5s.txt` verbatim), decoded through the wired `DnxDecoder`, and compared per-plane against ffmpeg's own decode at the Lead-ratified tolerance. I executed the consumer suite directly: 6/6 pass, and the printed L1-frame-0 histogram (−1:24848, +1:29408, |Δ|≥2:2 after summing Y/Cb/Cr) reproduces the admission record's documented numbers exactly — the comparator is provably the record's comparator. The one genuine defect: `unpack_i420` (365-381) is dead code with zero consumers repo-wide, hidden by the file-opening `#![allow(dead_code)]`; plus a swallowed `create_dir_all` error. No committed dnxhd fixtures exist — the doc says so honestly ("the corpus holds ZERO dnxhd lanes") and generation is the method.

## 3. Findings
F-001 [S3]
Where: dnx/mod.rs:1 and 364-381
Code:
```

```
and
```
/// Unpack our packed I420 output into planar Y/Cb/Cr.

```
What is wrong: `unpack_i420` has zero callers anywhere in the repo (rg over the whole tree excluding target: only its own definition matches). It is dead test infrastructure, and the module-opening `#![allow(dead_code)]` is precisely what keeps rustc from reporting it — a lint-suppression hiding dead code (spec 6.5). With exactly one consumer module (dnx_differential.rs), the "shared surface, consumers pick" justification for the allow is thin. What correct looks like: delete `unpack_i420` and scope the allow away, or keep the helper with a `#[allow(dead_code)]` on it alone plus a reason. Confidence: HIGH — Verification: rg (`rg -c "unpack_i420" --glob '!target' .` → only mod.rs:1 hit).
Why it matters: dead comparators rot silently; a future agent could "fix" I420 unpacking that nothing exercises.

## 5. Test honesty
No tests in this file (support module). The consumer suite's tests are strong and EXECUTED here: lane-integrity MD5 pins vs committed evidence, byte-count parity, per-plane maxΔ≤2, sign-balance ratio, |Δ|≥2 < 1% of differing, and a truncated-frame typed-refusal test. Mutation reasoning: a broken `compare_plane` that always reported maxΔ=0 would make the tolerance asserts vacuous BUT the lane-MD5 and byte-count pins plus the sign-balance/differing percentages (nonzero, stable across my run and the record) would still constrain the decoder; a broken `unpack_yuyv` would inflate maxΔ and fail the ≤2 ceiling. The record-histogram reproduction (§2) is independent confirmation the comparator computes what it claims.
