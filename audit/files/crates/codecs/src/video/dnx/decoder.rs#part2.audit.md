The second half of the DNxHD wrapper is the trait surface and the output pool: a stateless configure/decode/flush triad that emits exactly one packed frame per packet, a bounded 4-slot `SharedBytes` pool with exact-size reuse, and an 11-test in-file suite plus a 6-lane ffmpeg differential that exercises this exact `Decoder::decode` path with real bytes (dnx_differential.rs:254 `decoder.decode(packet, &mut sink)` — all green in baseline runs #3/#4). The one real defect is a test that does not test what its name promises (F-001); the rest is consistency debt. As with part1: none of this is reachable from a shipped build because nothing mints a `dnxhd` track.

## 3. Findings

### F-001 [S3]
Where: crates/codecs/src/video/dnx/decoder.rs:1037-1066 (test `pooled_slots_reuse_exact_sizes_without_stale_bytes`)
Code:
```
        // A same-size reuse takes the rotation, not a new allocation
        // (observable as a differing fill on the recycled slot).
        let small2 = synthetic_422(8, 2);
        let c = packed_slot(&mut slots, &mut next, &small2, len_small);
        assert_eq!(c.len(), len_small);
```
What is wrong: the test's name and comment promise "no stale bytes on reuse", but the only assertions on the reused slot are `c.len()`. `small2` is generated by the same `synthetic_422(8, 2)` as `small` — identical content — so the claimed "differing fill on the recycled slot" is impossible by construction, and a partial-write regression on the reuse path (e.g., a future fast path that memcpys only the luma plane into a recycled slot) would leave stale chroma bytes that this test cannot see: `c` is never compared to `a`, to `small`'s expected repack, or to anything else.
Why it matters: the pool-reuse path is the steady-state hot path of this decoder; its only dedicated test is a tautology for the property it names. The property is currently true only because `pack_into` happens to be total (verified by reading it), not because anything pins it.
What correct looks like: make `small2` carry DIFFERENT per-sample values (e.g., `synthetic_422` with an offset) and assert the reused slot's bytes equal the hand-computed repack of `small2` — that both proves reuse happened and pins full overwrite.
Confidence: HIGH — Verification: read (test body + `synthetic_422` at 669-687 compared).

### F-003 [S4]
Where: crates/codecs/src/video/dnx/decoder.rs:646 (this chunk) vs crates/codecs/src/video/hevc/decode.rs:448 and crates/codecs/src/video/h264/decode.rs:470,783
Code:
```
            interlaced: picture.interlaced,
            generation: packet.generation,
```
What is wrong: the frame `generation` source is inconsistent across the twin decoders: dnx (and 10 other decoders: aac/mp3/mp2/opus/adpcm/mjpeg/pcm/alac/flac, census via `rg "generation: packet.generation"`) stamp `packet.generation`, while the h264/hevc hw twins stamp `self.generation.unwrap_or(GenerationId::FIRST)`. Post-`drop_stale_packet` the two are always equal today, so no behavioral bug — but the divergence is drift bait the first time someone weakens the stale guard.
Why it matters: two sources of truth for the same field; a future change to guard semantics (e.g., accepting future generations for pre-roll) would silently split behavior between decoders.
What correct looks like: one convention (packet.generation after the guard is the more honest: it is what the sink actually decoded) applied everywhere; the hw twins' `unwrap_or(FIRST)` fallback masks a would-be invariant violation instead of failing.
Confidence: HIGH — Verification: read + census command above.
