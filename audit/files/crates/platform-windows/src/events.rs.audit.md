## 1. One-paragraph verdict
The one file in the platform set whose logic is genuinely executed and honestly tested: a bounded Mutex+VecDeque queue with a clamped minimum capacity, oldest-first drop under pressure, monotonic dropped/pushed counters, poison-tolerant push/drain, and four host tests that assert exact FIFO contents, exact drop counts, the clamp, and concurrent-push safety — all of which would fail if the queue were broken (baseline 16/16, cargo-test-workspace.txt:4054-4073). The code is correct; every `PlatformEvent` variant is constructed by the real WASAPI callback translator (wasapi.rs:481-551). The defects are architectural and documentary: the file is a byte-identical triplicate (platform-linux/macos differ only in the card number on line 2), the header doc talks about "the PulseAudio event loop here" — copied from the Linux crate and false in the Windows (and macOS) copies — and the production path that feeds it belongs to a crate nothing in the product depends on.

## 2. What actually works (verified)
- Baseline test execution: `event_queue_drains_fifo_and_empties`, `event_queue_is_bounded_and_counts_drops`, `event_queue_capacity_is_clamped_to_one`, `event_queue_is_thread_safe_for_callback_threads` all pass (cargo-test-workspace.txt:4056-4060). Test bodies read and judged honest (see §5).
- Variant-vocabulary completeness: all 5 PlatformEvent variants constructed in production code — wasapi.rs:481 (StateChanged), 500 (Added), 516 (Removed), 534 (DefaultChanged), 551 (SetChanged fallback) — verified by rg.
- Copy-paste proof: `diff` of this file vs platform-linux/src/events.rs shows exactly one differing line (line 2, card 7.A1 vs 7.A2); vs platform-macos/src/events.rs same (7.A1 vs 7.A3).

## 3. Findings
F-001 [S3]
Where: whole file; evidence: rg over all Cargo.tomls (no dependents on platform-windows)
Code:
```
pub struct DeviceEventQueue {
    inner: Mutex<VecDeque<PlatformEvent>>,
    capacity: usize,
    dropped: AtomicU64,
    pushed: AtomicU64,
}
```
What is wrong: the queue's only production writer is the WASAPI notification client (wasapi.rs:686, `register_notification_client(Arc::clone(&queue))`) and its only readers are the crate's own tests — no shipped entry point constructs a `DeviceEventQueue`. The mechanism works, but nothing in lumen-cli/desktop can ever drain an event from it.
Why it matters: device hotplug events generated by the real integration would be pushed into a queue nobody polls; the plumbing is built to be wired and never wired.
Confidence: HIGH — Verification: ran rg (exit 1, no dependents).
F-002 [S4]
Where: crates/platform-windows/src/events.rs:4-5 (and 13-14)
Code:
```
//! OS notification callbacks arrive on foreign threads (the OS
//! callback thread on Windows, the PulseAudio event loop here), so
```
What is wrong: "here" is platform-windows — there is no PulseAudio event loop in this crate; the Windows callbacks come from the WASAPI MMDevice notification thread. The sentence is a verbatim copy from platform-linux/src/events.rs (verified byte-identical apart from line 2) where "here" = PulseAudio is true. Line 13-14's "it knows nothing about PulseAudio or DRM" repeats the Linux-specific vocabulary. The same false sentence ships in platform-macos/src/events.rs (its callbacks are CoreAudio listeners).
Why it matters: the module doc misstates which OS integration feeds the queue on this platform — doc-rot from blind triplication.
Confidence: HIGH — Verification: read + diff.

[PROPOSAL] can collapse the two"). Any queue bug or semantic change must be applied four times.

F-004 [S4]
Where: crates/platform-windows/src/events.rs:123-128
Code:
```
    pub fn len(&self) -> usize {
        if let Ok(queue) = self.inner.lock() {
            return queue.len();
        }
        0
    }
```
What is wrong: on a poisoned mutex `len()` reports 0 and `drain()` reports empty even though the queue may hold events — a consistent "poison = empty" policy, but nowhere documented; a consumer polling `len()` after a panicking drainer sees "no events" rather than an error. Cosmetic given the policy is at least self-consistent.
Confidence: HIGH — Verification: read.
