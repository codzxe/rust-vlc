## 1. One-paragraph verdict
This is a working, deterministic, std-only WebAssembly binary emitter that synthesizes the two committed example extensions (`ext.example.metadata`, `ext.example.panel`) and maintains them via `--check` drift detection. The hard proof it works is in the baseline: the regenerated bytes are byte-identical to the committed blobs (`committed_example_modules_match_regeneration ... ok`, :4572), and the emitted modules then load and run end-to-end in the wasmi host — api handshake, honest manifest report, jailed `fs_open`/`fs_read` of a real sidecar, tag bytes read back out of guest memory (:4573-4574). So the wave question "does the wasmi host actually execute a plugin end to end?" answers YES — in this dev/test lane only; no shipped binary (`lumen`, `lumen-tauri`) depends on plugin-host-wasm at all. Defects are minor: the `extract` example drops `fs_close`'s status while its own doc table claims "returns the last import status", and the emitter is a self-acknowledged near-duplicate of the tests/common fixture emitter with no cross-check binding the two.

## 3. Findings
### F-001 [S4]
Where: crates/plugin-host-wasm/src/bin/lumenext-examples.rs:370 and 410-412 vs 435-438
Code:
```
    // extract: open the sidecar (jailed), read it into the result
    // buffer, close. The status of the failing import (if any) is the
    // return value. locals: 0 = path_ptr, 1 = path_len, 2 = status.
```
(and, at 435-438:)
```
            &i32c(HANDLE_AT),
            &i32load(),
            &call(fs_close),
            &dropv(),
```
What is wrong: The doc table (line 370) says `extract` "returns the last import status", and the body comment says "the status of the failing import (if any) is the return value" — but `fs_close`'s status is explicitly `dropv()`-ed; the return value is `fs_read`'s status only. If `fs_close` fails after a successful read, `extract` still returns 0.
Why it matters: This is the canonical example every extension author copies; it demonstrates dropping an import status while its own documentation claims full propagation. (The host-side consequence is benign — the sidecar bytes are already valid — so the doc wording, not the behavior, is the defect.)
What correct looks like: Either keep and return the close status (chain `read_st` and `close_st`), or fix both comments to "returns the `fs_read` status; the close status is advisory and discarded".
Confidence: HIGH — Verification: read (stack trace of the emitted body; dropv at 438).
### F-002 [S4]
Where: crates/plugin-host-wasm/src/bin/lumenext-examples.rs:41-44
Code:
```
// ---------------------------------------------------------------------------
// The wasm binary emitter (public-spec format, std-only — the trimmed
// twin of the fixture emitter in tests/common/mod.rs)
```
What is wrong: Two hand-rolled wasm emitters live in the crate: this one and `tests/common/mod.rs` (`fn uleb` :95, `pub struct Wasm` :142, `fn finish` :238). The header documents the duplication but nothing binds them: a fix to one emitter (e.g. an encoding bug) never propagates to the other, and only THIS emitter's output is pinned by `committed_example_modules_match_regeneration`.
Why it matters: Divergent emitters mean the fixtures used by hello-world/install-lifecycle tests and the committed example blobs are validated by different code that can drift apart silently. The memory-layout constants ARE cross-enforced (conformance test :140-142 comment), but the emitter internals are not.
What correct looks like: Extract the builder into a shared `pub(crate)` module used by both the bin and tests/common, keeping one emitter under test.
Confidence: HIGH — Verification: read (both emitters located; no shared module between src/bin and tests/common).
