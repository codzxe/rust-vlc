## 1. One-paragraph verdict
A textbook-correct, std-only SHA-256: FIPS 180-4 constants and rounds are right (and mathematically proven by the green NIST-vector test — any wrong constant or rotation breaks every digest), the streaming buffer logic handles every boundary I traced (56-byte padding edge, 63/64-byte buffer edges, chunk splits at 1/3/63/64/65/199), padding correctly excludes itself from the length field, and `finish(self)` consumes the hasher to prevent silent reuse. Both tests are green in the baseline run. The only defects are structural: this is the THIRD independent hand-rolled SHA-256 in the repo (audio-output test helper, xtask web_budget, now the production one), and the hex encoder does 32 per-byte `format!` allocations. Nothing shipped executes any of it — the crate has no dependents.

## 2. What actually works (verified)
— `sha256::tests::nist_vectors` and `update_split_invariance` green in baseline `orchrun-test-workspace-nofailfast.log.txt:4517-4518` — FIPS vectors for empty input, "abc", the 56-byte vector (the exact padding boundary that forces the two-block case), and 1,000,000×'a' (multi-block + length-field), plus chunk-invariance at sizes 1/3/63/64/65/199 over 10k bytes.
— Constants: all 64 K values and 8 H0 values compared against the FIPS 180-4 tables — identical (and the passing vectors make any error there impossible anyway).
— Edge traces: message 55 B → single padded block; 56 B → 0x80 forces zeros to 64, compress, 56 zeros, length — two blocks; 63 B → 0x80 fills the buffer, compress, 56 zeros, length; multi-`update` with buffer pre-fill (buf_len=10 × data 5/54/100 B) — all correct.
— `bit_len` computed from `total_len` BEFORE padding, and `update_pad` deliberately bypasses length bookkeeping (97-98) — the classic padding double-count bug is absent.
— Consumer chain real: `module_digest` (package.rs:338-340) formats the `sha256:<hex>` provenance form; install.rs:386/503 compares computed vs declared digest (tamper refusal, PackageError::HashMismatch/InstalledHashMismatch — both variants really constructed, error.rs census).
— Header precedent claim verified TRUE: audio-output/tests/common/mod.rs:76 (`pub fn sha256_hex`) and tools/xtask/src/cmd/web_budget.rs:44 ("sha256 IS implemented here").

## 3. Findings
### F-001 [S4]
Where: crates/plugin-host-wasm/src/sha256.rs:1-7 (and the two sibling copies)
Code:
```
//! std-only SHA-256 (FIPS 180-4 public math).
//!
//! Same precedent as `audio-output`'s test helper and `tools/xtask`:
```
What is wrong: This is the third independent SHA-256 implementation in the repository: `crates/plugin-host-wasm/src/sha256.rs` (this one), `crates/audio-output/tests/common/mod.rs:76` (`sha256_hex`), and `tools/xtask/src/cmd/web_budget.rs` (own implementation per its line-44 comment). The header presents the duplication as precedent rather than debt.
Why it matters: Three copies of cryptographic math must be verified three times; a future fix (e.g. a performance or a length-overflow correction) applied to one copy silently misses the others. The dependency-discipline motive (C5 grant, "no new dependency") is legitimate — but a single shared `crates/hash-mini` (or one canonical location re-exported by the other two) would keep zero external deps AND one verification surface. Blast radius today: low — all three pass their own vectors/goldens.
What correct looks like: One canonical std-only implementation in a tiny workspace crate (or at least a cross-reference comment in all three files naming the other two, plus a shared vector test).
Confidence: HIGH — Verification: read (three copies located and confirmed by grep).
### F-002 [S4]
Where: crates/plugin-host-wasm/src/sha256.rs:170-174 (and 84-86)
Code:
```
    let mut out = String::with_capacity(64);
    for b in digest {
        out.push_str(&format!("{b:02x}"));
    }
```
What is wrong: Per-byte `format!` — 32 transient heap allocations per digest; and `finish` pads byte-at-a-time through `update_pad(&[0])` in a `while` loop (84-86), one function call per zero byte (up to 63 calls).
Why it matters: Purely cosmetic today — digesting is once-per-package (cap 64 MiB), where compression dominates by orders of magnitude. But it is the pattern the repo's own perf rules discourage, and the hex half has a zero-cost fix.
What correct looks like: `use std::fmt::Write`; `write!(out, "{b:02x}")` (no allocation), or a 512-byte hex lookup table; for padding, a direct slice fill (`self.buf[self.buf_len..].fill(0)` loop by 64-byte blocks).
Confidence: HIGH — Verification: read.
