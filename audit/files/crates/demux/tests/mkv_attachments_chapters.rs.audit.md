## 1. One-paragraph verdict

This is one of the repo's better test files: the generated lane builds a real MKV with ffmpeg (chapters via ffmetadata, a JPEG cover and text note via `-attach`), compares the demuxer's chapters/attachments against live ffprobe, and then pins byte-exact `FileData`, exact nanosecond chapter times, titles, MIME types and damage counters — an independent-oracle differential (writer ≠ parser) that fails loudly if the chapters/attachments parse regresses. The corpus lane has the same design but is dead weight everywhere that matters: it requires `/tmp/my-project/corpus-v4` (absent on this machine, never provided by any workflow or script), and its "skip" is an `eprintln` + `return` that still counts as a pass in the suite totals. One "sanity bound" block asserts nothing.

## 2. What actually works (verified)

- The generated lane's assertions are real and specific (lines 396-434): attachment count, byte-exact `FileData::Inline` against the generated files on disk, MIME strings, chapter count, exact `start_ns`/`end_ns` (0/1.5e9, 1.5e9/4e9), titles, `beyond_duration == 0`, `damage.is_empty()`. Breaking the chapters or attachments parser fails this test.
- The oracle is independent: ffprobe (lines 52-78, 89-125) parses the same file; the fixture is produced by ffmpeg. No golden file generated by the code under test (no circularity).
- Fail-loud environment handling where it counts: `Command::output().must()` panics if ffprobe cannot spawn while the corpus is present; `assert!(status.success(), "ffmpeg fixture generation failed")` (line 306) fails if ffmpeg (e.g., without libx264) cannot build the fixture.
- The packet-walk sanity (216-223) proves the metadata getters don't break the demux walk (packets still flow) — a real invariant, cheaply checked.
- `open_via_input` goes through the production `input::FileAccess` (common/mod.rs:546-550) — the composition at the `plugin-api` seam is exercised, not a mock stream.

### T-002 [S3] The "present-timestamp sanity bound" asserts nothing
Where: crates/demux/tests/mkv_attachments_chapters.rs:225-231
Code:
```rust
    // A present-timestamp sanity bound: chapters land inside the
    // stream's own timing vocabulary.
    if let Some(start_ns) = first_start_ns {
        let _ = Stamp::Present(media_types::time::Timestamp::new(
            (start_ns / scale) as i64,
            demuxer.segment_info().time_base().must(),
        ));
    }
```
What is wrong: The block constructs a `Timestamp`, binds it to `_`, and discards it. There is no assertion on the value — no bound check, no range comparison, nothing. The comment claims a "sanity bound"; the code checks only that `Timestamp::new` does not panic (which, for a valid base and any i64, it does not — and `time_base().must()` would have failed earlier in `start()` anyway). It would not fail under any chapter-timestamp regression.
Why it matters: Per the audit's test-honesty bar, this is assertion-free test code wearing a check's name — it inflates the apparent coverage of the ns→ticks chapter conversion (the conversion the mod.rs audit flagged in F-002's family).
What correct looks like: Assert the constructed timestamp's nanos round-trip, or assert `start_ns` is within the segment duration when one is declared — or delete the block.
Confidence: HIGH — Verification: read.

### T-003 [S4] Generated fixture is cached forever once built — "rebuilt at run time" (header, line 20-21) is only true on first run
Where: crates/demux/tests/mkv_attachments_chapters.rs:308-322 (cover cache), 333-376 (mkv cache)
Code:
```rust
    let out = dir.join("d2a-generated.mkv");
    if !out.exists() {
```
What is wrong: The MKV and its cover JPEG are built under `std::env::temp_dir()/lumen-d2a-fixtures` only when absent. Every later run — across ffmpeg upgrades, chapter-spec edits, and code changes — reuses the stale artifact. The header says "the generated fixture is rebuilt at run time" (lines 20-21); it is built once and cached indefinitely. The differential itself stays internally valid (ffprobe and the demuxer read the same cached file, and the byte-exact checks read the same cached cover), so this is hygiene, not correctness — but a partial/corrupt leftover from an interrupted run would poison every subsequent run with no rebuild path short of manual `rm`.
Why it matters: Misleading doc line plus a silent cache with no invalidation; parallel `cargo test` invocations can also race the generation.
What correct looks like: Cache keyed on content (e.g., embed the ffmeta/args hash in the filename) or rebuild unconditionally — the fixture costs one 4-second lavfi encode.
Confidence: HIGH — Verification: read.

### T-004 [S4] Hand-rolled ffprobe JSON scraping, duplicated between the two readers
Where: crates/demux/tests/mkv_attachments_chapters.rs:60-70 and 105-114
Code:
```rust
        let field = |name: &str| -> Option<String> {
            let pat = format!("\"{name}\":");
            let at = chunk.find(&pat)? + pat.len();
            let rest = chunk[at..].trim_start();
```
What is wrong: Both `ffprobe_chapters` and `ffprobe_attachments` carry a copy-pasted `field` closure that scrapes JSON by substring search over chunks split on `"id":` / `"index":`. A chapter title or attachment filename containing those sentinel substrings missegments the rows; an ffprobe output reshuffle silently turns fields into `None` (which then fails the differential loudly — the failure mode saves it from being dishonest). The closure is duplicated verbatim.
Why it matters: Fragile oracle plumbing that will break confusingly on ffprobe updates; duplication invites the two copies diverging.
What correct looks like: One shared `field` helper (or serde_json, which the workspace already admits elsewhere) + a shared row splitter.
Confidence: HIGH — Verification: read.

### T-005 [S4] Chapter ns values narrowed with `as i64` and a `-1` sentinel
Where: crates/demux/tests/mkv_attachments_chapters.rs:150-151, 72-73
Code:
```rust
        let start_ns = atom.start_ns as i64;
        let end_ns = atom.end_ns.map_or(-1, |t| t as i64);
```
What is wrong: `atom.start_ns` is u64; the cast wraps values above i64::MAX, and the `-1` sentinel doubles as ffprobe's parse-failure marker (`unwrap_or(-1)` at 72-73), so a hostile wrapped value and an unparsable probe field become indistinguishable. In practice the corpus is valid media, and any mismatch fails loudly — recorded because the same narrowing pattern is a real defect at the demuxer seam (mod.rs F-002 / cluster.rs C-002 family).
Confidence: HIGH — Verification: read.
