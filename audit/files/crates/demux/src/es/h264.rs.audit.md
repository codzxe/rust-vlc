## 1. One-paragraph verdict
A 29-line delegation shim over the shared Annex-B engine (`super::annexb`), and the answer to this audit's hostile question is clean: es/h264.rs is NOT reachable from the MP4 path — MP4 H.264 is avcC (length-prefixed config record) and is extracted as such in containers/mp4.rs:237; the Annex-B engine is only ever constructed for the raw-ES probe ids ("h264"/"hevc"), and even that construction goes straight to `AnnexbVideoDemuxer::new` in containers/es.rs:186 without passing through this file. So the module's `open()` is exercised only by the in-crate fuzz harness and the codecs differential suite (which I ran: 17 tests pass, including parallel `*_annexb` and `*_mp4` lanes over identical content — direct evidence the two framings coexist without cross-contamination). The defects are dead-surface hygiene: `EXTENSIONS` has zero consumers (media-probe hand-mirrors its own table, "no crate edge"), the `probe()` has zero shipped consumers (media-probe's signature/es.rs has its OWN hand-rolled NAL sniffer at lines 220-237 — a parallel implementation that can silently drift), and the `.avc` extension entry promises Annex-B semantics for a name that in the wild denotes length-prefixed raw AVC.

F-003 [S4]
Where: crates/demux/src/es/h264.rs:14-17 (with crates/media-probe/src/signature/es.rs:220-237)
Code:
```
pub fn probe(header: &[u8]) -> bool {
    super::annexb::probe(AnnexbCodec::H264, header)
}
```
What is wrong: The shipped prober never calls it — media-probe's signature/es.rs carries its own hand-rolled NAL-type sniffer (`let h264_type = b & 0x1F; if !matches!(h264_type, 1..=15)`), a parallel implementation of the same discrimination. Two Annex-B sniffers can drift (probe says h264, demuxer scan refuses) — the exact probe-vs-demux race class the AVI suite documents. Today the demux-side open path does not consult this probe either (AnnexbVideoDemuxer does its own scan), so the race is bounded; the duplication is the debt. Confidence: HIGH — Verification: read + grep.
