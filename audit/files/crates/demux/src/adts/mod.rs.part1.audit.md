## 3. Findings

### F-001 [S2] ADIF: unconditional 4-bit `num_pce` read + self-built fixture evidence — conformance UNVERIFIED
Where: crates/demux/src/adts/mod.rs:574-578 (and fixtures test_support.rs:144, tests.rs:459)
Code:
```
        let bitrate = bits.read_bits(23)? as u32;
        let num_pce = bits.read_bits(4)? as u8;
        if !bitstream_type && num_pce > 0 {
            return Err(error::adif_multi_program());
        }
```
What is wrong: The parser reads a 4-bit `num_program_config_elements` for **both** CBR and
VBR bitstreams. In ISO/IEC 13818-7 the ADIF header transmits this count only for
variable-rate bitstreams; a constant-rate (CBR) stream carries exactly one
program_config_element with no count field (faad2-style decoders read the 4 bits
unconditionally, so both conventions circulate — the spec text itself was NOT available in
this sandbox, so this dimension is UNVERIFIED, and I state my memory explicitly rather than
assert it). What is *verified*: every ADIF test fixture is generated by this repo's own
builders, and both builders write that 4-bit field into CBR streams —
`crates/demux/src/adts/test_support.rs:144` (`push(&mut bits, 0, 4); //
num_program_config_elements = 0`, emitted after `bitstream_type = 0`) and
`crates/demux/src/adts/tests.rs:458` (`bits.push(u64::from(num_pce), 4);` unconditional).
So the passing tests (`adif_cbr_walk_matches_the_block_arithmetic` etc., nofailfast
log:1495–1500) prove the parser parses the parser's own format, nothing more.
Why it matters: if the count field is not transmitted for CBR, every real-world CBR ADIF
file (the only flavor this demuxer accepts) is misparsed: the PCE decode starts 4 bits
early, so profile/sampling_index/channel counts shift — either a typed
`adif_bad_params` refusal of a valid file or, worse, a silently wrong rate/channels track.
No test could catch it because the oracle is the SUT.
What correct looks like: either (a) cite the exact ISO syntax clause in a comment and pin
the field's presence per that text, or (b) obtain one real ADIF file (e.g. from an
independent encoder) and pin the open path against it; at minimum the doc must stop
presenting "cross-format agreement" as ADIF evidence — it is self-agreement.
Confidence: HIGH on the code/fixture facts; MEDIUM/UNVERIFIED on the spec reading
(blocked: no ISO text, no faad2/symphonia ADIF source in the sandbox —
symphonia-codec-aac-0.6.1 has no ADIF parser, checked by rg).

### F-002 [S3] `stream_info()` reports channel_configuration 7 as 7 channels — contradicts the repo's own decoder
Where: crates/demux/src/adts/mod.rs:408-416
Code:
```
    pub fn stream_info(&self) -> Option<AdtsStreamInfo> {
        Some(match self.head.as_ref()? {
            RawAacFormat::Adts(h) => AdtsStreamInfo {
                format: "adts",
                rate: h.sample_rate()?,
                channels: u16::from(h.channel_config),
```
What is wrong: channel_configuration 7 means **8** channels (7.1) per ISO 14496-3 Table
1.17 — the repo's own decoder says so: `crates/codecs/src/audio/aac/adts.rs:65-75`
(`/// … 7 means 8 channels` / `match config { 0 => 0, 1..=6 => config, _ => 8 }`). The
demuxer's public stream info maps the raw field value, so a 7.1 stream reports 7 channels.
Why it matters: the demux and decode layers disagree about one header; any future consumer
of `stream_info().channels` (the field is documented as "the fields ffprobe reports") gets
a wrong number. No test covers config 7: the corpus truth table has only mono lanes
(`crates/demux/tests/adts_corpus.rs:80-93`, channels: 1) and the unit test at
tests.rs:105-114 uses config 2.
What correct looks like: reuse the same channel-count resolution the decoder uses (or
export it from one place), and add a config-7 unit row.
Confidence: HIGH — Verification: read both sites; contradiction is verbatim.

### F-003 [S3] `probe()` accepts MP3 frame headers; the "rejects the rest" test omits the known collision
Where: crates/demux/src/adts/mod.rs:147-152 (test: adts/tests.rs:84-90)
Code:
```
pub fn probe(header: &[u8]) -> bool {
    if header.len() >= 4 && &header[0..4] == b"ADIF" {
        return true;
    }
    header.len() >= 2 && header[0] == 0xFF && header[1] & 0xF0 == 0xF0
}
```
What is wrong: `0xFF 0xFB` (MPEG-1 Layer III, the most common MP3 frame header in
existence) satisfies this predicate (`0xFB & 0xF0 == 0xF0`) — the probe answers "ADTS" for
MP3. The layer bits (`header[1] & 0x06`) that distinguish ADTS (`00`) from MP3 Layer III
(`01`) are not checked. The unit test's name promises "rejects the rest" but its four
negatives (`0xFF 0x0F`, "RIFF", `0xFF`) do not include the notorious case.
Why it matters: `probe` is a `pub` API of the demux crate and is re-exported verbatim by
the ES registry surface (`crates/demux/src/es/aac.rs:19-22`) without the layer check — any
caller of that surface inherits the false positive. The shipped CLI lane is protected only
because media-probe's own signature adds the refinement
(`crates/media-probe/src/signature/phase5.rs:134-139`, `prefix[1] & 0xF6 == 0xF0`), i.e.
the shipped selection path re-implements the probe correctly while the crate's public
probe stays wrong.
What correct looks like: `header[1] & 0xF6 == 0xF0` in `adts::probe` itself (exactly the
media-probe refinement), plus an MP3 negative in the test.
Confidence: HIGH — Verification: read; the shipped-path mitigation was traced
(phase5.rs:134-139, containers/mod.rs:52).
Note (S4 tail, folded here): `es/aac.rs` is a 60-line doc-heavy re-export module whose
probe delegates to the unrefined one — duplication with drift risk between the two
"registries" (demux ES surface vs media-probe).

### F-004 [S3] CRC acceptance evidence is a byte-identical copy of the SUT; zero external coverage
Where: crates/demux/src/adts/mod.rs:537-539 (use); oracle: test_support.rs:28-40 vs mod.rs:979-991

```
            if !raw.protection_absent && crc16_header(&full[..7]) != be16(&full[7..9]) {

            }
```
Oracle (test_support.rs:28-33, copy of mod.rs:980-987):
```

    let mut crc: u16 = 0xFFFF;
```
What is wrong: the "good CRC walks" half of `crc_mismatch_is_typed_and_good_crc_walks`

refused `demux.adts.crc-mismatch` if the algorithm is wrong — a valid-file open failure

What correct looks like: one known-good CRC vector from the spec (or an independently
generated protected frame) pinned in the test; delete the duplicated implementation from

Confidence: HIGH on the duplication/no-coverage facts (verified by od on fixtures +

Note: `crc16_header` itself is defined in A10's part2 range (979–991); this finding is

### F-005 [S3] First-claim strictness asymmetry: garbage that *shapes* like a bad header kills the open, identical mid-stream damage recovers
Where: crates/demux/src/adts/mod.rs:522-531
Code:
```
            // The first ADTS claim: strict, typed validation.
            if raw.sampling_index >= SAMPLE_RATES.len() as u8 {
                return Err(error::bad_sampling_index());
            }
            if raw.channel_config == 0 {
                return Err(error::bad_channel_config(at));
            }
```
What is wrong: the open scan advances past bytes that lack a syncword or have nonzero
layer bits (514-521), but the first syncword-shaped, layer-00 claim gets a **hard refusal**
for a bad sampling index / channel config 0 / bad CRC — even when that claim is a random
false positive in pre-stream garbage rather than the stream's real first frame. The same
damage mid-stream is *recovered* by the bounded resync (documented damage policy). The
scan window exists precisely to find a real frame inside garbage, yet a 14-bit false
positive (syncword+layer ≈ 1/16384 per offset, ×3/16 for indices 13–15) anywhere in the
64 KiB window before the real frame aborts the open. ffmpeg's raw-ADTS demuxer resyncs
past it.
Why it matters: realistic dirty files (header garbage, embedded junk before frame 0) open
in ffmpeg and refuse here; the module doc sells the scan as "bounded scan for the first
strict-valid frame" (mod.rs:503) but implements "strict validation of the first *claim*".
What correct looks like: on a strict-validation failure at a scanned candidate, advance
one byte and continue the scan; reserve the typed refusal for when the window is exhausted
(the same acceptance predicate the resync uses).
Confidence: HIGH — Verification: read; the divergence is a policy choice recorded in the
commit message ("strict first frame") but the false-positive case is not covered by any
test (corpus garbage lane is *tail* garbage, per commit 543e9a29). This is a
robustness/parity defect, not fakeness — the code does what its doc says, but the doc's
own analogy ("the acceptance predicate ffmpeg's raw ADTS demuxer was measured using",
mod.rs:53-54) does not hold at open time.

### F-006 [S3] ADIF copyright_id parsed as a null-terminated string, not the fixed 72-bit field
Where: crates/demux/src/adts/mod.rs:560-568
Code:
```
        if copyright_present {
            // Byte-terminated null string (the GPAC parser's
            // convention; bounded so a lying length cannot loop).
            let mut seen = 0u32;
            while bits.read_byte()? != 0 {
                seen += 1;
                if seen > 64 {
                    return Err(error::adif_bad_params());
                }
            }
        }
```
What is wrong: ISO 13818-7's adif_header carries a fixed 72-bit `copyright_id` (nine
bytes); this parser consumes a null-terminated string instead (the comment admits it
follows "the GPAC parser's convention"). A 9-byte copyright id with no interior zero byte
consumes following header bits until some zero byte appears — every subsequent field
(original_copy, home, bitstream_type, bitrate, PCE) is then read from the wrong offset,
producing either a bogus typed refusal or a misparsed CBR walk. The 64-byte bound prevents
the infinite loop but not the misparse. (ffmpeg's ADIF path skips a fixed 72 bits — from
my knowledge of that codebase, UNVERIFIED in this sandbox.)
Why it matters: conformance drift on an already-fragile format lane; the demuxer accepts
GPAC-shaped ADIF and rejects/derails ISO-shaped ADIF.
What correct looks like: read exactly 72 bits when copyright_id_present; if the GPAC
string convention must be tolerated, try fixed-72 first and fall back, and pin both with
external vectors.
Confidence: MEDIUM (code facts HIGH; spec/GPAC/ffmpeg details UNVERIFIED — no sources in
sandbox).

### F-008 [S4] Open scan: one Vec allocation + one seek+read per byte offset
