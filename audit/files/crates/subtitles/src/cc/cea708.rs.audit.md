## 1. One-paragraph verdict
Internally clean staged implementation of the DTVCC half: reassembly is bounded (max 127 B, overrun guard pinned as defensive by its own test), the service-block walk is overflow-safe (`saturating_add` + `min`), every malformed input is typed `CcDamage`, no unsafe/unwrap/panic exists in the file, and the "recorded, not interpreted" honesty claim for native services 2–63 is exactly what the code does (classify + count only; no window state exists anywhere in the crate). The structural weakness: three load-bearing CTA-708 transcriptions — cc_type 2=start/3=continuation, packet length = 2×code+1, escaped service = 8+(escape&0x3F) — are pinned only by hand-crafted vectors derived from the same reading, with no reference decoder or corpus in the sandbox (the author's worklog admits this); I could not verify any of them against the spec, and a polarity error would kill every real 708 stream while the suite stays green. Two smaller defects: command-level truncation inside a block is swallowed by the native walk, and the 708 damage path bypasses the caller's `MAX_DAMAGE_EVENTS` cap that the module docs advertise.

## 2. What actually works (verified)
— `cc::cea708::tests` 6/6 ok in `audit/runs/baseline/orchrun-test-workspace-nofailfast.log.txt:5329-5334` (reassembly lock/complete, typed continuation-without-start, size-code cap 63→127, escape + size-0=32 blocks, truncated/bad headers typed, native walk histogram).
— Bounded allocation verified by read: `expected = code*2+1` with 6-bit `code` ≤ 63 → ≤ 127 ≤ `MAX_DTVCC_PACKET` (128); the buffer only grows to exactly `expected` (odd lengths, 1+2N); the `DtvccOverrun` guard is provably defensive — test `size_code_caps_below_the_packet_guard` pins it.
— Overflow-safe truncation: `let end = pos.saturating_add(len).min(packet.len());` (line 273) — no usize overflow on hostile block sizes.
— Native-walk honesty: `walk_native_block` classifies and counts; no interpretation, matching the module honesty table and docs/formats/sub-cc.md:42-44.

## 3. Findings

### F-001 [S3]
Where: crates/subtitles/src/cc/cea708.rs:5-12, 181-182, 261 (and tests 310-404)
Code:
```rust
//! DTVCC packet layer. A `cc_type == 2` triplet starts a packet —
//! its first byte carries `sequence_number` (2 bits, ignored: the
//! reference decoders tolerate loss by re-locking on any start)
//! and `packet_size_code` (6 bits); the expected packet length is
//! `2 × packet_size_code + 1` bytes
```
```rust
                let code = (data[0] & 0x3F) as usize;
                self.expected = code * 2 + 1;
```
```rust
            service = 8 + (escape & 0x3F);
```
What is wrong: Three spec-mapping constants that determine whether ANY real CEA-708 stream decodes — (a) cc_type 2 = packet START / 3 = continuation (cc_data.rs:27-28 repeats it), (b) packet length = 2×packet_size_code+1 bytes, (c) two-byte service escape mapping service = 8 + (escape & 0x3F) — are pinned only by this module's own hand-crafted vectors, which were built FROM the same reading. There is no reference decoder, no recorded corpus, and no spec copy in the sandbox; the author's worklog (archive-2026-10.md:9956) admits "no CC reference corpus … NO reference-encoder differential — hand-crafted vectors cross-checked against the spec". I could not independently verify (a), (b), or (c) against CTA-708, and my own recollection of the cc_type table conflicts — this audit records UNVERIFIED, not confirmation.
Why it matters: If (a) is inverted, every real 708 packet's start triplet is treated as an orphan continuation (`DtvContinuationWithoutStart` damage per packet) and the DTVCC layer NEVER produces a packet — 708 and the service-1 608-compat route are dead on real input while all 6 unit tests and the acceptance suite stay green (they feed the same polarity the code asserts). Same class for (b)/(c): one wrong constant silently corrupts or kills the walk. The moment the H.264 SEI feed seam (open per sub-cc.md:82-83) is wired, this graduates from latent to S2.
What correct looks like: A spec-transcription proof artifact: the exact CTA-708 §9.3/§9.4 table rows quoted in the record doc with a citation, or one captured real-stream vector (any GA94 SEI dump from ffmpeg -bsf extractextradata/-debug or a broadcast sample) decoded and byte-compared, or a cross-check against ffmpeg's cc handling in-tree.
Confidence: HIGH that the risk exists and the vectors are circular; UNVERIFIED on which side of each mapping the spec falls. — Verification: read + worklog citation; no spec/reference available in sandbox.

### F-002 [S4]
Where: crates/subtitles/src/cc/cea708.rs:294-302
Code:
```rust
    while pos < payload.len() {
        let op = Cc708Op::classify(payload[pos]);
        let len = op.total_len().min(payload.len() - pos);
        if record.ops.len() < MAX_RECORDED_OPS && !record.ops.contains(&op) {
            record.ops.push(op);
        }
        pos += len;
    }
```
What is wrong: A final command truncated by the block boundary is silently clipped (`min(payload.len() - pos)`) AND still recorded in the op histogram — no damage entry distinguishes "DEFINE_WINDOW seen complete" from "DEFINE_WINDOW seen truncated". Only block-level truncation is typed (upstream `DtvccTruncatedBlock`); command-level truncation is invisible.
Why it matters: The module doc sells the record as proof "the stream parses" (line 22-24: "a record proves the stream parses"); a clipped-command stream produces the identical record as a clean one. The histogram also desyncs after `Reserved` (0x93-0x96, walked as 1 byte) if a reserved/EXT1-escaped code carries parameters.
What correct looks like: `if op.total_len() > payload.len() - pos { record/​damage truncated-command }` — the function already takes a mutable record; add a truncated-command counter or take the damage vec.
Confidence: HIGH — Verification: read + hand-trace (e.g. payload ending in a lone 0x98 DEFINE_WINDOW byte).

### F-003 [S4]
Where: crates/subtitles/src/cc/cea708.rs:171-176, 236-239 (vs cc/mod.rs:226-230, 59-61)
Code:
```rust
    pub(crate) fn push(
        &mut self,
        cc_type: u8,
        data: [u8; 2],
        damage: &mut Vec<CcDamage>,
    ) -> Option<Vec<u8>> {
```
What is wrong: Both cea708 entry points push `CcDamage` events directly into the caller's raw `Vec`, bypassing `CcDecoder::note()`'s `MAX_DAMAGE_EVENTS` (256) cap. cc/mod.rs:59-61 advertises "Never … unbounded allocation (the damage ledger … capped)" and mod.rs:197-199 documents `CcUpdate.damage` as "capped at MAX_DAMAGE_EVENTS" — false for every damage variant pushed from this file (`DtvContinuationWithoutStart` once per orphan triplet, one per `DtvccOverrun`/`DtvccBadEscape`/`UnknownService708`/`DtvccTruncatedBlock`).
Why it matters: A public-API caller feeding `CcDecoder::decode` a large triplet slice (the parameter is unbounded `&[CcDataTriplet]`) gets an uncapped, input-proportional damage vec where the 608 path would have stopped at 256. Today's only feed (GA94, cc_count ≤ 31 per payload, drained per call at mod.rs:275) cannot exceed the cap — latent, but the documented invariant is violated by the API's shape.
What correct looks like: Pass the capped `note()` closure/handle into the 708 layer, or enforce the cap inside `push`/`parse_dtvcc_packet`.
Confidence: HIGH — Verification: read of both files; per-call drain confirmed (mod.rs:275 `std::mem::take`).
