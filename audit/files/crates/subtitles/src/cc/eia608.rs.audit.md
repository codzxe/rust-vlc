## 1. One-paragraph verdict
This is real, carefully written decoder code — the PAC row table matches the ccextractor `rowdata` table (verified entry by entry), the mid-row/PAC attribute nibble table matches CEA-608's color/underline/italics map exactly, every index is range-proven (panic-free trace: all six table lookups bounded by their match guards), and the eight unit tests plus the eleven cc_acceptance tests pin the pop-on double buffer, roll-up scroll, PAC pen, backspace/DER, and parity inverses — all green in the baseline run. But the file lives in a crate no shipped binary links, its "FULL" claim has three untested holes (tab offsets, Text mode, roll-up resize), and two `changed`-signal paths return `true` without touching the displayed grid. The honesty tables in cc/mod.rs and docs/formats/sub-cc.md disclose the Text-mode approximation and the [VERIFY] charset slots, so the docs are mostly honest — the word "FULL" and the "pinned by tests" claim for tab are the drift.

## 3. Findings

### F-001 [S3]
Where: crates/subtitles/src/cc/eia608.rs:465-477
Code:
```
            0x25..=0x27 => {
                let rows = lo - 0x23; // 2..=4
                if self.mode == CaptionMode::RollUp(rows) {
                    return false; // re-send: window size only
                }
                if !matches!(self.mode, CaptionMode::RollUp(_)) {
                    self.displayed.clear();
                    self.hidden.clear();
                }
                self.rollup_base = self.cursor_row;
                self.mode = CaptionMode::RollUp(rows);

```
What is wrong: when a channel already in roll-up receives a DIFFERENT window size (RU2→RU3 — a real broadcast pattern), the `matches!` guard skips the clear, only `rollup_base`/`mode` change, and the arm still returns `true` with the comment "the entry clear changed the screen" — no entry clear ran and no cell changed.
Why it matters: `decode_pair`'s bool is the displayed-grid-changed event signal; cc/mod.rs:349-350 turns it into a `CcCaptionEvent` with a full 15×32 grid clone. The resize path emits a spurious ~4 KB event per code. Behavior is not corrupted (grid content correct), so S3 not S2.
What correct looks like: return `false` from the resize sub-path (or track whether the clear actually ran), and fix the stale comment. Add a test — none of the 8 unit or 11 acceptance tests sends 0x26/0x27 after 0x25 (`rg -n "0x26|0x27"` → only the table comments).
Confidence: HIGH — Verification: read (all callers of the return value traced: cc/mod.rs:347-351).

### F-002 [S3]
Where: crates/subtitles/src/cc/eia608.rs:541-545
Code:
```
        } else {
            // Pop/paint/text: home the column.
            self.cursor_col = 0;
            matches!(self.mode, CaptionMode::PaintOn | CaptionMode::Text)
        }
```
What is wrong: (a) In Text mode (T1–T4, entered via 0x14 0x2A/0x2B) a Carriage Return must scroll the text window / advance the row (CEA-608 text-mode semantics); here it only homes the column, so continuous text-mode traffic overwrites row 15 forever. (b) For PaintOn and Text the arm returns `true` — "displayed grid changed" — although only the cursor moved (same spurious-event class as F-001).
Why it matters: T1–T4 services (news crawls, continuous text) render garbage after the first line; the `true` adds spurious events. Mitigations that keep this at S3: the module docs (34-37), cc/mod.rs honesty table (line 46) and docs/formats/sub-cc.md (line 45) all disclose "paint-on approximation (documented)", and no shipped binary reaches this code. There is ZERO test coverage of Text mode (`rg "0x14, 0x2A|0x14, 0x2B"` → nothing) — the approximation's actual behavior is unpinned.
What correct looks like: in Text mode, advance `cursor_row` (scrolling the window at the base row like roll-up) before homing; return `false` when no cell changed; add a Text-mode test that would fail under the current no-scroll behavior.
Confidence: HIGH — Verification: read; spec semantics from CEA-608 text-mode CR behavior (spec text not in sandbox — semantics UNVERIFIED against CTA-608-E document itself, cross-checked against ffmpeg/ccextractor behavior descriptions in the module docs).
