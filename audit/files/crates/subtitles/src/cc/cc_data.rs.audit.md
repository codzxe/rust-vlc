## 1. One-paragraph verdict
The two byte-aligned GA94 grammars are correct ATSC/CTA-708 implementations with honest typed errors and real negative tests I ran and passed. The SCTE-20 grammar is the weak third: its bit layout (7 data bits + 1 "reserved" bit per caption byte, marker nibbles consumed-and-discarded at the end) contradicts the SCTE 20 standard layout (7 data bits followed by a 4-bit '1111' marker per byte), so on a real SCTE-20 stream the second byte of every pair and every subsequent triplet decode as garbage; the only test vector is generated by the code's own writer (the comment admits "approximate"), so nothing in-tree can catch it. The claimed authority ("ffmpeg's mpeg12 SCTE-20 walk") could not be verified and, per my knowledge, does not exist in ffmpeg. Unreachable from any shipped binary regardless.

## 2. What actually works (verified)
— `cargo test -p subtitles --lib cc::cc_data` -> 8/8 pass (exit 0): GA94 roundtrip, 4-way T.35 rejection (country/provider/identifier/type), truncation + marker + zero-bit rejections, process-flag-0 empty-not-error, trailing-byte tolerance, MPEG-2 entry parity with SEI body, SCTE-20 internal roundtrip + typed truncation.
— Byte-aligned `cc_data()` bit math checked against CEA-708: flags byte masks `0x40` (process) / `0x20` (zero_bit, rejected) / `0x1F` (count) at lines 178-183; triplet byte `[5 reserved][1 valid][2 type]` via `t[0] & 0x04` / `& 0x03` at lines 206-207. Bounds math `needed = 1 + n*3 + 1` (line 194) with `body.len() < needed` guard — no slice can go out of range (max end index 3n+1 < needed=3n+2 for n>0; n=0 reads only the marker at index 1).
— `eia608::with_odd_parity`/`parity_ok` (eia608.rs:77-91) are real and correct odd-parity implementations (count_ones based).

## 3. Findings
F-001 [S2]
Where: crates/subtitles/src/cc/cc_data.rs:297-305 (layout claim) and 343-369 (implementation)
Code:
```rust
/// triplet `[cc_valid 1][cc_type 2][cc_data_1 7 + reserved 1][cc_data_2 7 + reserved 1]`
/// — the bit order of the reference decoders' SCTE-20 walk (no
/// leading reserved bit, unlike the byte-aligned `cc_data()` form).
```
and (lines 349-369)
```rust
        for slot in &mut data {
            let bits = r.take(7).ok_or(CcDataError::Truncated {
                what: "SCTE-20 data bits",
                needed: 7,
                got: 0,
            })? as u8;
            let _ = r.take(1); // reserved bit — value not defined
            // Re-synthesize odd parity in the MSB so the 608 layer's
            // uniform parity rule applies.
            *slot = eia608::with_odd_parity(bits);
        }
```
What is wrong: SCTE 20's `caption_user_data` places a 4-bit `marker_bits` field ('1111') after EACH 7-bit `cc_data_prime` field — `[valid 1][type 2][data1 7][marker 4][data2 7][marker 4]` = 25 bits per triplet — not 7+1-reserved = 19 bits with the nibbles at the end. Under the standard layout this parser reads data1 correctly, then takes the FIRST marker bit as the "reserved" bit, then reads `111` + the top 4 bits of data2 as data2, and every later triplet's alignment is off by 6 bits per preceding triplet. Real SCTE-20 streams decode garbage from byte 2 onward.
Why it matters: `docs/formats/sub-cc.md:30` and the feature-matrix evidence string present "SCTE-20 bit-packed" as implemented; a cable-broadcast SCTE-20 stream is the realistic case for this grammar. The author's own worklog admits the pin is unverified: "SCTE-20 bit order pinned per ffmpeg's walk (stated in code, one-line flip if contradicted)" (docs/worklog/archive-2026-10.md:9956) — and the cited "ffmpeg mpeg12 SCTE-20 walk" (line 325) is UNVERIFIED: no ffmpeg tree exists in this sandbox, and I know of no SCTE-20 support in ffmpeg's mpeg12dec (long-standing open feature request).
What correct looks like: `take(7)` data + `take(4)` marker (validated '1111', damage-typed on mismatch) per byte, per the SCTE 20 syntax; then a real standard-conformant vector.
Confidence: MEDIUM (standard text paywalled/not in-tree; ffmpeg reference unverifiable here) — Verification: read + layout reasoning; UNVERIFIED against the SCTE 20 document itself.
