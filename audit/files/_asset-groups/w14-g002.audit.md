## 1. One-paragraph verdict
Both assets are real, spec-valid, byte-reproducible artifacts of the committed
deterministic generators (`gen-icon.py`/`gen-ico.py`) filled with the one brand
color `product.toml` carries — and that is ALL they are: each image contains
exactly one pixel color (#4f8cff) across its entire canvas. They are wired into
the tauri shell's build (`bundle.icon`), are referenced nowhere else in code or
packaging, and no installer ever installs either file: the Linux lanes
regenerate their own identical PNG at package time, and the Windows/macOS
installers ship no icon resources at all (no production .icns exists in the
repo). The app's user-visible icon identity is therefore a flat blue square on
Windows/Linux and a generic icon on macOS — a documented placeholder for the
Linux lane only (RELEASE.md known-limit #5), silently applied to the tauri
shell surfaces. Currently the whole lane is dead anyway: the crate cannot
compile (app.rs:301 E0425), so these icons decorate a binary this tree cannot
produce.

## 2. What actually works (verified)
— `python3 scripts/release/gen-icon.py /tmp/gen-icon-check.png '#4f8cff'` →
"wrote ... 512x512 RGBA, fill #4f8cff, 1819 bytes"; `cmp` with
`apps/desktop-tauri/icons/icon.png` → **byte-identical**. Same for
`gen-ico.py` (687 bytes) vs `icon.ico` → **byte-identical**. The generators'
determinism claims (gen-icon.py:13-16, gen-ico.py:15-17) hold exactly; the
committed files are provably the generator outputs at the committed accent.
— Full structural decode (python, my own parser): icon.png = PNG sig, IHDR
512x512 8-bit RGBA non-interlaced, IDAT+IEND CRCs valid, 0 trailing bytes;
icon.ico = ICONDIR reserved=0/type=1/count=1, ICONDIRENTRY w=0 h=0 (→256),
planes=1, bpp=32, payload=665 @ offset 22, 22+665=687 exact, payload is a
valid 256x256 RGBA PNG. **Pixel census: 1 distinct pixel per image —
(79,140,255,255)** = `product.toml:95` `accent_color = "#4f8cff"`. No tEXt/
metadata chunks, no trailing data, no embedded payload of any kind. Suspicious
content: none (and byte-identity to the generators rules out steganography).
— `file(1)` concurs: "MS Windows icon resource - 1 icon, 256x256 with PNG
image data" / "PNG image data, 512 x 512, 8-bit/color RGBA".

### F-005 [S4]
Where: apps/desktop-tauri/icons/icon.ico:7-22 (the single ICONDIRENTRY)
Code:
```text
reserved=0 type=1 count=1 | w=0(→256) h=0(→256) colors=0 rsvd=0
planes=1 bpp=32 payload=665 offset=22   (my parser's dump of bytes 0-22)
```
What is wrong: the ICO carries exactly one 256×256 PNG-compressed entry — no 16/24/32/48 px sizes. Spec-legal (verified header; PNG-in-ICO is the standard Vista+ form), and Windows downscales from the 256 entry, so the practical impact on a flat square is nil; but it is below the multi-size convention real-world .ico files follow, and PNG-only single-entry files are the part of the format legacy tooling mishandles most. (What tauri's own template icons contain: UNVERIFIED — no tauri sources in this sandbox.)
Why it matters: quality/hygiene only; noted so nobody mistakes the minimal entry set for a deliberate multi-size design.
What correct looks like: gen-ico.py emitting 16/32/48 BMP entries + the 256 PNG entry (stdlib-feasible; ~20 more lines), or a comment in the script recording that the single-entry form is deliberate.
Confidence: HIGH — Verification: ran (header parse + `file` + `od`); the OS-side rendering behavior itself: UNVERIFIED (no Windows environment).
