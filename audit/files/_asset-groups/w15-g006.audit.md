## 3. Findings

### F-001 [S2 — cross-ref W15-A04 F-001, independently confirmed] Hotkey overrides are write-only state
Where: ui/src/screens/settings/areas/hotkeys/overrides.ts:16-39
Code:
```
export const localStorageHotkeyOverrides: HotkeyOverridesStore = {
  load() {
    try {
      const raw = window.localStorage.getItem(STORAGE_KEY);
```
What is wrong: the store (`lumen.hotkeys.overrides.v1`) round-trips overrides that no runtime key handler reads — my independent sweep: the storage key appears only in overrides.ts, the HotkeysEditor (writer), controls.tsx reset-all, and tests; PlayerScreen's accelerator display reads generated DEFAULTS (PlayerScreen.tsx:216-221); keymap.ts has no override read. The header admits "a MOCK localStorage round-trip today, the real write path (keymap config over the client bridge) is the app layer's handoff."
Why it matters: a user rebinds a key, clicks Apply, reloads — the override looks durable and changes nothing (full analysis and severity owned by W15-A04's HotkeysEditor.tsx audit F-001; recorded here so the group file stands alone).
What correct looks like: wire keymap.ts to merge overrides at match time, or stage/disable the editor's Apply per the project's honesty grammar.
Confidence: HIGH — Verification: my own rg sweep + read; cross-ref audit/files/.../HotkeysEditor.tsx.audit.md.

### F-002 [S4] Stale schema comment in settingsThemeSync — the "auto" gap it warns about is closed
Where: ui/src/theme/settingsThemeSync.ts:26-29
Code:
```
 * PICKER already renders the third cell (Light · Dark · System, f03 lane)
 * writing "auto"; the schema enumeration (schemas/settings.toml
 * `interface.theme`) is still dark/light only — the REAL engine write path
```
What is wrong: at HEAD the schema enum CARRIES "auto" (generated/schema.ts:96 `enumeration: [{dark}, {light}, {auto}]`; schemas/settings.toml:76-80 documents adding it as the k12-regression fix). The comment still tells the reader the engine write path will reject "auto".
Why it matters: a fixer following this comment would "repair" a non-gap, and the k12 load-validation story (which dropped persisted "auto" until the schema carried it) reads confusingly against the stale text.
What correct looks like: regenerate the comment to the post-fix reality (schema carries auto; localStorage seam validates it).
Confidence: HIGH — Verification: read schema.ts:87-99 + settings.toml:73-90.

### F-003 [S4] Lane-seam precedence divergence across the family
Where: ui/src/screens/playlist/usePlaylistMsg.ts:34 vs ui/src/screens/settings/settingsMsg.ts:70-71
Code:
```
    (key: MessageKey | PlaylistLaneKey): string => m(key as MessageKey) ?? laneCatalog[key],
```
```
  return (key: SettingsMsgKey): string =>
    settingsLaneCatalog[key] ?? m(key as MessageKey) ?? "";
```
What is wrong: two precedence conventions in one seam family — playlist/subtitles seams resolve CATALOG-first (a registered catalog value beats a lane retitle), settings resolves LANE-first (retitles must beat the catalog until registered — the k12 fix for a real shell-vs-rows copy divergence, documented at settingsMsg.ts:16-23). A future playlist/subtitles retitle registered in messages.ts but not yet merged would silently show the OLD catalog copy on those surfaces.
Why it matters: the exact shape of the bug k12 already had to fix once, now latent in the other two seams; nothing machine-checks the convention.
What correct looks like: one documented precedence for all lane seams (or a comment in each catalog-first seam stating why retitles cannot occur there).
Confidence: HIGH — Verification: read of all three seam files (useSubtitlesMsg.ts:24 same shape).

### F-004 [S4] Generator typo ships mangled "[media]" into the generated bindings doc comment
Where: ui/src/screens/settings/areas/hotkeys/generated/bindings.ts:9 (source: ui/scripts/gen-hotkeys-data.mjs:88)
Code:
```
  /** keymaps/default.toml section (edia], [navigation], …). */
```
What is wrong: "(edia]" is a mangled "[media]" — the typo lives in the GENERATOR (gen-hotkeys-data.mjs:88) and is inherited verbatim by the generated output, which may not be hand-edited (drift-guarded by hotkeys:check).
Why it matters: cosmetic, but it regenerates forever until the generator is fixed; the file's own fence makes hand-repair the wrong move.
What correct looks like: fix the string in gen-hotkeys-data.mjs and regenerate.
Confidence: HIGH — Verification: rg hit at both sites.
