## 3. Findings

### F-001 [S3]
Where: ui/src/i18n/keys/w26.f13.ts, ui/src/i18n/keys/w26.i03.ts, ui/src/i18n/keys/w26.i16.ts
Code:
```ts
// w26.f13 lane keys — the player app menu's frame-exact labels (menu.png /
// menu.svg, analysis §A1). Registered into ui/src/i18n/messages.ts by the
// Lead after the wave merge; until then ControlBar resolves them through its
// seam-first lane resolver (PlayerScreen's c6/f09 pattern), so the copy
// renders identically before and after.
```
What is wrong: "until then" has passed and the resolver is gone. All three files have ZERO importers (verified: `rg -l "keys/w26.f13\""` etc. — empty; w26.i16's only mentions are wave-name comments in icons.tsx). Their keys are fully registered in messages.ts (python3 cross-check: f13 6/6, i03 12/12, i16 2/2 present in the catalog) and referenced by production code through the catalog. The lane files are dead duplicates of catalog content — pre-registration scaffolding that outlived its purpose. ControlBar's live resolver imports w26.k07 (:55), not f13/i03.
Why it matters: dead code (the scale's own S3 example); worse, they are LIVE-LOOKING dead code — a maintainer editing "player.appmenu.*" copy in w26.f13.ts changes nothing (messages.ts wins), the exact drift trap the lane headers warn about in the other direction.
What correct looks like: delete the three files (their i03 sibling already documents the correct lifecycle — its header notes k18 pruned dead keys from it; the file itself should have followed).
Confidence: HIGH — Verification: zero-importer rg × 3 + catalog cross-check (all keys registered) + production-reference check (all keys referenced outside i18n).

Confidence: HIGH — Verification: import verified, CLIP_INFOS keying verified, arbitrary-source synthesis path read.
