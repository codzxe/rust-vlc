## 3. Findings

### F-001 [S3]
Where: plugins/extensions/metadata-provider/plugin.wasm + plugins/extensions/ui-panel/plugin.wasm (the group as a whole)
Code:
```toml
# product.toml:166
wasm-extensions = false         # Phase 7
```
What is wrong: the two blobs are the only real plugins in the repository, and nothing that ships can load them. plugin-host-wasm has zero dependents (rg over every Cargo.toml); `product.toml` disables wasm extensions; no packaging script references plugins/; the shipped `lumen` CLI links only plugin-api's in-process contracts (Demuxer/Access — see discovery.rs audit).
Why it matters: the plugin architecture is real machinery (host, sandbox, packaging CLI, conformance) + real modules, with zero product integration. Any claim that "Lumen supports plugins" at the user level is currently false — the whole lane is test-proven and product-inert. (The README itself is honest: these are "example extensions" for a walkthrough.)
What correct looks like: the Phase-7+ card that flips `wasm-extensions` and wires the host into a shipped entry point.
Confidence: HIGH — Verification: rg dependents + product.toml read + baseline packaging gate log (no plugin payload).

### F-002 [S4]
Where: plugins/extensions/metadata-provider/plugin.wasm (embedded manifest data section; same in ui-panel/plugin.wasm)
Code:
```toml
hash = "sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855"
```
What is wrong: the manifest embedded in each module's data section carries the SHA-256 of the **empty string** (`e3b0c442…` is the canonical empty-input digest) as its provenance hash, while the committed `manifest.toml` files carry the documented placeholder form `sha256:…(64 hex)`. Two different placeholder conventions for the same field, one of them masquerading as a real digest of nothing.
Why it matters: a consumer that verifies a module's self-reported manifest against the blob's actual digest will mismatch by design — and the mismatch value is a *valid-looking* digest, not an obvious placeholder. Confusing for the packaging/tamper-check path the README documents (`stamp_manifest_hash`).
What correct looks like: the embedded manifest uses the same `sha256:…(64 hex)` placeholder form (or the real digest stamped at emission time).
Confidence: HIGH — Verification: `strings -a` of both blobs (embedded manifest read); empty-string SHA-256 value is a known constant; README l.15-18 documents the placeholder convention the committed manifests follow.
