# FX4-A02 — the host audio-control verbs, routed for real (FIX-PLAN §3 F1.1c)

## Approach

The W07 verdict was "the ENTIRE user-facing volume/EQ/mute/balance
surface is dead: `audio.set-volume` refused by every shipped host"
(W07-A02/A06/A07/A08). FX3-A03 landed the engine half — `AudioControls`,
the runtime master chain on the streaming pipeline. My row is the host
half: route the catalog's audio-control verbs through the one command
layer (`lumen_dispatch` — the entry the machine mode, the desktop shell
and the tauri shell all drive, ARCH-5) to the live session's controls.

**The plumbing discovered by reading the working verbs.** Pause/resume
go through the ENGINE's inbox (`SessionCommandKind::Pause` — no audio
rows exist there); the class-S snapshots (`media.get-info`) are host
methods reading host-held state. The audio controls live on the
pipeline inside the `CliFrameConsumer`'s locked state (`ConsumerState::
audio: Option<AudioLimb>`) — host-side, not engine-side — so the verbs
are class-S host methods: validate → lock the consumer → reach the
audio limb's controls → apply → answer the chain's own read-back
(getters), never the request echoed.

**Three drift findings, stated up front (honesty contract):**

1. **Catalog drift on set-balance/set-eq.** The assignment names
   `audio.set-volume/set-mute/set-balance/eq`. The catalog
   (`crates/commands/src/catalog/{command,ids}.rs`) has
   `audio.set-volume`, `audio.get-volume`, `audio.set-mute`,
   `audio.list-devices`, `audio.set-device`, `audio.set-delay` — there
   is NO `audio.set-balance` and NO `audio.set-eq` command anywhere in
   the catalog (the audit itself recorded this: "the command catalog
   has no `audio.set-eq` (only audio.set-volume/set-mute)"; the UI's
   `data-pending-command="audio.set-eq"` markers await it). Balance/EQ
   therefore cannot be "no longer refused" — there is no verb to
   route. The seam I build reaches the full `AudioControls`
   (`set_balance`/`set_eq` included — FX4-A05's session-level tests
   already pin those through `session.limb.audio_controls()`), so the
   day the catalog grows those ids the routing is a dispatch arm away.
   Serving them would have required catalog edits in
   `crates/commands` — outside my file domain.
2. **The refusal site is dispatch.rs, not host.rs.** The verbs were
   refused by `route`'s catch-all (`unsupported-for-host`) and absent
   from `SERVED`. A host.rs-only change cannot un-refuse a verb — the
   assignment's own "route them for real / mirror a working verb's full
   path" therefore required the routing arms + SERVED entries in
   `apps/cli/src/dispatch.rs` (un-owned by any other FX4 row —
   verified against the tsv). I made that minimal edit and disclose it
   here.
3. **help.rs is forced by the existing pins.** `served_table_matches_
   the_help_synopsis` (dispatch.rs tests) asserts SERVED ↔ the `--help`
   synopsis are the same set, and `synopsis_ids_parse_and_cover_the_
   served_set` (help.rs tests) pins the count at 15. Serving the verbs
   without the synopsis row fails the central test run; a synopsis row
   without a served id fails it too. One row (naming the three ids,
   marked "(machine mode)" so it never advertises a REPL verb that
   does not exist — parse.rs is FX4-A06's file and has no
   `volume`/`mute` verb) plus the count pin 15 → 18. No test was
   weakened; both pins were extended.

**The frozen FX4-A01 seam (parallel wave, NOT in the tree at my write
time — `rg audio_controls apps/cli/src/pipeline_host.rs` was empty).**
Per the contract I coded against `audio_controls()`; the engine's own
docs (FX3-A03, `controls.rs`) name "the CLI's `AudioLimb`" as the host
seam, and FX4-A05's landed test file independently pins the same shape
(`session.limb.audio_controls()`). My one call site is
`host.rs::audio_limb_controls`: `guard.audio_mut().map(AudioLimb::
audio_controls)` — i.e. it needs `ConsumerState::audio_mut()` (the
mutable twin of the existing `audio()`) plus
`AudioLimb::audio_controls(&mut self) -> &mut AudioControls`. If
FX4-A01's landed reachability accessor differs (e.g. `audio_controls`
directly on `ConsumerState`), the reconciliation is ONE line in that
single helper — that is why the seam is isolated there.

## Test design

`apps/cli/tests/fx4_a02_host_audio_verbs.rs` — the in-process harness
of `pipeline_accounting.rs` (`CliHost` + the real `lumen_dispatch`)
for five tests, plus one through the real binary:

1. `fx4_a02_set_volume_is_served_and_reads_back_the_live_chain` —
   THE W07 inversion: open the stereo PCM fixture → `AudioGetVolume`
   answers the live identity `1.0` (hydration before any set) →
   `AudioSetVolume 0.5` completes with the applied truth → the read
   twin confirms → a second set (0.25) moves the same live chain → the
   session stays `Playing` (the between-quanta discipline, never a
   rebuild).
2. `fx4_a02_set_mute_round_trips_and_composes_with_volume` — mute on
   → `AppliedBool(true)`; the volume read-back still 0.5 (mute is a
   stateless multiply by zero, FX3-A03's composition property held
   through the verb lane); unmute → `false`; volume still 0.5.
3. `fx4_a02_audio_verbs_without_a_session_refuse_not_ready` — all
   three verbs on a fresh host: `[session.not-ready]` — the state
   truth, never a panic, never the capability lie.
4. `fx4_a02_limb_less_session_refuses_typed_not_a_fake_default` —
   the ADTS fixture (the host's own `in_band_config_audio_stays_limb_
   less` seam pin) opens limb-less; `audio.set-volume` refuses
   `[audio-output.not-ready]` instead of fabricating a default applied
   nowhere.
5. `fx4_a02_invalid_volume_refuses_typed_at_the_control_boundary` —
   −1.0 → detail code `audio.gain_negative`; NaN → `audio.gain_
   not_finite` (W07-A02 F-001's discipline: typed, never a clamp).
6. `fx4_a02_machine_mode_audio_verbs_answer_completed_not_refused` —
   the audit's reproduction, inverted, through the REAL binary
   (`--control-stdio`): open → set-volume → get-volume → set-mute as
   NDJSON on the wire; the responses carry the §2.6 payloads
   (`audio-volume` 0.5 / `applied-bool` true) and the
   `unsupported-for-host` string is gone from the whole transcript.

The sample-level oracle (volume/mute/EQ observable in rendered
samples) is FX4-A05's lane — their `fx4_audio_path.rs` (landed) pins
it through `session.limb.audio_controls()` at the session depth and
their host-level test pins exactly my wire payloads.

## Acceptance vs FIX-PLAN

F1.1c's "sound experience knobs" acceptance: "volume and mute work
in-session" — delivered at every host chained through `CliHost`
(CLI machine mode, desktop, tauri): the verbs complete against the
live master chain and answer the applied truth; the honest refusals
(none of session / no audio limb / bad volume) are typed. The FIX-PLAN
bullet's "EQ math wired to nothing" and "mute and balance dead" halves
are closed engine-side (FX3-A03) and observable session-side
(FX4-A05); balance/EQ verbs await the catalog ids (drift #1 above —
out of my file domain). No public API churn: three `pub(crate)` host
methods, three dispatch arms, one data row.

   read twin of the same §2.6 surface, needed by FX4-A08's UI

   unwired config: my validation is the engine-true boundary (finite,

   that config join lands — the followup is the settings-schema
   consumer seam, not a host patch.

   (ADR-005)") is still accurate for the remaining refused audio ids
