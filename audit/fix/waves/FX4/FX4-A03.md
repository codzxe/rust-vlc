# FX4-A03 — desktop host audio chain verification (chains through CliHost)

## Approach

The assignment: the desktop (apps/desktop) chains through the CLI host
(`CliHost`) per the architecture, so the FX4-A01 backend factory and
the FX4-A02 verb routing should be inherited by construction — verify
that end-to-end at the code level, fix anything broken in
`apps/desktop/src/**`, and lock the inheritance against drift with
`fx4_a03_*` regression tests. This is the desktop-crate twin of
FX4-A04's tauri-lane verification.

I read the full audio-relevant surface of my file domain
(`shell.rs`, `dispatch.rs`, `host.rs`, `files.rs`, `main.rs`,
`lib.rs`, `frame_tap.rs`, `transport.rs` headers) and traced the
construction chain out into the shared host (`apps/cli/src/host.rs`,
`apps/cli/src/dispatch.rs`, `apps/cli/src/pipeline_host.rs`), the
wrapper that drives this crate in production
(`apps/desktop-tauri/src/app.rs`), and the crate's existing test
conventions (`tests/pipeline.rs`, `tests/common/mod.rs`, the
shell.rs pacer proofs). Grounding: RULES, wave-FX4.tsv row FX4-A03,
FIX-PLAN §3 F1.1, wave-08 SUMMARY (S0: every host renders audio into
NullBackend), FX4-A04's report, and the per-file audits for the two
files at the heart of the chain (shell.rs, dispatch.rs — the rg over
ALL `audit/files/apps/desktop/src/*.audit.md` finds zero
audio-related findings).

**The verification answer: the desktop host inherits the audio path
by construction and contains nothing to remove.** The four audit
questions resolved to "already-correct":

1. **Construction is shared, not per-host.**
   `ShellRuntime::new` (apps/desktop/src/shell.rs:126) composes
   `ShellHost::new()` (apps/desktop/src/dispatch.rs:82-87), which
   adopts the CLI's own `lumen_cli::host::CliHost::new()`
   (dispatch.rs:84 — the ARCH-5 reuse). No other host or pipeline
   constructor exists in `apps/desktop/src/**`; the production
   consumer (the ADR-004 tauri wrapper) manages exactly one such
   runtime (apps/desktop-tauri/src/app.rs:290-292) and registers
   exactly one command (app.rs:293).
2. **The audio session opens in the SHARED open path.** Every
   acquisition funnel — `ShellRuntime::open_path` (shell.rs:300-304)
   → `open_path_request`/`open_file_request` (dispatch.rs:220-261,
   `Command::SessionOpen` with `options: Default::default()`) — and
   the webview-invoke path (`ShellRuntime::dispatch`, shell.rs:153,
   options passed verbatim from the wire) route through the ONE
   `lumen_dispatch` (apps/desktop/src/dispatch.rs:211-213) →
   `lumen_cli::dispatch::lumen_dispatch` → `CliHost::open_session`
   (apps/cli/src/host.rs:901), which constructs the audio limb at the
   shared `pipeline_host::open_audio_session(channels, rate, anchor)`
   (host.rs:944) — the exact site FX4-A01's backend factory owns
   (today `NullBackend::open_stream`, pipeline_host.rs:1784-1785; the
   factory replaces it there). The desktop inherits FX4-A01
   automatically the moment it lands; no desktop-side wiring is
   needed or possible.
3. **No discard shortcut, no second pipeline, no dead controls.**
   `OpenOptions`' default is `no_audio: false`
   (crates/commands/src/catalog/types.rs:240-252) and no
   `no_audio`/`no_video` construction exists anywhere in
   apps/desktop/src (rg: zero hits). The pacer delegates to the
   adopted host's own pumps (`pump_once` → `CliHost::pump`,
   shell.rs:259; `pump_session` → `CliHost::pump_wallclock`,
   shell.rs:280) and `PACER_TICK` is *derived* from
   `lumen_cli::pipeline_host::RENDER_QUANTUM` (shell.rs:80-81) — no
   second clock. The crate's own transports/bridges/taps
   (`wire.rs`, `transport.rs`, `frame_tap.rs`) carry the LUF1 VIDEO
   record lane only. rg `NullBackend|NullDevice|NullStream|
   open_audio_session|AudioLimb|AudioPipeline|audio-output` over
   apps/desktop/src: zero hits — the crate cannot even name the
   backend types (audio-output is not a dependency). rg the whole
   audio-verb vocabulary (`SetVolume|SetMute|Volume|volume|Mute|
   Balance|Equalizer`): zero hits — there is no desktop-side audio
   controls surface to go dead; audio verbs flow to the adopted
   host's route table (today the honest ADR-005 refusal,
   apps/cli/src/dispatch.rs:193-194; post-FX4-A02 the
   `audio_controls()` routing — inherited verbatim because the
   desktop delegates verbatim, dispatch.rs:212).

Consequently item 2 of the assignment ("fix anything broken in your
domain") resolved to **nothing to fix** — this is a pure-verification
deliverable: the locking tests plus this report. Zero `src/` changes;
one new test file. (FX4-A04 reached the same answer for the tauri
lane; the two wrappers agree.)

## Changes per file

- **apps/desktop/tests/fx4_a03_audio_lane.rs** (NEW — the only
  change). Four tests, convention-mirrored (integration test file in
  `apps/desktop/tests/`, `concat!(env!("CARGO_MANIFEST_DIR"), …)`
  fixture paths, bounded pump loops with wall-clock hang guards,
  match/`unreachable!` style, no unwrap/expect, lumen-allow-literal
  comments on path literals):
  - `fx4_a03_desktop_runtime_audio_lane_runs_to_end` — the runtime
    constructed exactly as the wrapper's `ShellState` manages it
    (`ShellRuntime::new(DEFAULT_EVENT_CAPACITY)`), the audio-only
    fixture (`tests/fixtures/generated/valid/
    wav_pcm_s16le_44k1_st.wav`, 0.2 s stereo 44.1 kHz PCM) opened
    through the desktop host's own funnel, play dispatched through the
    single command, then ONLY pump ticks drive the session to `Ended`.
    Asserts the audio-lane observables on the adopted host's public
    seams: `audio_lane_counters()` accepted > 0 (audio-only media:
    every accepted frame is audio — a discard shortcut or limb-less
    open leaves it at zero forever), `position_us()` inside
    190 000..=210 000 µs (audio-only media advances ONLY through the
    audio-master sample counter; the CLI conformance lane's oracle
    for this same fixture is `ok: time 0.200000s (100.0%)`), `Playing`
    and `Ended` reached, egress conserving. Time-tick counts are
    deliberately NOT asserted (250 ms tick interval > the 0.2 s
    fixture — zero ticks is correct behavior).
  - `fx4_a03_open_funnel_keeps_the_audio_track_enabled` — the
    discard-shortcut oracle at the wire level, for BOTH acquisition
    funnels the desktop owns: the classifier funnel
    (`open_path_request`) and the drag-drop translation
    (`PathDragDrop::on_files_dropped`, first-openable-wins) ship
    `session.open` with `no_audio == false`, `no_video == false`,
    live from the start. Any future funnel drift that disables audio
    fails at the wire level, before any engine behavior changes.
  - `fx4_a03_audio_verbs_delegate_to_the_adopted_host` — the
    verb-routing drift-lock over the whole catalog audio surface
    (`audio.set-volume/get-volume/set-mute/list-devices/set-device/
    set-delay`): the desktop shell answers EXACTLY what a bare
    adopted `CliHost` answers for the same request on
    identically-driven hosts (request_id, session, generation, and
    result compared). A desktop that grows its own audio-verb
    handling — dead controls surface, rewrite, interception — makes
    the answers diverge and fails here.
  - `fx4_a03_live_session_audio_verbs_delegate_unchanged` — the
    live-session twin: the SAME fixture driven to identical engine
    state through (a) the runtime's own funnels and (b) a bare
    adopted host driven through the identical dispatch sequence
    (state equality asserted before the comparison), then the same
    `audio.set-volume` through both — identical answers. This catches
    a shell that intercepts audio verbs only once a session is live
    (the realistic drift for a desktop-side volume knob).
- **No `src/` changes** — the audit questions resolved to
  already-correct by construction (findings 1-3 above); every
  `apps/desktop/src` file on the audio path was read in full or
  header-verified, and the per-file audits contain zero audio
  findings.

## Test design

The four tests are **outcome-invariant across the sibling landings** —
deliberately so, because the wave compiles centrally as a whole: a
test pinning "audio verbs refused" would break the moment FX4-A02
routes them; a test pinning "set-volume served" would break if FX4-A02
slips. The delegation-equality invariant (`the shell answers what the
adopted host answers`) holds on BOTH sides of FX4-A01/A02's landings
because equality is between two hosts driven identically — which is
exactly the property my assignment owns: the desktop's *inheritance*,
not the host's *behavior*. Likewise the run-to-end test observes the
backend-agnostic seams (`audio_lane_counters`, the sample-counter
clock) that hold over the null device today and over the factory after
FX4-A01.

Unlike FX4-A04's tauri twin (CI-gated behind webkit2gtk-4.1), this
crate builds headlessly, so these four tests run in the **ordinary
workspace lane** — the same lane the shell.rs pacer proofs run in
(`pacer_proof_pump_once_drives_a_real_session_to_end` is the oracle
they were authored against). No new dependencies, no dev-dependencies
edit (lumen-cli/commands are already regular deps of the crate, which
is what makes the twin-drive comparison possible from an integration
test). rustfmt (edition 2021, the allowed exception) ran clean on the
file.

## Risks & followups

1. **The tests have not executed on this box** (cargo test is
   forbidden; the orchestrator compiles centrally). They are
   calibrated against proven neighbors: the shell.rs pacer proofs
   (same runtime, same pump loop, 1024-pump bound = the AVI proof's
   own headroom over ~170 actual pumps), the CLI's end-position oracle
   (`container_conformance`: this exact fixture ends at 0.200000s), and
   the CLI host's own WAV limb tests. If the 0.2 s fixture needs more
   than 1024 pumps the bound assertion fails loudly — a calibration
   fix, not a design change.
2. **The live-twin state-equality assert is the canary**: the twin
   drive assumes `CliHost::pump()` stays deterministic (whole-ring
   drain; the wall variant is `pump_wallclock`, not used here) and
   that the runtime's dispatch extras (`observe_response`, the event
   drain) never mutate engine state — verified by reading
   (shell.rs:153-167; dispatch.rs:100-109 is a read-only cursor). If
   that ever changes, the test fails at the state assert BEFORE the
   verb comparison — loud, not silent.
3. **For FX4-A02 (owner of apps/cli/src/host.rs + dispatch.rs)**: the
   wave row names `set-balance/eq` verbs, but those are not catalog
   ids today (`crates/commands/src/catalog/command.rs` carries
   set-volume/get-volume/set-mute/list-devices/set-device/set-delay
   only) — adding catalog variants touches crates/commands, which is
   in neither sibling's stated file domain; their report should state
   the decision. My tests sweep the six existing ids, which is the
   correct drift surface regardless.
4. **The shipped GUI stays null-backend until someone enables
   `backend-cpal` in a shipped graph** — identical to FX4-A04's risk
   2: the desktop crate cannot enable a backend feature by
   construction (audio-output is not even a dependency); the feature
   flip is a Cargo.toml decision for the Lead (out of RULES scope for
   every FX4 agent).
5. **Observed, out of my audio scope** (from the per-file audits,
   left untouched): shell.rs F-004 (`pump_session` untested in
   shell.rs — my tests drive `pump_once` like the proven oracle; a
   `pump_session` variant needs the injectable-clock seam, F1.2's
   hardening lane), F-005 (`unreachable!` in `bind_frame_channel` —
   frame lane), F-007 (discarded `ResponseObservation`); dispatch.rs
   F-001 (grow-only event-log contract), F-004 (the `pub engine_host`
   escape hatch — used by these tests for observability, which is its
   documented intent). None are audio-lane defects; the desktop
   binary's honest exit-86 skeleton posture (main.rs) is unchanged.
