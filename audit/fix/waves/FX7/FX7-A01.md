# FX7-A01 — W1-06: the hold stashes the CONVERTED frame

## Approach

Row FX7-A01 of wave-FX7.tsv: the W1-06 registered defect — the root
cause of the FX6 wave's 18/60 frame-presentation shortfall — "the
present-hold stashes the UNCONVERTED I420 frame → renderer refusals;
stash the CONVERTED frame". Evidence chain honored: FX6-R3/R4's
diagnosis, the per-file audit (F-001), the W1-06 register note in the
code itself, and the hold code.

**The defect as found — no drift.** apps/cli/src/pipeline_host.rs,
the `accept_video` match arm at **:1686-1717** (the registered
:1686-1714 region; the arm's body after rustfmt ends at :1717):
the accept path converts I420→RGBA into `uploadable` at :1669-1682
and hands it to `video.scheduler.push(uploadable)` at :1683;
`PushOutcome::WindowFull` carries the frame back untouched
(crates/video-engine/src/scheduler.rs:120-127 "The untouched frame,
handed back"), but the arm stashed `frame.clone()` — the UNCONVERTED
original — at old :1712. `retry_video_hold`
(:1355-1374) then re-pushed those originals via
`scheduler_push_for_hold` (:1160-1169); the renderer refuses I420
uploads (`render.upload.format-unsupported`, renderer.rs:239-241 —
`uploads_format` accepts only Rgba8/Bgra8), so the 44 hold-retried
frames of the fixture never presented: 60 decoded, 60 selected by the
scheduler, 16-18 taken by the renderer — the exact loss FX6-R3/R4
pinned and the W1-06 register note self-documented. The conversion
IS available at stash time (it happens before the push, in the same
call), so the registered remediation applies as written — no drift
to report beyond the line shift the FX6 reports already recorded.

## The fix

One line of behavior, the comment block rewritten to record the
closure (the file's docs elsewhere already described the intended
state — `ConsumerState.video_hold`'s "FIFO of already-converted
frames" (:1267), `scheduler_push_for_hold`'s "no conversion: the hold
stores already-converted frames" (:1160) — the code was the
deviation; they are now true as written):

- The arm's pattern now binds the handed-back frame:
  `PushOutcome::WindowFull { frame: held, .. } if
  state.video_hold.len() < MAX_VIDEO_HOLD`, and the stash is
  `state.video_hold.push_back(held);` — the CONVERTED frame the
  scheduler refused admission for, not a re-clone of the original.
  No extra clone, no allocation change vs the defect's `frame.clone()`
  (one move instead of one clone — strictly cheaper).
- **The hold's other semantics preserved exactly:** FIFO ordering
  (push_back / pop_front, unchanged), the `MAX_VIDEO_HOLD` bound and
  its guard (unchanged), the drop-and-count past the bound (the
  second `WindowFull | UnschedulablePts` arm at :1718-1722, untouched
  — `video.refused` and `state.frames_refused`), the retry loop's
  Pushed/Refused/Dropped accounting (:1355-1374, untouched), and the
  seek boundary's generation-filtered retain (:1425-1426, untouched).
  The scheduler's own counters (`full_rejections`, `pushed`) are
  minted inside `scheduler.push` before the arm runs — unchanged.
- The comment block: the `[KNOWN DEFECT …]` card is replaced by the
  closure record (`[W1-06 CLOSED (FX7-A01)…]`) naming the measured
  loss it removes, and — per the honesty contract — the second,
  load-bearing defect the register note warned this fix exposes is
  kept ON the register in place (doc 03 §8 / 3.B: `advance_time`'s
  whole-ring-per-pump drain; see Risks).

`retry_video_hold` and `scheduler_push_for_hold` needed zero edits:
their docs already assume converted residents, and pushing an
already-converted frame into the window is exactly their contract.

## Test design

Three tests, the mutation each of the audit's own gap note ("NO test
exercises the WindowFull hold arm — stashing converted frames would
change zero test outcomes" — audit §5 GAP):

1. `fx7_a01_window_full_hold_stashes_the_converted_frame` — the UNIT
   pin (apps/cli/src/pipeline_host.rs tests module, where the six
   i420/reseeded unit tests live): a fact-less `CliFrameConsumer`
   over `wall_clock(0)`; 16 future-dated I420 frames fill the
   scheduler window (the `DEFAULT_MAX_PENDING` cap); the 17th hits
   the WindowFull arm; the test asserts the hold holds exactly one
   frame whose format is **Rgba8**, whose payload is 8×8×4 bytes
   (not the 96-byte I420 original), and whose pixel content is THIS
   frame's own BT.601-full conversion of Y=90 Cb=100 Cr=110 (R≈65,
   G≈112, B≈40, ±1 Q16 — computed against the same tables
   `i420_conversion_matches_jfif_vectors` pins). Under the defect
   this fails on `held.format == I420` — the direct mutation kill.
2. `fx7_a01_hold_presents_every_decoded_i420_frame` — the PIPELINE
   regression (new file apps/cli/tests/fx7_a01_hold_presents_decoded_
   frames.rs, the fx4/fx5 convention — same drive shape as
   pipeline_accounting.rs: open through the ONE dispatch, settle,
   `advance(RUN_PUMPS)`, headless accounting): the 4:2:0/I420-bearing
   fixture (avi_mjpeg_pcm.avi — 60 MJPEG frames) run to `Ended` at
   position 2.000 s; the decode oracle first (120 accepted, 60
   pushed, 0 late/refused — unchanged by the fix), then the W1-06
   closure: **`video_presented == scheduler_presented +
   scheduler_repeats`** (the exact residual FX6-R4's ledger derived
   as `hold_refusals` — now asserted at exactly zero), **`video_
   presented >= 60`** (every decoded frame presentable — the 60/60
   intent at the pipeline level), `staging_frames ==
   video_presented` and one full-frame RGBA copy per present
   (`staging_bytes == staging_frames·320·240·4` — the presents rode
   the upload path in the converted vocabulary). The mechanism pin
   `!renderer_wgpu::uploads_format(media_types::PixelFormat::I420)`
   keeps the regression non-tautological: with the upload gate
   refusing I420, covering all 60 can ONLY hold because the hold
   stashed CONVERTED frames.
3. `fx7_a01_presentable_run_is_deterministic` — two whole-media runs
   agree on the accounting (the determinism twin
   pipeline_accounting.rs already runs for the trail/position/PNG).

No new dependencies (renderer-wgpu and media-types are existing
lumen-cli [dependencies] — verified in apps/cli/Cargo.toml; the
test file imports only commands/lumen_cli/testkit, all already used
by neighbouring tests). No `.unwrap()`/`.expect()`/unsafe; the
`unreachable!` guards match the neighbouring tests' style.
