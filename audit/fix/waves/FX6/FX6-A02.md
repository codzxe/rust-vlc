# FX6-A02 — the ticker lane's stamps + receipt surface (FIX-PLAN §3 F1.2, wave-FX6 row FX6-A02)

## Approach

**The path drift, stated first.** My assignment and the wave TSV
cite `apps/desktop/src/app.rs` (:109 ticker, :223-229 shipping). That
file does not exist, and neither does its audit evidence
(`audit/files/apps/desktop/src/app.rs.audit.md`). The real defect site
is `apps/desktop-tauri/src/app.rs` — the cited line numbers match it
exactly (`:109` `SESSION_TICK = 10 ms`, `:223-229` the
`records.last()` ship), and the audit evidence that exists is
`audit/files/apps/desktop-tauri/src/app.rs.audit.md` (W14-A02, whose
F-005 is precisely "only `records.last()` (:223) is ever used — the
drained older records are allocated then discarded"). Per RULES I
located the real defect and fixed it there; everything below refers to
that file.

**The seam, read at write time.** The assignment's seam contract said
to read `apps/desktop/src/mailbox.rs` at write time and consume
FX6-A01's hardened surface exactly if present. It IS present —
FX6-A01 landed mid-flight while I was reading: the mailbox now has
`drain_to(&mut Vec<ShippedFrame>)` (the exhaustive drain, per-record
timestamps passing through untouched),
`MailboxStats::frames_produced()/frames_dropped()`, drop-reason
attribution and `last_enqueued/last_dequeued_ns`. The stamps ride the
records the ticker's reachable seam (`ShellRuntime::take_frame_records`
→ `FrameTap::drain_records` → `Vec<Vec<u8>>`) drains — each record's
LUF1 header carries `frame_id`/`pts_ns`/`emitted_ns` — but the
mailbox's own counters are NOT reachable from the tauri ticker:
`take_frame_records` returns only a `usize` and the shell exposes no
tap/mailbox stats accessor (shell.rs/frame_tap.rs are outside my file
domain).

**The parallel sibling, landed first.** FX6-A03 (whose row also lists
`apps/desktop-tauri/src/app.rs`) rewrote the ticker's ship region
while I was mid-edit — my first edit attempt failed verbatim-match
against their concurrently rewritten region. Their landed lane
(`crate::frame_channel::FrameLane`, bounded capacity 2, offer /
take_newest / drop-oldest / flush-on-rebind, conserving stats) now
carries the policy and the counters between the ticker's drain and
the webview dispatch, and their tests (`fx6_a03_frame_lane.rs`) pin
the bound, the policy and bytewise timestamp passthrough. I therefore
INTEGRATED instead of duplicating: my first-pass standalone lane unit
(own counters + own choose/ship logic) was superseded and replaced by
the slim observer that composes with their landed counters — no
second FrameLane, no second counting vocabulary.

**What row A02 uniquely owns in the final tree** (the two gaps
neither A01's nor A03's landed surface covers):

1. **The timestamp passthrough, made observable** —
   `record_stamps` reads the shipped record's own wire stamps (the
   frozen v1 header offsets, verified against `desktop::wire`'s
   encoder), `ShipLog::note_dispatched` latches them at every
   dispatch, and the receipt states them — the pre-FX6 ticker never
   read a single stamp off the records it shipped.
2. **The periodic produced-vs-dropped receipt** — every 128 ships the
   lane's counters (offered/shipped/overflow/superseded/stale) plus
   the last dispatched record's stamps hit stderr, mirroring the app's
   existing diagnostic convention (`eprintln!` + `lumen-allow-literal`
   markers) — A03's stall notice stays immediate; this cadence carries
   the totals the F1.2 hardware run measures ("instrument: frames
   produced vs frames dropped", FIX-PLAN §3 F1.2).

The 10 ms cadence itself is untouched: `SESSION_TICK`
(:110, unchanged) and the loop's `sleep` are exactly as audited —
the 4K-starvation question stays the hardware run's job, which the
counters/receipt now make measurable.

## Test design

`tests/fx6_a02_lane_receipt.rs`, a new integration-test file per the
RULES preference (avoids collisions with the siblings in this
crate), riding the same CI gate as every test in this workspace-
excluded crate (`tauri-check`, which installs webkit2gtk-4.1 — the
gate `fx4_a04`/`fx6_a03` ride). The tests drive the exact
composition the ticker's dispatch half runs
(`take_newest → note_dispatched → receipt over lane.stats()`), with
records built by the desktop crate's OWN wire encoder — so the stamp
reads are proven against the encoder's real output (a cross-check of
the frozen offsets, not a hand-built mirror):

1. `fx6_a02_dispatched_record_stamps_ride_the_lane` — the stamps
   latched are the record's own; a later dispatch re-latches; a
   truncated record and a non-LUF1 buffer latch `None` (the anomaly
   visible, never a guess).
2. `fx6_a02_lane_counters_increment_as_the_mailbox_reports` — three
   simulated ticks (one record / a burst of two / nothing) drive the
   bounded lane's offered/shipped/dropped counters tick by tick, the
   identity conserves, and the observer's stamps track the newest
   dispatch.
3. `fx6_a02_receipt_carries_produced_dropped_and_shipped_stamps` — a
   capacity burst (overflow drop + superseded drop) then one
   dispatch: the receipt line carries shipped/produced/dropped, all
   three drop buckets, and the dispatched record's frame_id/pts_ns/
   emitted_ns — the oracle for the stderr surface the hardware run
   greps.
4. `fx6_a02_receipt_reports_counters_alone_when_no_stamps_latched` —
   no latch → the counters still report, no fabricated stamp line.

## Risks & followups

1. **Same-file concurrent edit with FX6-A03** (both rows list
   `apps/desktop-tauri/src/app.rs`): I wired three statements into
   their landed dispatch block (the `note_dispatched` call, the
   128-ship receipt arm) and one declaration above it. If their final
   tree differs from what I read, the central compile reconciles at
   exactly those sites — the composition contract is:
   take_newest → note_dispatched(&record) → send_record → receipt
   over lane.stats() every 128 ships.
2. **The mailbox's own `frames_produced()/frames_dropped()` (FX6-A01)
   are not yet reachable from the tauri ticker** —
   `ShellRuntime::take_frame_records` returns a `usize` and no
   accessor chain exposes the tap's mailbox stats to the wrapper.
   Threading them into the same receipt needs a shell.rs/frame_tap.rs
   accessor (outside my file domain) — recorded as the wave's
   reconciliation point; the receipt's produced/dropped are the ship
   lane's counters, which is the half the webview-side lane actually
   observes.
3. **The receipt cadence rides the ticker thread** — observable on
   the launch/hardware lanes' stderr (one line per 128 ships ≈ 4 s at
   30 fps), not provable headlessly; the pure receipt content is what
   the tests pin.
4. The tests are CI-gated with the whole excluded crate (webkit2gtk)
   and so have never executed on this box — authored against the
   landed pub surfaces (`app::ShipLog`, `frame_channel::FrameLane`)
   and the desktop crate's real encoder, mirroring the fx4-a04/fx6-a03
   authoring posture.
