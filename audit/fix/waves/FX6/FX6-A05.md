### 1. The putImageData lane — verified correct + honest at the code level

  frame's width/height differ — `putImageData` is 1:1, never scaled; the

  (`frame-channel.ts:419-425`), so the mutation never escapes the call
  (re-verified this wave). Correct.
* **Refusal honesty** (`:321-324`): a null 2D context is a typed throw
  caught by onRecord — diagnostic, never a crash, never a stall.

### 2. The frame counter — surfaced honestly

New in `FrameCanvasSurfaceLive` (the shell-only live half):

* A **counter readout** (`data-frame-stats="webview"`, class
  `.lumen-player__frame-stats`, bottom-left chip on the canvas base):
  `Frames presented N · Last frame id N · Skipped records N`.
* **presented/skipped are THIS webview's counts** — incremented at the
  draw call and at the refusal path inside onRecord; they are
  measurements, not estimates, and are labeled as the webview's own.
* **lastFrameId is engine truth riding the transport** — read from the
  decoded record header (the 0-assignment engine counter, visible
  end-to-end). The cell stays EMPTY before the first frame — a "0"
  would CLAIM a frame was drawn (ids start at 0).
* **The gap, not fabricated**: the engine's produced/shipped/dropped
  counters do not ride the transport (FX6-A03's seam, this wave). The
  readout never invents them; the gap is stated in the component's own
  comment block and here. When a future wave adds a frame-stats event
  kind through `crates/commands`, `paintFrameStats` + the readout are
  the obvious extension points.
* **Imperative repaint** (`paintFrameStats`): the readout updates in
  the same onRecord lane as the canvas draw — no per-frame React
  re-render churn; a React re-render re-reads the live counters, so the
  readout can never desync from the painter.
* Browser mode: the readout never mounts (the frame lane doesn't
  either) — the honest empty surface stands.
