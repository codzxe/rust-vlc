# FX2-A07 — CoreAudio master-element property-address fix (FIX-PLAN §3, F1.1c "fix on the way past for the macOS lane")

## Approach

The audit's exact finding (W08-A02 F-001, S1, cited at
`coreaudio.rs:133-137` — no line drift, verified verbatim): the file
declared `const ELEMENT_MAIN: u32 = 1` where Apple's public
`AudioObjectBase.h` pins `kAudioObjectPropertyElementMaster` (renamed
`kAudioObjectPropertyElementMain`) to `0`, and **every**
`AudioObjectPropertyAddress` the file built carried `element:
ELEMENT_MAIN`. The audit enumerates all of the file's queries as
master-element (whole-object / whole-scope) queries — devices list,
default output, name, UID, stream configuration, nominal rate, both
listener registrations and both removals — and distinguishes **no**
genuinely non-master query. I re-verified this against the source: the
file had exactly 11 inline address constructions, all
`element: ELEMENT_MAIN`; none targeted a numbered stream. So the fix is
a re-pin of the one constant to 0 — plus hoisting the six distinct
(selector, scope, element) triples into named `const`s so that "the
property-address construction" itself is what the regression test
pins, per the assignment's wording.

The constant's old doc leaned on a `[VERIFY]` note ("compile-only
evidence"); the audit itself proved that excuse hollow — the value is
checkable against the public header from any OS. The new doc cites the
header; the module-doc evidence-status paragraph was updated to match
(the numeric-value `[VERIFY]` is retired; the hardware `[VERIFY]`
items that are genuinely uncheckable without a macOS — e.g. the
listener same-property re-entrancy claim — are retained).

## Changes per file

**crates/platform-macos/src/macos/coreaudio.rs** (only file changed):

1. `ELEMENT_MAIN: u32 = 1` → `0`, doc now pinned to
   `enum { kAudioObjectPropertyElementMaster = 0 }` with the W08-A02
   F-001 provenance.
2. Six new **private** constants (no public API churn): `ADDRESS_DEVICES`,
   `ADDRESS_DEFAULT_OUTPUT`, `ADDRESS_DEVICE_UID`, `ADDRESS_NAME`,
   `ADDRESS_NOMINAL_SAMPLE_RATE`, `ADDRESS_STREAM_CONFIGURATION_OUTPUT`
   — each `selector + scope + ELEMENT_MAIN`.
3. The 11 former inline `AudioObjectPropertyAddress { … }` literals now
   pass `&ADDRESS_*` (SAFETY comments preserved verbatim at every
   call site):
   `system_device_ids`, `default_output_device_id`, `describe_device`
   (UID + name), `preferred_format`, `output_channels`, `Watch::drop`
   (both removals), `subscribe` (both adds + the rollback removal).
4. Module doc: evidence-status paragraph updated as above.
5. Behavior is otherwise bit-identical — `describe_device`'s
   "no UID → `Ok(None)` skip (never guess)" arm, the listener logic,
   and every bound/teardown invariant are untouched.

**Which queries now use element 0** (the F1.1 critical-path
statement — all 11 call sites):

- `kAudioHardwarePropertyDevices` (system object, global scope): the
  enumeration probe (`system_device_ids`) **and** the devices
  listener add / remove / rollback-removal (`subscribe`, `Watch::drop`).
- `kAudioHardwarePropertyDefaultOutputDevice` (system object, global
  scope): the default-device read (`default_output_device_id`, also
  called from inside `on_property_change`) **and** its listener add /
  remove.
- `kAudioDevicePropertyDeviceUID` and `kAudioObjectPropertyName` and
  `kAudioDevicePropertyNominalSampleRate` (per-device, global scope).
- `kAudioDevicePropertyStreamConfiguration` (per-device, **output**
  scope) — element 0 is the aggregate whole-scope
  `AudioBufferList`, which is exactly what `output_channels` sums.

## Test design

In-module `#[cfg(test)] mod tests` at the bottom of `coreaudio.rs`
(why not a new `tests/fx2_a07_*.rs` integration file, breaking from
the usual preference: the constants and the `AudioObjectPropertyAddress`
type are module-private and macOS-cfg'd — an integration test cannot
see them without pub-ifying ABI internals, i.e. public API churn,
which the DoD prohibits; and no FX2 sibling works in this crate, so
no edit-collision risk). The test module rides the module's own
`cfg(target_os = "macos")`: it **compiles and runs on a macOS host
only**; on Linux the module is not compiled at all, which is precisely
the cfg discipline (below) that keeps the crate compiling on this host
— the wrong-OS lane stays covered from the outside by the existing
`tests/seam_behaviour.rs` (16 tests, host-runnable).

1. `fx2_a07_master_element_is_element_zero` — the audit's exact
   finding as a unit pin: `ELEMENT_MAIN == 0`. Fails on the pre-fix
   file (`1`).
2. `fx2_a07_master_queries_address_element_zero` — every one of the
   six addresses the code builds has `element == 0` (and ==
   `ELEMENT_MAIN`), plus the full (selector, scope) halves pinned
   against `SELECTOR_*`/`SCOPE_*` — so an address can no longer drift
   back onto element 1 or onto the wrong scope silently.
3. `fx2_a07_property_address_abi_pins_the_public_header` — the raw
   numbers behind the addresses: system object `1`, and the eight
   four-char codes as `u32::from_be_bytes(*b"glob"/"outp"/"dev#"/
   "dOut"/"uid "/"name"/"str#"/"nsr ")`. I re-derived all eight
   independently with python3 (8/8 match the file constants; the audit
   verified the same values by arithmetic). A fat-fingered selector now
   fails a test instead of the first HAL call on hardware.

Limitation (honest): the tests pin the constants the code builds; a
future *new* hand-written address literal with a nonzero element would
not be caught (the six `ADDRESS_*` consts are now the only construction
path, and the named-const refactor makes that the path of least
resistance).

## Acceptance vs FIX-PLAN

- **§3 F1.1c** ("CoreAudio `ELEMENT_MAIN=1` vs master=0 property-address
  bug (W08-A02) — fix on the way past for the macOS lane"): fixed
  exactly as scoped; the report above states which queries now use
  element 0 (all 11 — the audit identified zero non-master queries,
  so none were kept on a nonzero element).
- **cfg discipline preserved**: the only file touched sits behind
  `src/macos/mod.rs`'s `#[cfg(target_os = "macos")] pub mod coreaudio;`
  which itself sits behind `src/lib.rs`'s
  `#[cfg(target_os = "macos")] pub mod macos;` — a Linux build never
  compiles this module; `audio_seam()`'s `#[cfg(not(target_os =
  "macos"))]` fallback arm is what answers on this host. No edits
  outside the cfg'd module; the crate's Linux compilation story is
  unchanged (`seam_behaviour.rs` untouched).
- **Lints/DoD**: no `unwrap`/`expect`/`panic!` added (tests are pure
  `assert_eq!`); no new TODO/FIXME/XXX; no `Cargo.toml` or dependency
  edits; no public API change (all new items private consts + a
  private `#[cfg(test)]` module); minimal-diff style preserved
  (SAFETY comments verbatim).
- **Formatting**: rustfmt (pinned toolchain 1.99.1 / rustfmt 1.10.0)
  run on the edited file, idempotent. Note: RULES prescribe
  `--edition 2021`, but the crate is edition 2024 and CI's gate is
  `cargo fmt --all -- --check`, which formats per the crate's edition;
  edition-2021 formatting would have reordered one unrelated
  `use crate::audio::{…}` line, so I formatted at the crate's edition
  to stay fmt-stable under the repo's actual gate.

## Risks & followups

1. **Hardware remains `[VERIFY]`** — no macOS SDK in this sandbox and
   the crate is an orphan (audit F-003, S3: zero workspace dependents),
   so **no CI lane compiles or runs this crate on darwin today**; the
   three `fx2_a07_*` tests execute only when such a lane exists. On
   this host they are compile-absent by design (the assignment's
   "rides the same cfg, runs on macOS CI only" case).
2. **W08-A02 F-002 (S2) NOT fixed** — outside this row's scope: the
   `on_property_change` default-output branch reads the *same* HAL
   property that fired the listener while its inline comment claims
   "a *different* property" (the audit's re-entrancy/deadlock hazard
   plus a false safety comment). Needs its own assignment.
3. F-004 (S4, `describe_device`'s dead `Result` generality) untouched.
4. Tests were not executed by this agent (cargo centrally gated);
   rustfmt's parse of the file is the machine syntax check, the four
   four-char-code pins were re-derived by python3, and the diff is
   mechanical (u32 constants + const-address indirection) — the
   central compile is the type-check oracle. If anything surfaces
   there it will be the test module's import list, which was
   cross-checked item-by-item against its uses.
5. The macOS audio lane (F1.1) still needs the render path itself —
   this file is enumeration/notification only (no AudioUnit/IOProc),
   per the audit's own matrix-row check.
