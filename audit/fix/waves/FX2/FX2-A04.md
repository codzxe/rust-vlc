# FX2-A04 — the three FX1 leftover guards (followups row)

## Approach

Three defects the FX1 wave named in its risk sections and explicitly left
out of scope; each fixed exactly as its audit finding prescribes.

1. **ASF Header Extension child walk** (W04-A10 F-002, S2 — the
   sibling of F-001 which FX1-A07 fixed in the header children walk at
   :562; FX1-A07's risk section recorded this twin "needs its own fix
   item"). Pre-edit `crates/demux/src/asf/header.rs:988-1016`
   (`walk_header_extension`): the bound check computed `off as u64 +
   size` with a plain add (:1002) and the cursor advanced with `off +=
   size as usize` (:1013) — the exact two adds the assignment cites
   (:1002-1013, no drift). A crafted near-u64::MAX ESP-child size
   overflowed the comparison add (debug: panic at the arithmetic;
   release: the wrapped sum slipped past the `> end` guard and the
   wrapped cursor walked backwards — the bounded re-read spin FX1-A07
   described, ≤ MAX_EXTENSION_CHILDREN). Fix: ONE `checked_add`
   (`let Some(child_end) = (off as u64).checked_add(size) else { … }`)
   whose single sum feeds both the bound check and the cursor advance —
   the audit's "checked_add on both" — with overflow minted as the
   typed `error::bad_object_size(0)` refusal, the same constructor the
   function's own `end > payload.len()` arm and FX1-A07's sibling fix
   already use. The let-else + checked_add + typed-error shape is
   copied from the sibling fix's idiom verbatim.
2. **MP4 ctts v1 offset misread** (F-007, S2 — the follow-up FX1-A03
   recorded: "the ctts v1 `i64be` arm is deliberately untouched").
   Pre-edit `crates/demux/src/mp4/mod.rs:1333-1334`: the v1 arm read
   the offset with `i64be(body, 12 + i * 8)` — 8 bytes at the 4-byte
   offset field's position, i.e. the offset OR'd with the NEXT entry's
   sample_count. Per the audit (unambiguous): ctts entries are 8 bytes
   in BOTH versions and §8.6.1.3's v1 only changes the offset's
   signedness (a 4-byte i32) — "What correct looks like: signed i32
   read like the v0 arm." Fix: the v1 arm becomes the v0 lane's own
   4-byte read re-interpreted as i32 (`i64::from(u32be(body, 12 + i *
   8).unwrap_or(0) as i32)`) with a spec-grounded comment. The v0 arm
   is untouched — per ISO 14496-12 v0's field is unsigned u32, but the
   house v0 read is deliberately two's-complement (the in-repo fixtures
   write negative offsets through `as u32`, pinned by the in-crate
   `ctts_shifts_pts_off_dts` suite) and rewriting v0 was not in scope;
   the assignment's fallback (v0 = u32, v1 = i32) was not needed since
   F-007 is explicit. The two arms are now the same expression by spec
   — kept as two branches so each lane carries its own documentation.
3. **The no-panic sweep's false promise** (the audit's ts-mod F-001
   note, quoted by FX1-A02's risk section: the guard test "sweeps a
   64-byte RIFF template only and cannot reach a 188-byte 0x47 window
   — its name is a false promise"). Pre-edit
   `crates/media-probe/src/signature/mod.rs:470-492`: one 64-byte
   RIFF/AVI/moov template with bare fixed-index slicing
   (`template[..4]`, `template[8..12]`, `template[16..20]`). Fix:
   (a) every magic placement goes through a new bounds-checked `place`
   helper — the FX1-A02 guard discipline (phase5's twin: check the
   length before the slice) — so the sweep's own construction cannot
   index-slice unsafely for ANY template length; (b) a second template
   is added, the TS-stride shape (0x47 at [0], second sync at the
   188-byte stride, 189 bytes) — the sweep's comment already claimed
   "two template windows" and now delivers them, so every truncation
   crosses 187/188/189 (the boundary that panicked the probe before
   FX1-A02's guard) and every single-byte mutation bends the stride
   check itself.

Arithmetic oracles were re-derived with python3 before writing
assertions (scratch in /tmp, not committed): the pre-fix v1 misread
produces pts `[1, 8796093025210, -4398046505104, -4398046502104]`
(offset OR next-run bytes, byte-exact replication of the old i64be
read), the fixed ladder `[0, 5048, 4976, 7976]`; the ASF crafted
blobs were modeled end-to-end (builder bytes + splice + fixed walk)
confirming overflow → typed error, overrun/control → unchanged
outcomes.

## Changes per file

1. `crates/demux/src/asf/header.rs` — `walk_header_extension` (now
   :1000-1025): the guard `if size < 24 || off as u64 + size > end as
   u64` + `off += size as usize` pair replaced by the let-else
   `checked_add` + `if size < 24 || child_end > end as u64` +
   `off = child_end as usize`, with a 8-line comment citing W04-A10
   F-002. `child_end` ≤ `end` ≤ `payload.len()` when the guard
   passes, so the usize cast is lossless. Non-overflowing shapes are
   byte-for-byte behaviorally identical (the sum value is the same).
2. `crates/demux/src/mp4/mod.rs` — the ctts v1 arm (now :1333-1341):
   `i64be(body, 12 + i * 8).unwrap_or(0)` →
   `i64::from(u32be(body, 12 + i * 8).unwrap_or(0) as i32)` + a
   spec comment; v0 arm, the FX1-A03 clamp and everything else in the
   arm untouched. `i64be` remains used by the elst arm (:1082).
3. `crates/media-probe/src/signature/mod.rs` — the sweep test (now
   :485-521) rewritten as described above: + `TS_STRIDE` const + the
   bounds-checked `place` helper + the 189-byte TS-stride template;
   the mutation/truncation loops now run over both templates. The
   sweep grows from ~16k to ~65k registry probes (deterministic, all
   bounded anchored scans).
4. `crates/demux/tests/fx2_a04_asf_ext_guards.rs` (new),
   `crates/demux/tests/fx2_a04_mp4_ctts_v1.rs` (new),
   `crates/media-probe/tests/fx2_a04_ts_stride_windows.rs` (new) —
   see below.

## Test design

Three NEW integration-test files (per RULES §DOD-2; no collisions —
FX2-A04 is the only FX2 agent touching these crates), following the
FX1 wave's conventions in each crate (`match`/`unreachable!` error
extraction, `assert!`/`assert_eq!` only, no unwrap/expect; demux uses
its own `test_support` seams and regular deps, media-probe uses
`testkit::Must`):

- **`fx2_a04_asf_ext_guards.rs`** — the builder's
  `minimal_asf_audio` with a Header Extension Object spliced in
  before the Data Object (Header size QWORD, declared child count and
  FPO File Size patched to the grown totals — layout re-verified
  against the builder source byte-for-byte in python); extension
  children are bare 24-byte heads (GUID + size QWORD — the walk is
  capture-and-ignore, the size QWORD is the only live byte):
  - `fx2_a04_asf_extension_child_size_overflow_is_typed_bad_object_size`
    — ESP-child size := `u64::MAX` at the walk's first iteration AND
    mid-walk after one clean advance → both the typed
    `demux.asf.bad-object-size` refusal. Pre-fix: debug builds panic
    at the plain add (the test failing via that panic IS the
    regression proof); release builds wrap.
  - `fx2_a04_asf_extension_overrun_without_overflow_still_walks` —
    size 1000 inside a 24-byte data field: no u64 overflow → the
    pre-existing note-and-break, `start()` still yields the PCM track
    (pins the checked add changed nothing for non-overflowing sizes).
  - `fx2_a04_asf_extension_well_formed_children_still_walk` — control:
    ESP + unknown-GUID children both counted → file still starts,
    one `pcm_s16le` track.
- **`fx2_a04_mp4_ctts_v1.rs`** — a `progressive` 4-sample track (dts
  [0, 3000, 6000, 9000]) with cts [0, 2048, -1024, -1024]:
  - `fx2_a04_ctts_v1_signed_offsets_read_as_i32` — the audit's executed
    ffmpeg ground truth (negctts.mp4: v1 runs `(1, 0), (1, 2048),
    (2, -1024)`) spliced byte-neutral over the builder's own 48-byte
    v0 ctts box → pts `[0, 5048, 4976, 7976]` (dts + signed cts).
    Pre-fix: pts `[1, 8796093025210, -4398046505104,
    -4398046502104]` — the assertion fails deterministically on the
    old code.
  - `fx2_a04_ctts_v0_two_complement_lane_is_unchanged` — v0 control:
    the builder's own v0 box with the same offsets written `as u32`
    reads the identical ladder (holds the v0 side of the equality and
    pins that the fix left v0 untouched).
- **`fx2_a04_ts_stride_windows.rs`** — registry-level (the lane the
  CLI open path runs):
  - `fx2_a04_ts_stride_boundary_lengths_are_typed` — every window
    length 0..=189 of the 0x47-led shape: below the stride →
    `Ok(mpegts)`; at/past it without the second sync → the typed
    `probe.no-demuxer` refusal at stage Probe; completing IS the
    no-panic proof at exactly the lengths the old sweep never reached.
  - `fx2_a04_ts_stride_second_sync_anchors_mpegts` — 189 bytes with
    the second sync at [188]: `mpegts` anchored, 189 bytes examined.
- The hardened in-module sweep itself
  (`builtin_signatures_never_panic_on_arbitrary_windows`) is the
  guard-3 src-side change and now sweeps the stride template at every
  truncation and mutation.

## Risks & followups

1. No compile/test run was possible (RULES: orchestrator gates cargo
   centrally); compile-verified by inspection + the python
   byte-exact oracles. The three test files copy their API usage
   token-for-token from the compile-proven FX1 suites
   (`fx1_a07_asf_child_size.rs`, `fx1_a03_mp4_box_bounds.rs`,
   `fx1_a02_short_ts.rs`).
2. The ASF extension-walk entry add `22 + data_size` (header.rs
   :993) is unchecked — out of the assignment's cited scope; it can
   only overflow on 32-bit usize targets (data_size is a u32), a
   residual worth one line in a later hardening pass.
3. `walk_header_extension` overflow now aborts the whole header parse
   with a typed error where release builds previously damage-noted a
   bounded spin — the deliberate policy (same as FX1-A07's sibling:
   honest refusal over silent recovery); a non-overflowing overrun
   still notes-and-breaks (pinned by the new overrun test).
4. The mp4 v0 ctts lane still reads its u32 offset two's-complement
   rather than ISO 14496-12's unsigned semantics — the house behavior
   the in-crate fixtures pin; noted for the audit's F-014/pts family,
   untouched here.
5. The sweep's cost grew ~4x (~65k bounded registry probes, up from
   ~16k) — still trivially fast, but a future template addition
   should mind the product (positions × 256 values).
