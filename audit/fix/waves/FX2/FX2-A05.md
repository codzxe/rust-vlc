# FX2-A05 — PropVariant 16B vs 24B x64 ABI (FIX-PLAN §3 F1.1b prerequisite)

## Approach

W08-A10 F-001 (S1), confirmed executed by W20-A03's repro
(`audit/scratch/w20a03_propvariant_size.rs`, `rustc -O`:
`size_of::<PropVariant>() = 16`, `align_of = 8`): the crate pins the
PROPVARIANT union at 16 bytes — `header: PropVariantHeader` (2+6+8 =
16) and `raw: [u64; 2]` (16) — while the real x64 ABI is 24 bytes:
an 8-byte vt/reserved header plus a 16-byte payload union (largest
members CAUB/BLOB `{ULONG; ptr}` = 16 on x64). The 16-byte stack slot
is handed by pointer to `IPropertyStore::GetValue` and
`PropVariantClear` (com.rs:381/:297), both entitled to write the full
24 bytes → 8-byte stack under-write class.

**No drift.** The cited lines match the tree exactly (union at
com.rs:237-244 pre-fix, `empty_prop_variant` zeroing `[0, 0]` at
:262-263). The audit's own "what correct looks like" was
"`raw: [u64; 3]` (24 bytes on 64-bit) or a full union mirroring
wtypes.h" — I took the minimal padding fix, which also preserves the
field order the audit recorded (header view `vt`@0, `reserved`@2,
`pointer`@8 unchanged; only the padding member's width changed). The
raw-word pin idiom is house style — dxgi.rs pins `SwapChainDesc` with
`_buffer_desc: [u64; 5]` (read, not edited; FX2-A06 owns it).

## Changes per file

- `crates/platform-windows/src/windows/com.rs` (2 hunks):
  1. `PropVariant::raw: [u64; 2]` → `[u64; 3]`. New layout
     arithmetic (x64): union = max(header 16, raw 24) = **24 bytes,
     align 8** — matches the wtypes.h ABI; `header.pointer` still
     reads offset 8 where `VT_LPWSTR`'s payload lives. Struct doc now
     states the 24-byte x64 ABI and cites W08-A10 F-001.
  2. `empty_prop_variant()` → `PropVariant { raw: [0, 0, 0] }`: zeroes
     all 24 ABI bytes (the audit's per-function table flagged the old
     two-word zero as "zeroes only 16 of 24 ABI bytes").
  - No cfg changes: the type stays inside the existing
    `#[cfg(target_os = "windows")]` module tree (crate discipline
    preserved; Linux workspace check unaffected).
- `crates/platform-windows/tests/fx2_a05_propvariant_size.rs` (new):
  the regression suite described below.

## Test design

The crate has **no existing windows-only test pattern** —
`tests/seam_behaviour.rs` exercises only the host-runnable
non-Windows fallbacks (16 tests, zero of which touch com.rs), and
there is no `#[cfg(test)]` module anywhere in the crate's src. Per the
assignment's fallback instruction, the new integration-test file
carries the type's own cfg gate:

`#![cfg(all(target_os = "windows", target_pointer_width = "64"))]` —
on non-Windows hosts (this Linux box) it builds as an **empty test
target**: compiles green under the workspace check, runs zero tests;
the assertions execute on Windows x64 lanes only (CI's merge-blocking
workflow is ubuntu-only today; the windows matrix lives in the parked
ci-full.yml — noted honestly, same `[VERIFY]` posture as the crate's
own header).

- `fx2_a05_propvariant_matches_the_x64_abi_size_and_alignment`:
  `size_of::<PropVariant>() == 24` and `align_of::<PropVariant>() ==
  8`. **Alignment note:** the assignment said "16-byte alignment
  assertion if the audit evidence specifies it" — the evidence
  (W20-A03 executed repro) specifies **8**, not 16 (the x64 ABI's
  payload members are pointer-wide); the test asserts 8, the value
  the audit recorded and the ABI dictates.
- `fx2_a05_propvariant_header_keeps_the_recorded_field_order`:
  pins the audit's recorded field order — `vt`@0, `reserved`@2,
  `pointer`@8, header size 16 — so the leading-bytes view cannot
  silently drift while the padding evolves.
- No new dev-dependencies (std only; testkit untouched).

## Acceptance vs FIX-PLAN

§3 F1.1b bullet 1: "PropVariant pinned at 16 bytes vs 24 on x64
(`com.rs`, W08-A10; executed `size_of=16`) — stack under-write class."
Fixed as prescribed (the audit's own `raw: [u64; 3]` option).
Not compiled: no cargo/rustc on this box (RULES; also no msvc target
installed — the same posture the crate's own header documents). Both
edited files were parse-checked via the sanctioned rustfmt (exit 0);
the layout claim is plain repr(C) arithmetic re-derivable by `rg
'raw: \[u64'` + inspection, and the 24/8 oracle values are the ones
W20-A03 executed against this exact type shape.

## Risks & followups

- **32-bit lane caveat:** `[u64; 3]` pins 24 bytes on any target, so
  a hypothetical i686-windows build would be over-sized (24 vs the
  16-byte x86 ABI — the *safe* direction for under-write; by-pointer
  usage only). No 32-bit lane exists and the crate never claimed one
  (its compile-verification target is x86_64-pc-windows-msvc). If a
  32-bit lane ever lands, split `raw` with cfg(target_pointer_width)
  arms — deferred, it adds never-compiled cfg machinery today.
- **Sibling findings left for followups (out of my scope, per the
  honesty contract):** W08-A10 F-002 (`ComApartment` auto `Send +
  Sync` breaks the same-thread `CoUninitialize` pairing contract) and
  F-003 (`prop_variant_string` skips `PropVariantClear` on both
  early-return paths → payload leaks). Both sit in the same file and
  bite exactly when F1.1 wires this crate in.
- The Windows-lane execution of the new tests is `[VERIFY]` until the
  parked ci-full.yml windows matrix (or the F1.1 hardware round)
  runs them — the same evidence status the crate itself carries.
