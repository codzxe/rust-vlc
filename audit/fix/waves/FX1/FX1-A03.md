# FX1-A03 — MP4 stts/ctts unclamped entry-count loops (FIX-PLAN §2 F0.4b)

## Approach

The audit's F-003 (S1, `audit/files/crates/demux/src/mp4/mod.rs.audit.md`): the
`stts`/`ctts` walks iterate the raw header `entry_count` (up to 4 294 967 295)
while every sibling table clamps its loop (`stsz:1230`, `stz2:1241`,
`stco:1270`, `co64:1280`, `stsc:1290`, `stss:1303`, `trun:1727` — pre-edit
positions). The field reads are memory-safe (`u32be`/`i64be` return `None` past
the end), so a crafted tiny box with `entry_count = 0xFFFFFFFF` walks ~4.3e9
failing reads — a minutes-scale CPU spin per box, repeatable per trak: a CPU
DoS on open, not memory unsafety.

The fix reuses the sibling `stco`/`stsz` idiom verbatim
(`let take = count.min(<bound>); for i in 0..take { ... } if count > take {
note }`), with the bound the audit prescribes — the entries the box body
actually carries: stts/ctts entries are 8 bytes after the 8-byte
version/flags+count header, so

```rust
let entries = count.min(body.len().saturating_sub(8) / 8);
```

The existing `MAX_SAMPLES` run-expansion ceiling (the pushes inside the loop)
is untouched; the clamp only bounds the walk. The unbacked remainder
(`count - entries`) is damage-noted with the module's existing
`"stts-count-over-ceiling"` / `"ctts-count-over-ceiling"` vocabulary, exactly
like `stco`'s `if count > take` tail.

## Test design

New integration-test file per assignment + RULES §DOD-2 (the crate has both
in-crate `mp4/tests.rs` unit suites and `tests/*.rs` integration suites; FX1-A02
and FX1-A07 in this same crate also added `tests/fx1_*` files, and a new file
avoids collisions with sibling agents). Uses only existing
deps (`demux`, `media-types`, `plugin-api` — the crate's own `[dependencies]`),
the public `demux::mp4::test_support::{mem_stream, progressive}` seam, and the
crate's `assert!`/`assert_eq!` + `unwrap_or_else(|e| unreachable!(...))`
conventions (no `.unwrap()`/`.expect()`, `panic!`, `todo!`).

Fixtures are byte-built raw boxes: a well-formed
`test_support::progressive` file, then the `stts`/`ctts` box is **spliced
in place at equal byte length** (asserted) so the `stco` chunk offsets stay
valid — the only lie in each file is `entry_count = 0xFFFFFFFF`. All expected
values (packet PTS ticks, packet counts, note magnitudes) were first verified
against a byte-exact python replication of the builder + splice + the fixed
parse (scratch: `/tmp/fx1a03/check.py`; all three shapes reproduced
`pts == [0, 3000]`, `[]`, `[2048, 4024, 6000, 9000]` and the exact note
magnitudes before the assertions were written).

- `fx1_a03_stts_entry_count_clamped_to_box_body` — `stts` declares
  0xFFFFFFFF entries over a 24-byte box carrying one (run 2, delta 3000):
  the walk completes with fewer entries (2 of 4 packets, PTS ticks
  `[0, 3000]`) and damage-notes exactly `(4294967294,
  "stts-count-over-ceiling")`. Pre-fix: same packets but **no note** — after
  the ~4.3e9-iteration spin — so the suite fails deterministically on the old
  code.
- `fx1_a03_stts_minimal_box_honors_no_entries` — the audit's minimal crafted
  shape (lying count, inert zero-run entry): zero deltas → zero packets, one
  note, EOS reached. (A literally 12-byte box — body shorter than the
  8-byte version/flags+count header — cannot even read `entry_count`: the
  field read returns `None` → count 0 → the loop is inert pre- and post-fix;
  the discriminating crafted shape is a *readable* lying count, which is what
  these fixtures build.)
- `fx1_a03_ctts_entry_count_clamped_to_box_body` — `ctts` declares
  0xFFFFFFFF entries over a 48-byte box carrying two (1, 2048) and
  (1, 1024): both offsets honored, the remaining samples default to zero
  (`cts.get(si).unwrap_or(0)`), 4 packets with PTS ticks
  `[2048, 4024, 6000, 9000]`, note `(4294967291, "ctts-count-over-ceiling")`.

## Acceptance vs FIX-PLAN

F0.4b acceptance: "stts 12-byte box parse bounded — a truncated stts/ctts box
must parse bounded and either complete with fewer entries or return the
module's existing typed parse error; never panic/OOB." **Satisfied via the
first arm**: the walk is bounded by the entries physically present in the box
body (`(body.len() - 8) / 8` ≤ 2M for the 16 MiB moov ceiling — each
iteration trivial), the parse *completes with fewer entries* (or none) and
damage-notes the unbacked remainder; never panics (the `u32be`/`i64be`
Option accessors remain the memory-safety seam); no typed error was needed.
Well-formed files are behaviorally identical (python control: entries ==
count → no new note). No dependencies, no API churn, minimal diff (+17 lines
in `mod.rs`, all inside the two arms).

  (~15-20 s per box per the audit) runs before the missing-note assertion
  fails — deterministic, but not instantaneous.
- Out of scope, recorded for the next wave: audit F-007 (ctts v1 reads an
  `i64be` spanning into the next entry — the arm my clamp now bounds), plus

  `stsc`/`stss` clamps bound against `MAX_SAMPLES` rather than body bytes;

  flagged by the audit — left as-is (minimal-diff rule).
