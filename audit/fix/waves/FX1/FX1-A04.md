# FX1-A04 — MKV lacing inversion + window-slide livelock (FIX-PLAN §2 F0.4c+d)

## Approach

Two defects, both confirmed-executed by the wave-04/05 audits:

1. **Lacing inversion (F0.4c, cluster.rs audit F-001, S1).** All three
   lacing codings read the count byte as the literal frame count;
   Matroska §6.3.6 defines it as **frames − 1** (ffmpeg — this repo's
   designated oracle, executed live in the mkv suites — implements
   `laces = *data++ + 1`). Fixed at the three count bindings
   (pre-edit lines 258 Fixed / 287 Xiph / 320 EBML — line 258 matches
   the citation, no drift). The Xiph/EBML coded-size loops
   (`0..frame_count−1`, first-vint + `2..frame_count` deltas) then read
   exactly the spec's `count` coded sizes with no further change. Two
   consequences handled in lockstep: the now-dead `frame_count == 0`
   guards were removed (count 0 is *legal* input under +1 — the
   degenerate one-frame lace), and the EBML path needed a 3-line
   degenerate early-return, because its first-size vint parse is
   unconditional: for a count byte 0 it would otherwise consume
   payload bytes as a "size" and emit two frames for a one-frame lace.
   With the early return all three codings agree on the degenerate byte
   — resolving cluster.rs audit F-004, which noted the codings disagreed.

2. **Window-slide livelock (F0.4d, mod.rs audit F-001, S1 — executed:
   watchdog kill, exit 124).** `next_block_packets` slides its bounded
   window two ways and **both** could re-issue an identical read
   forever: (a) the block-cover slide (cited 644-663, pre-edit 647-663
   — no drift) re-reads `[cursor, cursor+4 MiB)` when the block spans
   past the window; a block with span in (4 MiB, 32 MiB] — a range the
   demuxer's own gate accepts — never fits, so the loop spins; (b) the
   cursor-advance slide (599-615) on a stream that ends inside the
   cluster's declared extent gets a **zero-byte** window and re-issues
   the same read forever. Both now carry the missing progress
   condition: if the slide's read cannot advance the walk (empty, or
   still not covering `data_end`), the loop breaks with the module's
   typed `error::truncated` instead of spinning. The guards `break`
   *before* re-assigning the window, so the documented restore-on-every-
   exit contract (the `next_event` recovery arm reads
   `window.end`/`window.cursor`) is preserved verbatim; the error then
   flows through `next_event`'s existing classification — `Truncated` +
   `reader.length() ≤ segment_end` surfaces the typed error to the
   caller, otherwise the contained-lie `Recovered` skip advances the
   walk. No public API change, no new error kinds.

## Changes per file

1. `crates/demux/src/mkv/cluster.rs` — `frame_count = count as usize`
   → `+ 1` at the three codings; removed the three now-dead
   `frame_count == 0` guards (lace_frames' Xiph/EBML arms, ebml_sizes');
   added the EBML one-frame-lace early return `Ok((1, 1))` with no coded
   sizes; doc comments updated to the frames−1 semantics. Three unit
   tests flipped (see Test design).
2. `crates/demux/src/mkv/mod.rs` — two guards in `next_block_packets`:
   slide 1 (empty read) → `error::truncated(window.end, from)`; slide 2
   (slid window still cannot cover `data_end`) →
   `error::truncated(data_end, from + data.len())`. ~14 LOC added,
   nothing else touched.
3. `crates/demux/tests/mkv_fixtures.rs` — `laced_fixture()`'s three lace
   heads flipped 3→2 (Xiph/EBML/Fixed), with comments stating the
   frames−1 rule. The audit flagged this fixture as spec-invalid under
   the old convention (its open item #1 demanded the lockstep fix); the
   two integration tests that consume it keep their expectations
   unchanged (see Test design).
4. `crates/demux/tests/fx1_a04_mkv_lacing_window.rs` (new) — the
   regression pins, per assignment.

## Test design

**The 3 pinned tests flipped (cluster.rs, the audit §5 "INVERTED" set).
The flip is exactly one byte per test — the lace head becomes
frames−1 — while every frame-count/size expectation stays identical.
That is the +1 pin in its purest form: the old code on the new bodies
yields one frame fewer (or refuses), so each flipped test fails on the
pre-fix code and passes on the fix:**

- `xiph_lacing_splits_and_remainder_last`: head `3` → `2`; still
  expects 3 frames [5, 300, 160]. Under the old code head 2 meant
  frame_count 2 → 1 coded size → 2 frames (the "HELLO WORLD!"-class
  mis-split the audit executed: last "frame" swallows the rest).
- `fixed_lacing_divides_exactly`: head `4` → `3`; still expects four
  equal 2-byte frames over 8 payload bytes. Old code on head 3: 8 % 3
  ≠ 0 → the body was *refused* (the audit's "spec-degenerate" note).
- `ebml_lacing_sizes_decode`: head `3` → `2`; still expects 3 frames
  [3, 3, 2]. Old code on head 2: 2 frames [3, 5].

**mkv_fixtures.rs `laced_fixture` (the second in-tree layer the audit
said pins the inversion): the three lace heads flip 3→2 with the frame
expectations untouched — `hand_built_laced_fixture_decodes_all_three_codings`
(9 packets, 9 keyframes, damage 0) and `laced_frame_payloads_are_byte_exact`
(the 9 byte-exact payloads) are now the integration oracle of the flip.
The semantics-agnostic tests in the file were hand-traced: the
overrun/remainder refusals and the mid-file `truncated_cluster` cut
still hit the same typed paths (the cut is caught by the pre-existing
`data_end > window.end` gate at 639, before any slide). The ffmpeg
differential lanes are unaffected: all corpus/fixtures SimpleBlocks
carry lacing bits `00` (the audit measured this). `mkv_extras_wiring`'s
malformed Xiph head `[2, 200]` still overruns under +1 (typed refusal,
same recovery count). `mkv/fuzz.rs` generates no laced blocks (rg
verified). No other crate pins the convention (rg over apps/, tools/,
crates/).

**New file `tests/fx1_a04_mkv_lacing_window.rs`** (integration style —
a NEW file per RULES, avoiding edit collisions; only existing
dev-deps: demux, plugin_api, media_types, testkit):

- `fx1_a04_lacing_count_byte_is_frames_minus_one` — the required
  lacing pin: one crafted SimpleBlock payload per coding through the
  public `demux::mkv::cluster::parse_block`, asserting count byte 2 →
  3 frames with exact lens AND frame starts (the starts pin that two
  coded sizes were consumed — one fewer under the inversion), fixed
  head 3 → 4 frames, EBML head 2 → 3 frames, plus the degenerate
  count-byte-0 lace where all three codings must agree (1 frame, the
  whole body past the head — the new EBML early return's pin).
- `fx1_a04_window_slide_oversize_block_terminates_typed` — the
  audit's executed livelock shape: a ~4.26 MiB SimpleBlock (span >
  4 MiB window, « 32 MiB gate) in an otherwise complete hand-built
  file. Pre-fix: the slide re-issued the identical 4 MiB read forever
  (exit 124). Post-fix: the first `next_event` terminates with the
  module's typed `demux.mkv.truncated`.
- `fx1_a04_window_slide_truncated_cluster_terminates_typed` — the
  required truncated-cluster-stream pin: cluster/segment declare a
  1 KiB ghost tail the stream never delivers (a test-local
  `SourceStream` whose `size()` over-reports — the truncated-after-open
  shape; with an honest stream the `segment_end` clamp makes this shape
  unreachable and the walk ends cleanly, so the lying size is the only
  honest way to craft it). The real block demuxes first, then the
  cursor-advance slide at the real end terminates typed.

The window tests run the walk on a watchdog thread
(`thread::Builder` + `mpsc::recv_timeout(30 s)` — the packet-queue
suites' exact pattern) because the pre-fix failure mode is a hang
*inside one `next_event` call*: a regression fails the test crisply at
the timeout instead of stalling the central run. No `.unwrap()`/
`.expect()`; `assert!`/`assert_eq!`/`unreachable!` per the neighbouring
suites. `rustfmt --edition 2024` (toolchain 1.99.1) ran clean on all
four changed files.

## Acceptance vs FIX-PLAN

- **F0.4c** "MKV lacing inversion `frame_count = body[0] as usize` →
  `+1` and fix the 3 tests that pin the bug": DONE — the +1 landed at
  all three codings (the audit located 258/287/320, not just 258), the
  3 INVERTED unit tests flipped, and the `laced_fixture` lockstep the
  audit's open item #1 demanded (a partial fix would have turned the
  fixture suite red). The +1 semantics are pinned end-to-end by
  `fx1_a04_lacing_count_byte_is_frames_minus_one` (unit seam) and the
  two existing fixture tests (demuxer seam, 9 byte-exact packets).
- **F0.4d** "MKV window-slide livelock exit condition": DONE — both
  slide sites terminate with the module's typed error (`demux.mkv.truncated`,
  stage Demux, kind Corrupt::Truncated), pinned by the two window tests;
  the stall and the oversize-block shapes both convert from infinite
  spin (100 % CPU, no event, no EOS, no error) to typed termination.
- No dependencies added; no public API churn; workspace lints obeyed
  (no unwrap/expect/panic in src; `unsafe_code` untouched; no
  TODO/FIXME markers left).

## Risks & followups

- **A legal block with span in (4 MiB, 32 MiB] now refuses typed
  instead of parsing.** The audit's preferred full fix is to *grow the
  window to cover the block* (the pool read is already positional); the
  assignment scoped the minimal exit/progress condition, so the
  trade-off is hang → typed refusal. Real files with >4 MiB blocks
  (large intra frames, laced high-rate audio) stop with
  `demux.mkv.truncated` rather than demuxing — recorded as follow-up
  work (F1 material, small: cap the slid window at
  `min(block span, MAX_BLOCK_BYTES)`).
- The machine-local corpus differential lane (`tests/mkv_corpus.rs`)
  could not be re-run in this sandbox. If corpus-v4 contains any
  mkvmerge-authored laced MKV, its recorded packet counts encoded the
  inverted demuxer and will now disagree — the demuxer now agrees with
  ffprobe (the corpus's own oracle), so those recordings need
  re-derivation, not the code.
- `cargo test`/`check` could not be run (per RULES — the orchestrator
  gates centrally). The changes are compile-verified by inspection
  plus a clean `rustfmt --edition 2024` parse of all four files; the
  three tests were hand-traced byte-by-byte against the demuxer's walk
  (window bounds, slide arithmetic, `next_event`'s truncation
  classification) — flagged as the residual risk.
- On a livelock regression the watchdog test fails at 30 s but the
  walker thread spins until process exit (same accepted trade as the
  packet-queue timeout tests). The oversize test transiently allocates
  ~5 MiB and one 4 MiB window read — bounded and freed per test.
- Not in scope, unchanged: cluster.rs F-002 (BlockGroup keyframe
  derivation), F-003/F-006 (timecode `as i64` wrap, 32-bit sums),
  mod.rs F-004 (16 MiB frame drop vs the documented 32 MiB spill —
  note it now interacts with the >4 MiB refusal), F-005–F-008.
