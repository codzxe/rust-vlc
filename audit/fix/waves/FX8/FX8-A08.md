## The normalizer duplicate-key fix (the issue DID exist)

Two defects in one function, both now fixed:

1. **Duplicate keys produced** — the old normalizer rewrote BOTH per-run
   label lines to the same placeholder key
   (`"normalized": "per-run",`), so every normalized transcript carried
   a `labels` object with **two identical keys** — visible verbatim in
   the baseline's own failure diff at
   `audit/runs/baseline/cargo-test-workspace.txt:2775-2776`
   (`"labels": { "normalized": "per-run", "normalized": "per-run",
   "hardware_class": "mock", ...`). RFC 8259 §4 names SHOULD be unique;
   a JSON reader collapses the two entries into one.
2. **Distinct keys collapsed (drift masking)** — the rewrite was
   depth-blind: ANY line starting `"os":` or `"environment_kind":`
   ANYWHERE in a transcript was normalized, so a same-named payload
   field that drifted would normalize away on both sides of the compare
   and the currency gate would pass real drift. This is the audit's
   F-004 (`harness.rs.audit.md` §3: "a future transcript field with the
   same name would be silently normalized").

The fix: rewriting is scoped to the transcript's `labels` object (enter
on `"labels": {`, leave on the next brace-only line — the emitter's
fixed shape), and it is **value-only**: the keys `environment_kind` /
`os` stay distinct, and the line's own tail (`,` / final newline /
nothing) is preserved. `fx8_a08_*` unit tests cover: distinct keys +
byte-identical cross-machine currency property; same-named payload keys
NOT normalized (a payload `os` drift stays visible — `assert_ne!`);
last-field/no-comma and unterminated tails; pass-through without a
labels block. Verified without cargo by a python3 line-for-line
simulation of the algorithm against the real `open.json`: the old form
reproduces the baseline's duplicate-key output, the new form does not,
the currency property holds, and a tampered `request_id` outside labels
still compares unequal.

## The refresh procedure

`scripts/quality/refresh_transcripts.sh` (exit 0 green / 1 the mode's
gate failed / 2 usage):

- **Writer (default / `--write`)** — `cargo build -p lumen-cli` (the
  wire-session scenario spawns `target/debug/lumen`) → **pre-flight**:
  `cargo test -p first-vertical --no-fail-fast --lib --test
  baselines_consistency --test class_b --test journey --test
  recovery_matrix --test wire_mode` — all green or REFUSE (evidence only
  commits green runs). The artifact-currency binary `tests/evidence.rs`
  is deliberately not in the pre-flight: its checks describe exactly
  what the writer re-renders (gating on them would deadlock the refresh
  — stale artifacts blocking their own regeneration); the full package
  is re-run post-flight instead → **regen**: `cargo test -p
  first-vertical --no-fail-fast --test evidence -- --ignored regen`
  (the package's own writer, which itself re-runs every scenario and
  refuses on any red check) → **post-flight**: `cargo test -p
  first-vertical --no-fail-fast` (currency checks included) — green, or
  the run reports red and does NOT retire the sidecar → on a green
  post-flight only, the writer **retires the STALE-TRANSCRIPTS.md
  sidecar** (its claim would stop being true).
- **`--check` (the gate)** — read-only (never writes `evidence/`; the
  package's own design). Exit 1 **if the STALE sidecar is present**
  (before any cargo — fail fast on the declared staleness), else build
  `lumen-cli` + `cargo test -p first-vertical --no-fail-fast --test
  evidence` (the three currency checks; the ignored `regen` never runs):
  1 on drift, 0 current.
- **`--inventory` (no cargo at all)** — python3-stdlib audit of the
  committed artifacts: the suite's `SCENARIO_IDS` parsed from
  `src/scenarios.rs` (12 ids) == the ledger's scenario_table ids (all
  verdicts `pass`) == the `transcripts/` file set (exactly 12, no
  extras); every transcript parses with `schema "transcript/1"`,
  `scenario` == its file stem, `hardware_class "mock"` + the
  null-audio/software-render pair + producing-machine labels;
  `final-frame.png` PNG signature + IHDR 320x240; the ledger's
  `sha256`/`bytes` claims re-derived from the actual 13 artifact files;
  the `2.E1-first-vertical.txt` record present and non-empty; the stale
  sidecar's presence reported either way.
