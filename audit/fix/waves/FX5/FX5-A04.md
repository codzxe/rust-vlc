# FX5-A04 — the CLI-level MP4 seek acceptance oracle (FIX-PLAN §3 F1.3's acceptance line, wave-FX5.tsv row FX5-A04)

## Approach

The acceptance to make executable: "`seek 1s` on sample.mp4 →
`TimingSeekCompleted`, position ~1.0 s, playback continues." The
executed defect my tests must flip is precise and recorded (wave-05
S0; W20-A02 F-1; W20-A05 F-001; REMEDIATION-MAP; MP4-REALITY-TRACE):
`seek 1s` → `TimingSeekFailed { "[demux] unsupported
(plugin.demux.reanchor.unsupported)", position_us: 0 }`, every MP4
seek, while MediaInfo said `seekable: true` — and the WAV contrast
completed `TimingSeekCompleted(1000000)`.

I coded to the CONTRACT exactly as `native_seek.rs` models completed
seeks (the assignment's instruction): the in-process
`CliHost`/`lumen_dispatch` harness (open → settle → wire seek →
assert the terminal, the clock, the epoch, then `advance` to the
end), over the committed class-A fixture — the same lane
`container_conformance.rs` already pins through the binary. The media
choice followed native_seek's exact method: **committed fixture, not
in-test generation** — `tests/fixtures/generated/valid/
mp4_mjpeg_pcm.mp4`, the AVI parent's exact twin (MJPEG+PCM, 2.000 s,
320x240 @ 30 fps, stereo s16le 44.1 kHz, stss 1..60 all-sync — the
landing granularity is the 33.333 ms frame grid; its expectations
toml commits the seek oracle `[seek] tolerance_us = 33_333`). The
WAV guard uses the committed `wav_pcm_s16le_44k1_st.wav` (0.200 s —
no 2 s WAV fixture is committed in-tree; the corpus WAVs ttf_seek
measures live outside the repo and no-op without `LUMEN_CORPUS`), so
the guard scales the same protocol to its half (a 50 % seek).

**The tolerance model** (per the assignment's pointer to
`avi/tests.rs:2695`): the landing is the keyframe-safe position
at/below the target — for a frame-aligned 1 s target on an all-sync
30 fps grid that is exactly 1.000 s; I assert the committed ±33 333 µs
window (one frame) rather than native_seek's exact-equality pin, a
deliberate robustness trade against one-frame implementation
variance in the reanchor's per-track cursor model. End-of-media
positions are exact pins (2 000 000 / 200 000 µs) — the same values
`container_conformance.rs` pins through the binary for these exact
fixtures ("ok: time 2.000000s (100.0%)" / "0.200000s").

**The one drift found, and how test 3 honors it honestly:** the
assignment's premise — "beyond-duration target → the engine's typed
refusal" — matches the demuxer-level AVI reanchor test
(`reanchor_at_end_lands_last_and_past_end_is_typed`), but NOT the
wire-level engine behavior on known-duration media: `resolve_target`
(playback-engine/seek.rs:273) clamps absolute/relative/percent
targets to the known duration (doc 05 §2.4, and the CLI's own usage
line in parse.rs: "the host clamps against the duration — clamping is
truth, not failure"), so a 9 s target on a 2.000 s media reaches the
demuxer as exactly 2.000 s — in-range for the landed extent check —
and completes at the last keyframe. Writing a "must refuse typed"
assertion for that input would contradict the documented contract and
fail the central run. Test 3 therefore pins the F0.4 discipline's
actual content on BOTH halves: the beyond-duration target's honest
clamp-completion (typed, no panic, lands at the end, never at the 9 s
request) and the genuinely-typed impossible seek — the same target
fired from `Ended`, the state table's refusal
(native_seek's `seek_from_ended_refuses_typed_at_the_old_position`
model verbatim: Stage::Session, "seek in Ended", position stands,
session survives, no terminal fabricated).

**FX5-A01 visibility (the assignment's required note):** at my first
read `fn reanchor` was ABSENT from `crates/demux/src/mp4/mod.rs` (rg
0 hits — the pre-landing state the audit recorded); by my finish it
had LANDED in the tree (mod.rs:2086 `reanchor` + `reanchor_progressiv
e`:2228 + `reanchor_fragment`:2294 — FX5-A01's same-wave edit). I
re-derived every asserted landing against the landed
`progressive_landings` math: the 1 s target → video sample 30 (pts
exactly 30 ticks @ 1/30 = 1.000 s), audio sample 30 (pts exactly
44 100 ticks @ 1/44 100 = 1.000 s) → the engine's audio-anchor
completion reports exactly 1 000 000 µs; the 0 target → sample 0 both
tracks → 0 µs; the clamped 2.000 s target → video sample 59
(1.966 7 s, audio cursor at end-of-track — the provably-never-delivers
pre-roll limb, whose completion anchors on the landing) → inside
test 3's [1 900 000, 2 000 000] window. The tests were written before
the landing was visible and are unchanged by it — the contract held.

## Test design

1. `fx5_a04_seek_1s_on_mp4_completes_and_lands_near_1s` — THE
   acceptance: open the MP4, settle, `advance(1)` (play briefly: one
   full pump renders the parked pre-roll — position > 0, session
   Playing), then `seek 1s` (Absolute). Asserts: exactly ONE
   `TimingSeekCompleted` and ZERO `TimingSeekFailed` (the executed
   F-001 shape's both halves); the terminal's position within
   1 000 000 ± 33 333 µs (the fixture's committed frame-grid oracle);
   the clock re-anchored in the same window; the session epoch
   survives under the seek's minted generation (same session id,
   `Idle → Opening` ×1, teardown edges ×0 — the D-4/D-7 no-reopen
   proof); state back to `Playing` after the in-pipeline rebuffer
   (settle); `advance(RUN_PUMPS)` → `Ended` at exactly 2 000 000 µs
   (the binary lane's own pin for this fixture); and the boundary's
   health counters (`headless_accounting`: frames/video refused = 0).
2. `fx5_a04_seek_on_mp4_repeats_and_composes` — the AVI
   double-reanchor/storm model: `seek 1s` → `seek 0` → `seek 50%`
   back-to-back through the wire. One terminal per seek (doc 05 §4.3
   invariant 4) at each actual landing (~1.000 s, ~0, ~1.000 s — the
   ±33 333 µs windows); generation before + 3 (each seek mints);
   epoch survives the whole storm; the clock at the LAST landing;
   the remainder plays to the exact 2 000 000 µs end.
3. `fx5_a04_seek_out_of_range_on_mp4_refuses_typed` — the F0.4
   discipline: a crafted beyond-duration target (9 s on 2.000 s,
   4.5× over) from `Playing` answers the doc 05 §2.4 clamp truth —
   one completion in the end-of-media window [1 900 000, 2 000 000]
   µs, never at the request, zero fabricated failures, epoch intact,
   media ending honestly (`Ended`, position ≥ 1 900 000 µs); then the
   same target from `Ended` is the state table's TYPED refusal —
   Stage::Session, "seek in Ended", the old position standing, the
   session surviving, no terminal fabricated.
4. `fx5_a04_seek_on_wav_reference_container_lands_within_tolerance`
   — the one cross-container guard (the reference implementation, not
   a re-proof): open the committed 0.200 s PCM fixture, settle, one
   50 % seek → one completion inside the requested half's ±10 %
   (the ttf-seek recorded Lands-class window; the frame-exact PCM
   reanchor actually lands 100 000 µs exactly), epoch survives,
   remainder to the exact 200 000 µs end.

## Risks & followups

1. **I could not execute the tests** (RULES.md forbids cargo test) —
   every asserted value is derived from the landed code paths
   (`progressive_landings`, `complete_seek`'s audio anchor,
   `resolve_target`, `seek_preroll`) and the recorded binary-lane pins
   on the same fixtures; the orchestrator's central run is the oracle.
   The least-derivable assertions are the mid-stream `Playing` state
   after the rebuffer settle and the `headless_accounting` zero-refusal
   counters on the MP4 lane (both the AVI twin's in-tree precedents).
2. **The ±33 333 µs neighborhood vs native_seek's exact-equality
   pins** is a robustness trade: the frame-aligned 1 s target lands
   exactly 1 000 000 µs on the landed math (both tracks' sample 30),
   so a future tightening to exact equality is a one-line change if
   the orchestrator prefers the stricter form.
3. **Test 3's clamp half depends on the duration being known** (track
   span ends): true for this fixture; a duration-less fragmented MP4
   would take a different out-of-range path (`demux.mp4.seek.out-of-
   range` straight from the demuxer) — that lane is FX5-A01's own
   crate tests' territory, not the CLI lane's.
4. The WAV guard intentionally uses the 0.200 s committed fixture
   (scaled 50 % target) because no ≥1 s WAV fixture is committed
   in-tree; if a longer WAV lands later, the guard can be re-pointed
   at a 1 s target without changing its shape.
