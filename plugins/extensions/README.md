# plugins/extensions — the example extensions (card 7.G1, issue #46)

Two real, loadable example extensions — one per extension archetype
doc 06 §2.3 (c)/(d) sketches — plus the generator that builds their
`plugin.wasm` modules deterministically. Everything in this walkthrough
was executed from the repository root on this tree; every output block
below is real command output, not illustrative.

| Directory | id | kind | capabilities | permissions |
|---|---|---|---|---|
| `metadata-provider/` | `ext.example.metadata` | `metadata-provider` | `provides = ["tags"]` | `fs-sandboxed-read` |
| `ui-panel/` | `ext.example.panel` | `ui-panel` | `surfaces = ["side-panel"]` | `ui-surface` |

Each directory holds exactly two source files:

- `manifest.toml` — the doc 06 §2.2 identity. Its `[provenance] hash`
  ships the **placeholder form** `sha256:…(64 hex)`; packaging stamps
  the real digest of the module it ships with (one implementation:
  `stamp_manifest_hash` in `crates/plugin-host-wasm/src/package.rs`).
- `plugin.wasm` — the guest module, **committed and pinned**: it is
  regenerated byte-for-byte by `lumenext-examples`, and the drift gate
  (below) fails CI if a committed blob diverges.

## Why a generator instead of Rust→wasm

The modules are emitted by `crates/plugin-host-wasm/src/bin/lumenext-examples.rs`
using the same public-spec wasm-binary emitter pattern the crate's
integration suites use (`tests/common/mod.rs`): hand-encoded
sections, LEB128, imports, data segments — std-only, no
`wat`/`wasm-tools`/`wasm32-unknown-unknown` toolchain dependency
(AGENTS.md §3.2: wasmi is the only pre-approved engine dep; nothing
else enters the build). The trade-off is honest: the examples are
written in emitter calls, not Rust source, because shipping a
Rust-compiled module would add a guest toolchain the dependency policy
has not ratified `[PROPOSAL — guest SDK, doc 06 §5.2]`.

Regeneration is deterministic — same input, same bytes, so the
committed blob can be diffed against regeneration:

```console
$ cargo run -q -p plugin-host-wasm --bin lumenext-examples -- "$(pwd)"
lumenext-examples: all modules already up to date

$ cargo run -q -p plugin-host-wasm --bin lumenext-examples -- --check "$(pwd)"
lumenext-examples: all committed modules match regeneration
```

(On a fresh checkout the first command writes both modules; `--check`
never writes and exits 1 on drift — it is run as a test, below.)

## The two protocols the examples speak

**metadata-provider (doc 06 §5.2, the command layer).** The engine
issues `extract(path_ptr, path_len)`; the guest `fs_open`s the media
sidecar *inside its jail*, `fs_read`s up to 4 KiB into its result
buffer, `fs_close`s, and returns the last import status. The host then
reads the length (u32 at guest offset 2052) and the tag text (at guest
offset 4096) out of the guest's linear memory — the no-host-pointers
model in both directions: request payloads are written *into the
guest's memory* by the host, results read back out of it.

Guest memory layout (the generator is the single source; the
conformance test mirrors these addresses):

| Offset | What lives there |
|---|---|
| 0 | the self-reported manifest (`init` hands it to `report_manifest`) |
| 1024 | the ready log line |
| 2048 | `fs_open`'s handle out-param / the panel descriptor (panel example) |
| 2052 | `fs_read`'s length out-param (u32 LE) |
| 4096 | `fs_read`'s result buffer / extract reads land here |
| 8192+ | free area — where the host writes request payloads |

**ui-panel (doc 06 §5.8).** `init` registers one declarative panel
descriptor through `lumen:v1.ui::ui_register_panel`; the host surfaces
it as a `PanelRecord`. Events arrive as `on_command(cmd_ptr, cmd_len)`
— payloads the host wrote into guest memory — and the guest
acknowledges them through `lumen:v1.log` (the observable v1 seam).
Panels exchange data through the command layer only; the descriptor is
a JSON object (`{"panel_id","title_key","surface"}`) the host
interprets.

## Walkthrough: build → package → inspect → install → verify

All commands run from the repository root, after
`source scripts/cargo-env.sh` in this sandbox.

### 1. Build (regenerate the modules)

```console
$ cargo run -q -p plugin-host-wasm --bin lumenext-examples -- "$(pwd)"
lumenext-examples: all modules already up to date
```

### 2. Package into `.lumenext`

`lumenext package` reads the example's `manifest.toml` + `plugin.wasm`,
stamps the manifest's provenance hash with the module's real sha256,
and writes the stored-entry ZIP (the format `read_package`/install
consume). The `.lumenext` lands next to the sources by default and is
gitignored:

```console
$ cargo run -q -p plugin-host-wasm --bin lumenext -- package plugins/extensions/metadata-provider
lumenext: packaged ext.example.metadata v0.1.0 (kind metadata-provider, api v1)
  module : plugins/extensions/metadata-provider/plugin.wasm (764 bytes)
  digest : sha256:ed7ec5bef684d20f36d0e0bb95ede58feb0caecd8c0777071cac6f6eea39ce82
  output : plugins/extensions/metadata-provider/ext.example.metadata-0.1.0.lumenext

$ cargo run -q -p plugin-host-wasm --bin lumenext -- package plugins/extensions/ui-panel
lumenext: packaged ext.example.panel v0.1.0 (kind ui-panel, api v1)
  module : plugins/extensions/ui-panel/plugin.wasm (764 bytes)

  output : plugins/extensions/ui-panel/ext.example.panel-0.1.0.lumenext
```

### 3. Inspect (the structural chain, no execution)

### 4. Install + run (the conformance kit)

`lumenext` deliberately never installs and never executes guest code —
install is the app's user-consented flow (doc 06 §5.7). The automated
equivalent is the conformance kit,
`crates/plugin-host-wasm/tests/plugin_examples_conformance.rs`, which
for each example: packages it through the same library stamping path,
installs it into a real `ExtensionStore` with an `InstallConsent`
matching the preview, loads it (re-validated end to end, digest
included), spawns it under the production `ResourceLimits::for_kind`
ceilings, and drives the protocol above — including the capability-
honesty assertions (`provides = ["tags"]` is only true because
`extract` really returns the sidecar's tag text), the typed `E_PERM`
error paths for missing/traversing paths, and the api-window refusal.

```console
$ cargo test -p plugin-host-wasm --test plugin_examples_conformance
running 5 tests
test committed_example_modules_match_regeneration ... ok
test lumenext_cli_round_trip_packages_and_inspects_both_examples ... ok
test examples_refuse_future_api_major_with_the_typed_error ... ok
test metadata_provider_example_passes_conformance ... ok
test ui_panel_example_passes_conformance ... ok

test result: ok. 5 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.01s
```

### 5. Cleanup

```console
$ rm plugins/extensions/*/ext.example.*-0.1.0.lumenext
```

(The artifacts are gitignored; removing them keeps the tree pristine.
`git status` is clean with them present too.)

## Writing your own extension

1. Create `plugins/extensions/<your-name>/` with a `manifest.toml`
   (start from either example: doc 06 §2.2 rules — id, kind, version,
   `api_version = 1`, `origin = "extension"`, kind-correct
   `[capabilities]`, deny-by-default `[permissions]`, `[provenance]`
   with the placeholder hash) and your module.
2. Build the module however your toolchain allows **without adding
   repository dependencies** — the in-tree path is extending the
   emitter in `lumenext-examples.rs`; whatever emits the bytes, only
   the committed blob + manifest are the artifact.
3. The module must export the entry points its kind implies and speak
   only the `lumen:v1.*` imports its permissions grant (undeclared
   imports refuse instantiation — that is the §2.2 escalation fence).
   `init` must return the negotiated api major after
   `report_manifest`-ing its own installed identity.
4. Package with `lumenext package`, inspect with `lumenext inspect`,
   and drive it through a conformance test like
   `plugin_examples_conformance.rs` — a manifest claim you cannot
   demonstrate is a manifest lie (doc 06 §7.2) and the kit must fail
   it.

## Honest limitations

- **Unsigned.** v1 ships no signature verifier (no crypto dep);
  packages report `Unsigned`/`Unverified` honestly. The signature
  block format and statuses exist; enforcement is a Lead-approved
  crypto ADR away (doc 06 §10 Q5).
- **No guest SDK.** The examples are emitter-built, not
  Rust-compiled; a real guest toolchain (`wasm32-unknown-unknown` +
  bindings) is `[PROPOSAL]` pending dependency approval.
- **Fuzz targets.** Doc 06 §7.7 requires cargo-fuzz registration for
  *parser* plugins. Neither example parses a bitstream **in-guest** —
  the metadata example moves bytes (the tag *interpretation* happens
  host-side in the command layer), and the panel registers a
  descriptor — so neither owes a `fuzz/<kind-short>_<capability>`
  entry. A real metadata provider that parses tag formats inside the
  guest does owe one.
- **The panel surface is declarative-only in v1**: the host records
  `PanelRecord`s and dispatches `on_command`; actual UI composition
  into the layout system is the app-side card.
- **The metadata example reads sidecar text** (a `.tags` file next to
  the media). It does not parse embedded ID3/Vorbis containers — that
  is the builtin `media-probe` crate's job (L2); the example shows the
  *extension protocol*, not a tag-format implementation.
