## Special-attention rulings (asked by the Lead)

1. **The trap-wrap assertion (lead-pre-g fix) — REAL semantics, not theater.
   Independently verified live.** a11y.spec.ts:144-167 encodes "a wrap is
   legal ONLY as a jump back to the trapped container's first focusable (the
   lowest DOM index recorded)". I reproduced the underlying behavior on
   /settings/global with a DOM-index instrument: the settings window
   focus-on-open puts focus at tabbable idx 21 ("Search settings"); Tab walks
   21→61 monotonically; at the last focusable (61, "Advanced Options") Tab
   wraps to **exactly 21** — `firstDomIndex = Math.min(...)` over the recorded
   stops = 21, so the assertion pins the trap's first-focusable landing, not a
   tautology. This matches the shared `Surface` trap primitive (DOM-order
   first focusable, per j04/j09) and i17's dialog drive-verification. The
   assertion is genuinely encoding the trap contract. Two honesty caveats
   remain: (a) it validates only the FIRST wrap then `break`s (fine for
   current single-trap routes, would silently stop auditing after a
   mid-document wrap), and (b) the dialogs whose traps it was written for
   (netstream/shortcuts, i17) are not in ROUTES — the assertion is exercised
   only via settings-global (i17's log says so honestly).
2. **Seeded-gate test patterns (lumen.onboarding.v1 shapes) — honest.** The
   e2e seed (a11y.spec.ts:44-53, smoke.spec.ts:16-24) is byte-for-byte the
   shape `completeOnboarding()` persists (onboardingState.ts:132-135:
   `{complete:true, choices:{telemetry,updateChecks,onlineSuggestions}}`), and
   the store's hydrate folds corrupt/absent stores to a fresh run
   (onboardingState.ts:87-99, `loaded.complete === true` — a seeded literal
   `true` folds to the wizard, exactly what i20 verified). App.test.tsx:61-105
   walks 13 fresh-run routes + `/onboarding` + `/dev/tokens`; :141-161 pins the
   `?onboarding=1` bypass semantics (per-navigation, writes nothing, next
   param-less nav re-gated). No theater found in the gate tests.
3. **smoke.spec flow coverage vs the "62-route" claim — the bar is
   session-only, not committed.** The 62-route claim lives in
   logs/w26.i20.md:107,206 ("68 checks run — superset": 25 routes × dark/light
   + 18 wizard-step checks), run as an ad-hoc battery against the live server.
   The committed e2e flow coverage is: smoke.spec = **1 test** (boot `/` with
   seed → h1 "Player"); a11y.spec axe = 11 routes; theme.spec = 1 route × 21
   cases. The gate itself has strong UNIT coverage (App.test.tsx) but **zero
   committed e2e** exercises the first-run redirect or the wizard
   Next×7→Get-started flow in a real browser — a regression in the gate's
   browser behavior (e.g. a hydration-order break between ThemeProvider and
   the store) would pass every committed e2e. Not dishonest (i20's log
   describes the battery as session verification), but the flow coverage the
   lane claims is not regression-protected.
4. **keymaps/ dir hygiene — exemplary.** default.toml is 281 lines of
   provenance-annotated bindings (per-entry `source`, conflict ids C-01..C-07,
   design-internal conflicts D-1/D-2, open questions Q1-Q8 all flagged), with
   an honest FORMAT FLAG (:28-37) recording the doc-05 §8.1 vs D-003 schema
   divergence, and [platform_overrides.macos] fully [VERIFY]-flagged. It has
   real consumers both ways: `ui/scripts/gen-hotkeys-data.mjs` (committed
   generated module + drift guard) and `player/keymap.ts` (documented
   [PROPOSAL] verbatim excerpt, :62-73, swap-point named). Two parsers exist
   (layout.ts parseTomlSubset vs scripts' parseToml) — duplicated by
   documented necessity (different TOML feature subsets). No dead entries
   found; unbound-by-source keys (repeat-cycle, history-forward) are recorded
   as such rather than invented.

## Dimension scores

### 1. Token discipline — **9/10**
Scope files are clean: a11y/focus.css:12-15 paints `var(--color-accent)`,
a11y/page.css:11-14 paints `var(--color-surface)`/`var(--color-content-primary)`
— no raw hex anywhere in `ui/src/a11y/**` (stylelint 0). App.tsx is
styleless. theme.spec's hardcoded RGB expectations are *assertions* pinning
the token pipeline, and I verified them against the truth source: orange
#d37918, light bright #b35f0d, focus-ring #824505 all match
themes/tokens.json (:226, :727-729). keymaps: n/a (no paint). The light-mode
ring override correctly consumes `var(--color-focus-ring)`
(lumen.css:210-212). Only dock: focus.css's own comment (:4-8) still
describes the ring as "the same token ring" without mentioning that light
mode re-points it elsewhere (see J19-10).

### 2. CSS architecture (app-level) — **8/10**
The two-file a11y layer is the right shape: two additive global floors
(focus ring, body paint), each with a precise comment explaining WHY it
exists as a floor beneath the primitives. The deliberate duplication with
lumen.css is documented at both sites (focus.css:8-10 ↔ lumen.css:131-136;
page.css:1-9 ↔ lumen.css:54-58) — "embeds without this sheet" is a defensible
rationale. Dock 1: the duplication is asymmetric — the light-mode
`--color-focus-ring` override lives ONLY in lumen.css (:210-212), so an embed
consuming a11y/focus.css alone regresses to the 1.40:1-on-light ring that
h05 F1 fixed; the "floor" is only a floor in dark mode. Dock 2 (cross-lane,
j05 P3-4 already filed): the `body { margin: 0 }` reset lives in
appshell.css, not in this body-owning layer. No specificity games, no
!important, no inline styles in scope.

### 3. React quality (gate + provideMain routing; RequireOnboarding wrap) — **9/10**
GatedShell (App.tsx:120-128) is the correct i20 landing: the gate wraps the
LAYOUT routes, so any route added to either group inherits first-run gating —
"nobody can opt a route out by forgetting a wrapper" (:114-118) is
structurally true. `?onboarding=1` is read per render via useSearchParams
(:103-106) — per-navigation bypass semantics are correct and pinned by
App.test.tsx:141-161. PlayerRoute owns only variant→URL routing (:137-150);
the no-onOpenMedia rationale (double-dispatch, a13→d1 fix) is documented at
:139-143. The provideMain split is verified TRUE, not just claimed:
PlaylistScreen:291, SettingsScreen:313/493 (mutually exclusive hydration
branches), MediaInfoScreen:20 render their own `<main>`; AppShell renders
`<main>` only when `provideMain !== false` (AppShell.tsx:662-666); I probed
`document.querySelectorAll("main").length === 1` live on 17 distinct routes
(11 spec + 6 probe) including the 404 and dialog screens. OnboardingEntry
(OnboardingScreen.tsx:875-879) keeps /onboarding itself honest post-complete.
Docks: RequireOnboarding's docstring (:881-882) still says "/player (and only
/player, per the card)" — stale since i20, now misdocuments the shell-wide
gate (J19-6); App.test.tsx inlines the seed/reset incantation in 2 of its 5
seeded tests instead of the seedOnboardingDone/clearOnboardingSeed helpers
defined 10 lines above (:52-58, :132-139 vs :34-43).

### 4. Test honesty — **6/10**
The discipline mechanisms are genuinely good: JUSTIFIED_EXCLUSIONS is empty
with a stale-entry surfacing design (a11y.spec.ts:33-37, 63-72 — violations
are printed with justification context rather than silently filtered); the
axe tags are the enforced wcag2a/2aa set with best-practice explicitly
scoped OUT (:6-11); the trap-wrap assertion is real (§Special attention 1);
theme.spec's 21-case matrix proves both cascade axes with values verified
against tokens.json; smoke.spec is honest about being a boot smoke and
documents its P4-GATE re-pin. But three concrete overclaims/blind spots:
(a) a11y.spec:17-19 claims "Every routable screen (doc 08 §1.6 inventory)" —
false: ROUTES has 11 of ~27 routable paths, and **keyboard-shortcuts and
open-network-stream are listed in doc 08 §1.6 itself yet absent** (plus
discovery, convert, 404, /dev/tokens, 8 of 13 settings areas). I probed the
uncovered set: all currently clean (0 axe violations, mains=1) — so this is
claim rot, not hidden violations, but the suite's header promises a bar it
does not meet. (b) tabThrough's `maxStops = 40` (:112) ends the walk
silently — there is no assertion that traversal EXHAUSTED (body reached or
wrap seen), so on any screen with >40 stops the audit passes while auditing
a prefix. This is not hypothetical: /keyboard-shortcuts measures **400+
stops without returning to body** in my probe, and it is precisely the
screen TAB_ROUTES excludes (:131-133) — the known-worst keyboard surface is
outside the keyboard audit, and the harness could not audit it today anyway
(J19-1, the lane's one P1). (c) the "focus ring paints the --color-accent
token" test (:180-199) runs only in default dark; in light mode the ring is
`--color-focus-ring` #824505 (measured rgb(130,69,5) ≠ accent) — the
assertion as written would fail in light, and no light-mode axe/tab audit
exists anywhere in e2e (J19-3). Plus §Special attention 3: the 62-route flow
bar is session-verification only.

### 5. i18n (route-level titles/labels) — **7/10**
App.tsx contains zero user-visible strings — nothing bypasses useMsg in
scope; the a11y CSS and keymaps carry no user copy (keymap labels go through
label-msgid indirection, resolved via the catalog). e2e assertions on
English copy ("Player", "light", "violet") are acceptable for an en-US
default e2e lane. The structural gap: there is NO route-level title
mechanism at all — `document.title` is never written anywhere in ui/src
(grep: zero hits) and index.html pins `<title>Lumen</title>`, so every
history entry and browser tab reads identically; for a screen-reader user
with multiple windows/tabs, /player, /settings/privacy and the wizard are
indistinguishable by title (J19-7). Route-internal labels (rail aria-labels,
nav names) are i18n'd and were j05-verified.

### 6. Dead code / Solstice remnants — **7/10**
In-scope files are clean (no solstice/sunset/tape/keycap/Nunito/data-backdrop
in App.tsx, a11y/, the three specs, keymaps — grep). But the tree still
ships the dead Solstice font: `ui/src/assets/fonts/nunito-latin-var.woff2`
(39KB) + `nunito-OFL.txt` — **zero references anywhere in ui/** (grep for
`nunito-latin-var|assets/fonts`: no hits), and Nunito is contract-§2
forbidden; this is exactly the "remove it wherever your owned files still
carry it" class of remnant, just in an unowned assets dir (J19-4).
Cross-lane: e2e/visual/manifest.ts:75-78 still asserts in a comment that
"the product default is dark + yellow ('Solstice Keyvox gold')" — stale
since the W26 orange re-pin theme.spec documents (J19-11). RequireOnboarding
docstring rot (J19-6) doubles as a doc remnant of the pre-i20 gate. The
keymap.ts [PROPOSAL] excerpt seed is NOT dead code — consumed, documented,
with its loader swap-point named.

### 7. A11y implementation — **7/10**
The core is real and I verified it end-to-end this session: 17/17 e2e green;
axe wcag2a/2aa = 0 violations on the 11 spec routes AND on the 9 uncovered
routes I probed (incl. the 404 and both dialog screens); single `<main>`
landmark confirmed live on 17 routes (the provideMain contract holds
everywhere, not just on the spec's routes); the settings focus trap cycles
21→61→21 with the wrap landing on the window's first focusable — the e2e
assertion encodes exactly that; every audited stop paints a ≥2px solid
outline; the dark ring resolves to the accent token (probe-verified equality
with a `var(--color-accent)` probe element). The page paint floor's origin
story (white-page 3.2:1 contrast fail, page.css:1-9) shows the suite has
caught real WCAG fails before. Docks, all coverage-shaped: (1) light mode is
never axe'd or tab-audited — the entire second theme, including the h05 F1
focus-ring fix, is unverified by e2e; (2) the tab audit's 40-stop budget +
TAB_ROUTES exclusion of the 400-stop shortcuts screen (J19-1); (3) the
dialogs' own traps (i17's Dialog conversion) have zero e2e presence — unit +
one-off drive logs only; (4) "every routable screen" claim rot (J19-2). None
of these hide a violation I could find — the gaps are unaudited surface, not
known-bad surface — but for THE a11y lane of the wave, the harness's
coverage claims outrun its coverage.

## Overall

**Mean: (9 + 8 + 9 + 6 + 7 + 7 + 7) / 7 = 7.6**

**Verdict: KEEP.** The architecture in scope is sound and, unusually for this
wave, its claims mostly verify at runtime: the layout-level gate is
structurally un-bypassable by omission, the provideMain premise is true on
every route I probed, the trap-wrap assertion encodes real trap semantics
(reproduced with DOM indices), the seeded-gate shapes are the exact persisted
contract, and keymaps/default.toml is the best-provenanced data file in the
repo. The score is dragged by test honesty: the a11y suite's *harness* is
excellent but its *coverage claims* outrun its coverage — "every routable
screen" is 11 of 27, the tab audit cannot see past 40 stops and excludes the
400-stop screen, light mode is entirely unaudited, and the flow bar the lane
cites is session-only. Fix J19-1 (harness, ~30 lines) and J19-5 (2 tests);
J19-2/J19-3 are one comment rewrite + one light-mode variant; the rest is
hygiene. Nothing justifies structural rework.
