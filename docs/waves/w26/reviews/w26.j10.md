## Special-attention rulings (asked by the Lead)

1. **The staged-command pattern — HONEST, but asymmetric. KEEP with a note.**
   DynamicsCard (DynamicsCard.tsx:56-64, 111-113) and VisualizerTool
   (VisualizerTool.tsx:56-63, 105-107) carry `data-staged-tool` +
   `data-pending-command` naming the forward-declared command
   (`audio.set-compressor/-spatializer/-stereo-widener/-visualizer`) plus a
   visible `role="note"` line — controls stay fully interactive on local state,
   never pretending engine binding. That is the right call for a UI wave ahead
   of the DSP layer. BUT EqualizerTool ships **no marker of its own** — the
   tools dialog wraps it (ToolsDialog.tsx:117-126) and shows the note via a
   `:has(.eq-tool--open)` CSS rule (dialogs.css:358-364), while the settings
   effects area stages it separately again. The EQ is the only tool of five
   that cannot stand alone; two hosts now duplicate its staging. (P3-4.)
2. **The spectrum data (bar-4 typo fix lineage) — VERIFIED CORRECT, well pinned.**
   `RESTING_LEVELS.spectrum = [5,14,12,16,13,8]` (types.ts:93-99) now matches
   ModeIcons' frame geometry exactly (SpectrumIcon.tsx:119-124: bars
   261−256/247/249/245/248/253 = 5/14/12/16/13/8) and the frame's
   5/14/12/16/13/8 set; the wrong-19 lineage is documented at types.ts:89-92
   and pinned three ways: raw data (VisualizerTool.test.tsx:191-196),
   data-level ratios ("0.313"/"1.000", :178-179) and rendered px heights
   (["13px","36px","31px","41px","33px","21px"], :182-186). Peak dots sit 3px
   above each bar top in both the icon (y-3) and the display
   (`bottom: barPx + 2`, VisualizerDisplay.tsx:133) — consistent. This is what
   a regression fix should look like.
3. **ToolSliderRow duplication vs the base Slider — the duplication is REAL and
   has ALREADY drifted.** The base `Slider` renders no ticks, so a row wrapper
   is justified; the problem is that the wrapper exists TWICE:
   `VideoSliderRow.tsx` is a 1:1 copy of `ToolSliderRow.tsx` (its own header
   admits it), and the copies have diverged — ToolSliderRow positions ticks on
   the fill domain (`calc(2px + (100% - 4px) * …)`, ToolSliderRow.tsx:84, the
   w26.i07 fix) while VideoSliderRow still uses the pre-fix full-width percent
   (`${left}%`, VideoSliderRow.tsx:82) — i.e., the exact 1.7px drift w26.i07
   fixed in dynamics survives in the video copy. The stated reason (label-key
   union hard-wired to w26.c2 keys) is solvable with a generic
   `<TKey>` + `resolveLabel` prop. (P2-3; video file itself is out of my edit
   scope — flag to Lead/video lane.)
4. **The rail pan fix (dialog reachability at 1024) — delivered and sound.**
   `.eq-panel__rail { width:100%; max-width:748px; overflow-x:auto;
   scrollbar-width:thin }` with `flex:none` 68px columns (equalizer.css:344-362)
   is exactly g15's fix direction; the fader element is sized 328px = 320 track
   + 4px thumb overhangs so panning never clips the thumb (equalizer.css:364-372).
   h13/h14 verified all 11 faders reachable at 1440 and 1024 (last column inside
   the dialog, `elementFromPoint` → track, not scrim). My read of the CSS agrees.
   Gap: unlike dynamics (which pins its sheet strings in harness.test.tsx:59-110),
   nothing pins the rail rule — a future "cleanup" could silently regress it. (P3-8.)
5. **Harness modules — clean.** Env-gated export (`W26C*_HARNESS_OUT`), CSS
   inlined from real files with missing-file comments, never imported by app
   code. The `innerHTML.length > 0` render checks are smoke-level but these are
   dev-only scaffolds, not product tests.

## Dimension scores

### 1. Token discipline — **9/10**

Every color in the three product sheets is `var(--…)`; the single raw hex in
scope (`#1a1611`, the 0 dB tick ink, equalizer.css:396) sits under
`stylelint-disable-next-line color-no-hex` with a frame citation and a
token-lane handoff note — the sanctioned exception pattern, and stylelint passes
because of the documented disable, not a config dodge. The dynamics tick ink
avoids a hex entirely by composing two semantic tokens to ≈#1A1611
(dynamics.css:239-244, Δ≤1/255 claimed and plausible). Raw px values are
structural dimensions, each with a frame citation (68 pitch, 348 list, 328
track…). Light-theme remaps are token-only (dynamics.css:276-300,
visualizer.css:414-432). Inline styles are all computed (tick offset, bar
height/width, peak bottom). Deduction: the color-mix tick ink and the pinned
`#1a1611` are both workarounds for one missing token — a `--color-tick` /
warm-well token would delete both contortions (already logged as a token-lane
ask; keep the pressure on).

### 2. CSS architecture — **7/10**

No dead selectors: every class in the three sheets is referenced by TSX, and
every TSX class has a rule (cross-checked selector inventory). No `!important`.
`[hidden]` display guards, `prefers-reduced-motion` blocks, and hover/focus
states are present in all three. Stylelint 18/standard green. Deductions:
(a) **triplicated tool-card shell** — `.dynamics-tool`, `.viz-tool`
(visualizer.css:25-121) and dialogs.css `.tools-card` each re-implement the
collapsed-48px-pill/expanded-59px-header grammar (~80 lines ×2 near-identical);
(b) **viz-select re-implements the shared Dropdown grammar** (~120 CSS lines +
a 230-line TSX component) that equalizer.css composes onto the primitive via
`.eq-tool__presets` scopes — the documented reason (Dropdown's `icon?:
IconName` can't carry the two-tone svg previews) is real but the consolidation
ask has been pending since w26.c1 (types.ts:16-21); (c) **specificity
jockeying over the slider primitive**: `.eq-panel .eq-panel__fader`
(equalizer.css:369) and `.eq-panel .lumen-slider--vertical.lumen-eq-slider
.lumen-slider__track` (:376-379) re-pin the primitive's own vertical anatomy —
the 4px track inset belongs in the primitive as a modifier, not overridden from
the panel scope by 3- vs 4-class specificity (order-dependent win);
(d) the **:nth-child-keyed preset curve glyphs** (equalizer.css:134-265,
~130 lines) key visual data to DOM position — safe only because
EqualizerTool.test.tsx:109-122 pins the list children; a `data-preset`
attribute would be structural. All documented, none breaking — 7.

### 3. React quality — **7/10**

Good: `EqFaderColumn` keeps drag preview in LOCAL state so a scrub re-renders
one column, not the 11-column panel (GraphicEQ.tsx:218-219) — the right
hotspot design; controlled/uncontrolled support on both EQ components; stable
keys (`band.id`, `row.id`, `mode.id`); `useId`-based aria wiring; data-driven
row defs keep the three dynamics tools at ~90 lines each. The staged-command
pattern is judged above (honest, keep). Deductions:
(a) **Slider math defect**: `EQ_GAIN_STEP_DB = 1` (presets.ts:86) collides with
fractional preset gains (5.6, −7.2, 16.4, 11.2 …) — `quantize()`
(interaction.ts:27-30) rounds to the lattice, so a keyboard step from Dance's
5.6 dB jumps +1.4 dB up (→7.0) but only −0.6 dB down (→5.0). Asymmetric,
surprising, and pinned as expected behavior in EqualizerTool.test.tsx:216-217
("snapped onto the 1 dB step lattice → 7.0") — the test is honest, the
behavior is wrong. (P2-1.)
(b) GraphicEQ writes internal state even when fully controlled
(GraphicEQ.tsx:113-121: `setOpenInternal`/`setStateInternal` run regardless of
`openProp`/`stateProp`) — dead writes + a divergent shadow state; the
tools-dialog mount also double-setStates per commit (GraphicEQ.commit →
EqualizerTool.commitFader). Harmless at this scale, wrong as a pattern. (P3-3.)
(c) DynamicsCard re-renders every row on every drag-move
(`setValues` per `onChangeLive`, DynamicsCard.tsx:52-54; rows unmemoized) — 7
rows max, acceptable today, a known hotspot shape if rows grow. (P3-5.)
(d) VisualizerModeSelect's open effect carries an
`eslint-disable react-hooks/exhaustive-deps` (VisualizerModeSelect.tsx:113-114)
— the dependency on `activeIndex` is real but intentionally open-transition
only; correct in practice (openList sets activeIndex synchronously before
setOpen), but it is the one suppressed lint in scope.
