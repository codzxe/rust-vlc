## 1. Token discipline — 9/10

**Evidence (good):** icon.css and surface.css carry **zero raw colors in declarations** — every ink/fill/radius/opacity/stroke is a semantic `var()`; frame hexes appear only in `/* frame: … */` provenance comments (icon.css:52, 56, 62, 104, 119; surface.css:9-21 header), and Icon.test.tsx:344-347 *enforces* this (strips comments, asserts no hex). icons.tsx carries no hex at all — ink is `currentColor`, and the stroke ladder maps 1:1 to the §1.4 tokens (Icon.tsx:32-36 → icon.css:73-79). The two-tone accent cascade (Lead L1) is coherent: dark details `--color-accent-strong` (#ab6314), bright details `--color-accent-icon` (#d37918), both verified in generated tokens.css:33-34; accent *profiles* override both (tokens.css:141+), so two-tone follows the user's accent. surface.css's one raw value — `rgb(0 0 0 / var(--opacity-scrim-strong))` (surface.css:40) — is stylelint-disabled inline with a `[PROPOSAL]` note for a scrim-ink token; token exists (0.24).

**Evidence (deductions):** icon.css:55-57 hardcodes a `:root[data-theme="light"]` selector to repaint two-tone details `--color-accent-icon` — necessary only because the light theme block (tokens.css:115-139) **does not override `--color-accent-strong`** (every accent profile does; light is the outlier). Frame-marked and correct today, but theme-layer knowledge now lives in a component sheet (token-lane handoff, see j04-8).

## 2. CSS architecture — 7/10

**Evidence (good):** stylelint green, no `!important` anywhere, no inline styles in any scoped TSX (grep). All three `no-descending-specificity` disables carry written, *correct* cascade justifications (icon.css:31, 65, 139 — I verified the specificity math: `.lumen-icon-host:hover .lumen-icon` (0,3,0) outranks `--selected` (0,2,0) regardless of order). Reduced-motion covered on both sheets (icon.css:88-92, 146-150; surface.css:158-174, 262-266). BEM consistent; `prefers-reduced-motion: no-preference` gating of sheet animations is the modern pattern. `.lumen-pane` vs `.lumen-panel` class-collision avoidance is documented at the use site (surface.css:206-210, Surface.tsx:243-244).

**Evidence (deductions):** dead rules with **no producer anywhere** (exhaustive grep incl. dynamic class-building):
- `.lumen-icon-host--selected .lumen-icon` (icon.css:32) — only `--open` is ever applied (ControlBar.tsx:814, 1040);
- `.lumen-icon-host--disabled .lumen-icon` (icon.css:81) — zero producers;
- `.lumen-icon--disabled` (icon.css:82) — produced only by Icon's `disabled` prop, which no screen passes (Icon.test.tsx:120 is the sole user);
- `padding: var(--lumen-icon-hit, 0)` (icon.css:15) — extension point adopted by no host (comment promises "interactive hosts opt in"; none do).
Also `.lumen-separator` geometry is split across two files (theme base sheet owns the shared hairline, surface.css:277-298 layers orientation) — documented and deterministic via data-attribute specificity, but a split-brain dependency.

## 3. React quality — 7/10

**Evidence (good):** Icon is an ideal leaf: glyphs are **module-level constants** (no per-render element recreation on a component rendered hundreds of times per screen), string-composed className is trivial, aliases share element instances safely (immutable). Surface runs ONE trap implementation shared by Dialog and Sheet (no copy-paste), keeps the listener stable via `onCloseRef`, and the `[hidden]` structural filter + explicit `preventDefault` Tab takeover is a documented jsdom-and-browser-correct design (Surface.tsx:96-108). All primitives are presentational leaves — zero re-render hotspots.

**Evidence (deductions):**
- `onCloseRef.current = onClose` writes a ref **during render** (Surface.tsx:67-68) — idempotent here, but it's the pattern React's concurrency docs prohibit; belongs in an effect.
- **Initial focus is hardcoded to the first focusable** (Surface.tsx:78-79) with no `initialFocus` API, forcing hosts to hack around it with effect-ordering assumptions (ShortcutsScreen.tsx:368-373 re-focuses the search field *after* the child Dialog's trap effect — child-before-parent ordering is real but fragile cross-file coupling; APG dialog pattern recommends configurable initial focus).
- Tab branch does **not** `stopPropagation` (Surface.tsx:101 — only Escape does, line 92). Two stacked Dialogs would run both traps on one Tab press (each queries its own subtree, which includes the nested dialog) and fight over focus. Latent — I verified all 11 Dialog hosts in the tree are leaves, no nesting today.
- `FOCUSABLE_SELECTOR` (Surface.tsx:29-36) misses `[contenteditable]`, `audio[controls]`, `video[controls]`, `summary`; Escape ignores `event.isComposing` (IME).

## 4. Test honesty — 6/10

**Evidence (good):** what exists is honest and strict. Icon.test.tsx pins **mined path-data fingerprints** against hand-redraw drift (lines 195-247), a 24×24 grid-bounds guard over all 85 glyphs (132-145), alias identity by serialized DOM (249-261), per-element sheet stroke overrides (187-193), and CSS-source token assertions including the no-hex rule (119-128, 324-347). No snapshots, no theater. Surface.test.tsx proves real behavior: focus move + opener restore (56-67), Tab wrap both directions (69-92), Escape reason (94-103), scrim gating with stopPropagation (105-123). 46/46 green (ran).

**Evidence (deductions):**
- **The two-tone feature has ZERO tests.** No test file in the repo asserts `twoTone`, `.lumen-icon--two-tone`, `.lumen-icon__detail`, `getTwoToneGlyph`, or the four dedicated `twoToneGlyphs` variants (icons.tsx:894-945) — grep across all `*.test.tsx` finds only the word "two-tone" in VisualizerTool.test.tsx:83, which counts `.viz-select__icon` nodes (ModeIcons, not the registry path). This is the file's largest recent change (~200 LOC of tone-split markers + 4 alternate glyphs + a CSS cascade). Notably, w26.i16's lane log claims "incl. … Icon two-tone tests" among 340 passing (docs/waves/w26/logs/w26.i16.md:344-346) — **no such tests exist in the checkout**; the log overstates coverage.
- Surface.test.tsx has **no test of the first-Escape-yields rule** (Surface.tsx:82-95, the w26.g19 P1-2 root fix this review was told to scrutinize). Its only exercise is end-to-end in a foreign lane (AddSubtitlesDialog.test.tsx:68-95). A regression to the selector would not fail any test in the owning suite.
- Other gaps: `[hidden]` filtering (Surface.tsx:102-104), zero-focusable fallback (105-108), Dialog with neither `label` nor `labelledBy`, two-tone mono-inertness (detail markers must not paint without the class).

**Evidence (deductions):** **9 of 85 registry names have no consumer anywhere in ui/src** (exhaustive quoted-literal scan outside `components/icon/`, including dynamic catalogs): `minimize`, `maximize` (sole occurrence is an English comment, AppShell.tsx:212), `left-sidebar`, `collapse-sidebar`, `expand-sidebar` (only `right-sidebar` is used — AppShell.tsx:425), `person`, `wand` (alias twins of the used `profile`/`customize-player`), `accessibility`, `vlc`. Also dead: `hasTwoToneVariant` (icons.tsx:956-959) — exported as a "test hook", used by no test; `variant="max"` / `--stroke-icon-max` (icon.css:77-79) — test-only; IconWrapper `sm` and `md` presets (icon.css:112-120) — production uses only `lg` (AppShell.tsx:495, 509). The a07 log documents the full-catalog decision deliberately (w26.a07.md:53-60), which mitigates intent but not the 10%-dead catalog + cross-tree duplication at wave J.

## 7. A11y implementation — 6/10

**Evidence (good):** Icon's decorative/named split is textbook — `aria-hidden="true"` by default, `role="img"` + `aria-label` + `<title>` when titled (Icon.tsx:73-78), proven by tests (Icon.test.tsx:105-117) and unchanged by variant (290-297); `pointer-events: none` keeps hit areas with hosts (icon.css:16). Dialog/Sheet: `role="dialog"` + `aria-modal` + labelled (labelledBy preferred, synthesized sr-title fallback, Surface.tsx:130-136, 169-180), focus moved in on open / restored to opener on close (tested), Tab trap wraps to first/last focusable and the e2e tab audit encodes wrap-must-land-on-first-DOM-focusable (ui/e2e/a11y.spec.ts:144-162). The first-Escape-yields *mechanism* is correctly reasoned: the native node-level listener fires before React's root delegation, and the shared Dropdown/MenuPopup popups render their `role="listbox"`/`"menu"` nodes only while open (Dropdown.tsx:326-329), so yielding to them is right.

**Evidence (deductions):**
- **P1 — the yield selector matches permanently-rendered listboxes, killing Escape on a real screen state.** `node.querySelector('[role="listbox"], [role="menu"]')` (Surface.tsx:89) cannot distinguish an open popup from an in-flow listbox. `SubtitlePickList` renders `role="listbox"` whenever candidates exist (SubtitlePickList.tsx:125-133) and is mounted inside `AddSubtitlesDialog`'s Dialog (AddSubtitlesDialog.tsx:262-267). In the Folder-2/Folder-3 candidate states the trap therefore yields on **every** Escape; nothing else handles it (SubtitlePickList's onKeyDown covers only arrows/Home/End/Enter/Space, SubtitlePickList.tsx:80-112; the dialog has no window-level listener), so the dialog **cannot be closed with Escape** — doc 08 §4.5 violated; keyboard users must find ✕/Cancel. Verified by code trace (all AddSubtitlesDialog Escape tests run in pairs mode, where the body is `role="list"`, so the suite is green blind to this). Knock-on: the gfix-E `guardedClose` dropdown branch (AddSubtitlesDialog.tsx:140-151, foreign file) is now unreachable — with a dropdown open the trap yields before `onClose` ever fires.
- Initial focus not configurable (see §3) — hosts override via effect-ordering.
- Dialog with neither `label` nor `labelledBy` renders an **empty accessible name** (empty sr-title span, Surface.tsx:176-180) with no dev warning.
