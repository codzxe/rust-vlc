## Special-attention rulings (asked by the Lead)

1. **The advanced-disclosure behavior — CORRECT in the shell, but it exists three
   times and the fix didn't propagate.** `SettingsSections.tsx:150-194`
   (`AdvancedDisclosure`: aria-expanded/aria-controls, guarded `scrollIntoView` on
   expand, i12's h08 #1 fix) is sound and is live via the generated screens
   (performance carries 8 `advanced: true` entries). But it is not exported, so
   `areas/index.tsx:163-187` (GlobalAreaScreen) hand-copies it — including the
   scrollIntoView — and `areas/video.tsx:170-193` (`CodecsFold`) hand-copies it
   **without** the scrollIntoView. The codecs fold therefore still ships the exact
   h08 #1 defect ("expanding reveals nothing" near the fold) that the shell half
   fixed. Both copies also hardcode `id="settings-advanced-rows"` /
   `"settings-codecs-rows"` separately; the shared id string is defined twice
   (SettingsSections.tsx:188, areas/index.tsx:180 — no live collision, mutually
   exclusive screens, but a trap). (P2-6, P3-4.)
2. **The search path — one real behavior bug + one dead mechanism.**
   (a) **P1-1:** the query is never cleared on navigation. `requestArea`
   (SettingsScreen.tsx:287-294) navigates while `searching` (SettingsScreen.tsx:281,
   387) keeps the content column in cross-area results mode. Repro: `/settings/global`
   → type "hide" → click the sidebar "Privacy" row → URL, window title
   ("Privacy Settings") and `aria-current` all move to Privacy, but the column still
   shows the stale "hide" hits; the Privacy screen is unreachable until the pill is
   cleared. This breaks the nav row's behavior contract; no test covers
   search+nav interaction.
   (b) **P2-2:** the in-area filter plumbing is dead-in-effect. Every consumer of
   `matches`/`rowMatches` (SettingsSections.tsx:218,131-143; GlobalAreaScreen;
   playback area) is **unmounted** whenever a query is active
   (SettingsScreen.tsx:387-409 renders results INSTEAD of `<Current />`), so the
   per-area filter can never filter; `SettingRowNode.keywords`
   (SettingsSections.tsx:26,222-224) can never match; and hand rows (Clear history,
   Reset picture, Output device) are invisible to search because `searchSettings`
   walks schema entries only (search.ts:47-54). ~40 lines of filtering API that
   reads as a live feature but cannot execute. Either render the filtered current
   area beside the results or delete the context filter surface.
3. **The persistence seams — honest and layered; minor gaps.**
   `persistence.ts` is small and defensive (corrupt JSON → `{}`, quota → in-memory,
   array rejected); the provider drops unknown keys (SettingsProvider.tsx:62-70);
   the desktop bridge gates rendering behind `hydrate()` (SettingsScreen.tsx:471-499)
   and `readKey` catches transport failures (config-settings.ts:100-122), so
   `void config.hydrate().finally(...)` cannot produce an unhandled rejection —
   verified, not a finding. Two deductions: `load()` casts
   `parsed as Record<string, SettingValue>` with no per-key **value-type**
   validation (persistence.ts:24 — a tampered `{"interface.keep-above": "yes"}`
   loads and silently renders as bool-false; only key membership is checked), and
   `memorySettingsPersistence` (persistence.ts:38-45) is a test double living in a
   production module (used only by three picker tests). No direct unit test exists
   for persistence.ts at all — the catch branches are uncovered (P3-6, P3-11).
4. **The nested-area-roots fix lineage (h11 #4 → i15) — VERIFIED healed.**
   Exactly one `[data-settings-area]` root per route: wrappers dropped the marker
   (playlist-services.tsx:13-14, recording.tsx:21) and `SettingsSections` emits the
   single root for composed screens (SettingsSections.tsx:235); recording.test.tsx:51-56
   pins it. The search-results branch (SettingsScreen.tsx:393-405) renders plain
   sections, no area root. No regression.
5. **The `schemaSectionsOf` union widening from wave I (the `SchemaSection` type
   fix) — the RIGHT fix, verified truthful.** The dead i12 attempt widened the
   output to `GeneratedSection[]` (rows: `SettingEntry | SettingRowNode`), which
   broke 9 areas call sites with TS2339. The relaunch instead declared the precise
   producer type `SchemaSection` (SettingsSections.tsx:49-53) with
   `entries: readonly SettingEntry[]` — checked against `generated/schema.ts:56`
   (`SettingsSection.entries: readonly SettingEntry[]`): the seed's sections never
   contain a hand row, so the narrowing is exact, not a cast-lie (only
   `title: string → MessageKey` is cast, the established msgid seam). Consumers
   widen deliberately via `withRows` (SettingsSections.tsx:78-94). This is
   textbook type-driven design — keep. Residue: `areas/index.tsx:141` still
   re-narrows with `"key" in row` (redundant since the fix; out of my edit scope —
   Lead note).

## Dimension scores

### 1. Token discipline — 9/10
All colors/typography/radii/motion resolve through semantic tokens
(`var(--color-surface-deep)`, `--radius-control`, `--motion-duration-fast`, …) across
both sheets; every frame-measured dimension carries a `/* frame: … */` comment
(settings.css:64,97-98,159,230,356; setting-field.css:41-42,113-121,176-178 — spot
checked against the annotations, consistent). Raw hex lives in comments only; the
single declaration-level hex is the documented token-seam fallback
`var(--color-slider-tick, #1a1611)` (setting-field.css:260) with
`stylelint-disable-line` + frame provenance + pending token-lane ask — the honest
way to hold a seam. The dropdown chevron rides a mask data-URI whose `%23000` is
mask geometry, not a color declaration (setting-field.css:62). Docked 1: the
`color-mix` literal percentages (95%, 92%, 85%/15%, 46%) are un-tokenized frame
recipes scattered across ~8 rules (settings.css:74,78,169,251,766,820) — they
should be one documented recipe each or a token once the token lane exists.

### 2. CSS architecture — 7/10
Stylelint clean, zero `!important`, zero inline statics. The specificity juggling is
deliberate and documented: active-before-hover for `no-descending-specificity`
(settings.css:310-313), the equal-specificity `:last-child` rule deliberately placed
after the scoped shaves so source order decides (settings.css:406-413), the
matching last-row rule after the row rules (settings.css:700-705) — all verified
consistent. The one-class-deeper override strategy in setting-field.css
(header, lines 3-9) is principled (import-order independence). Deductions: three
dead rules (P3-2), one rule duplicated across the two sheets (P3-3), and the
area-scoped gap overrides use two different scoping mechanisms (class vs
`[data-settings-area]`, P3-1). The sheets are extremely comment-dense (~40%
comments) — honest and traceable, but the archaeology cost is real.

### 3. React quality — 7/10
Hooks are correct and the tricky parts are documented: all hooks run before the
`isAreaId` early return with an explicit Rules-of-Hooks note (SettingsScreen.tsx:245-247);
the callback-ref mount-focus design (SettingsScreen.tsx:184-215) correctly races
async data arrival and never re-fires on search typing; the `requestCloseRef`
latest-closure seam is explained. Keys are sound everywhere (sidebar ids, hit
composite keys, entry keys; tick/scale index keys are static-count — fine). The
wave-I `SchemaSection` fix is right (ruling 5). Deductions: the production module
cycle `SettingField ⇄ areas` (P2-5); the dead-in-effect search plumbing (P2-2);
non-memoized context value + fresh `matches` closure per render
(SettingsScreen.tsx:280 — every shell render re-renders all search-context
consumers; harmless at 13-area scale, P3-7); the render-phase ref write
(SettingsScreen.tsx:302, P3-8); the per-keystroke clamp in the text-well number
parsers (P3-10).

### 4. Test honesty — 8/10

assertions (`queryByRole(... )` toBeNull, SettingsScreen.test.tsx:72-76,139), and

### 5. i18n — 9/10

### 7. A11y implementation — 7/10
