## Dimension 2 — CSS architecture: **6**

- stylelint green, zero `!important` (verified), no inline statics — inline styles are runtime geometry only (`--lumen-slider-*`, row `top/height`, buffer `left/width`).
- **Broken geometry contract at the base scope (P1-1)**: `.lumen-slider__thumb` (slider.css:87) carries the L8 inset formula `left: calc((100% - 4px) * p / 100 - 6px)`, and its comment (:83-86) asserts "Fill ends at 2px + (100% - 4px)·p" — but the base `.lumen-slider__fill` (:61-66) is `left: 0; width: calc(p * 1%)` (full width, NO inset). The comment describes the EQ anatomy, not this rule's own fill. The g16-P2-3 Lead fix over-applied the EQ formula to the base thumb without changing the base fill.
- **Live-measured regression** (Playwright, `/settings/video`, Hue slider; settings skins inherit base fill/thumb geometry — setting-field.css:229-241 re-skins only top/height/color/radius): `Home` (p=0) → thumb right edge **+2px past** fill end, thumb left edge **6px outside the track** (thumbL 1061.5 vs trackL 1067.5); `End` (p=100) → thumb **2px short** (1385.5 vs 1387.5); p=50 flush. Matches err = 2 − 4p/100. Affects every settings slider (video 5, audio 12, playback, interface, subtitles). Pre-fix base thumb `(100% - 8px)·p` was flush-at-100 and never stuck out — the fix regressed this surface.
- **Vertical EQ fader never got the L8 fix (P1-2)**: `.lumen-eq-slider.lumen-slider--vertical .lumen-slider__thumb` (slider.css:371) still ships the old `bottom: calc((100% - 8px) * p / 100)` grammar that g16-P2-3 killed horizontally. Live-measured (tools dialog → Audio → Open Equalizer, 11 faders): p=80 → thumb top 385.4 vs fill top 388.2 (**2.8px over**); p=50 → 479 vs 483 (**4px over**); math gives 6px at p=0 → 2px at p=100. Flush needs the vertical L8 mirror: `bottom: calc((100% - 4px) * p / 100 - 6px)` (verify: thumb top = H−2−(H−4)p/100 = fill top at every p). Base vertical (:125) has the same stale grammar. i07 verified `flushDelta: 0` on the 16 horizontal dynamics rows only (w26.i07.md:29-31) — the vertical axis was missed by every fix wave.
- Correct applications, for the record: horizontal EQ (slider.css:173) and `.dynamics-slider` (dynamics.css:206) are flush at every p (inset-2 fill + L8 thumb, internally consistent).
- Dead rule: `.lumen-vtable__head { position: sticky; top: 0; z-index: 1 }` (list.css:165-170) can never activate — the head is a flex **sibling** of the scroller `.lumen-vtable__body` (:172-176), not inside it. Misleading (implies the head scrolls).
- Duplication: `.lumen-vrow:hover` (list.css:153-156) and `.lumen-lrow:hover` (:241-245) both paint `surface-hover` + bright text — when ListRow sits in a VirtualList row both fire (same color, harmless, but two sources of truth for one grammar).

## Dimension 3 — React quality: **7**

- The interaction engine (interaction.ts) is genuinely good: stable callbacks, justified exhaustive-deps disables, pointer-capture feature detection, live-dedupe via `emittedRef`, pointercancel aborts without commit, `clamped === value` keyboard bail-out — all pinned by call-order tests.
- Controlled-component contract (value→render, never optimistic) is rigorous and documented at every layer.
- **Re-render hotspot (P2-4)**: `setRange(computeRange(...))` (Virtual.tsx:26-27) always installs a fresh object, so **every scroll event re-renders the whole window** even when startIndex/endIndex are unchanged — most scroll ticks inside the overscan band re-render ~30 row wrappers + consumer rows for nothing. One-line fix: `setRange(prev => (prev.startIndex === next.startIndex && prev.endIndex === next.endIndex && prev.totalHeight === next.totalHeight) ? prev : next)`.
- Minor: `Tabs` context value is a new object every render (Tabs.tsx:37-42) — all tab/panel consumers re-render on any Tabs render. Fine at current scale.
- VirtualList API gaps that force consumer-side DOM surgery are graded under a11y (P2-2/P2-3); architecturally the `semantics` prop restructure (Virtual.tsx:105-115) is clean and the shrink-lag clamp (:100-101) is correct and tested (List.test.tsx:241-261).
- Scroll anchoring: absolute rows in a constant-height spacer = native anchoring, no jumps; `computeRange` clamps stale scrollTop past a shrunken dataset (range.ts:35, tested :152-157); `scrollToIndex` effect keyed on `[index, align]` fields (Virtual.tsx:99) correctly avoids refiring on inline-object identity churn. Sound.

## Dimension 7 — A11y implementation: **6**

- **Slider keyboard operability: exemplary.** Arrows ±step, Shift coarse ×10, PageUp/Down, Home/End, `aria-orientation` honored (ArrowUp always increases), `aria-valuetext` formatters, disabled = `aria-disabled` + tabIndex −1 + pointer-events none + truthful value — all tested (Slider.test.tsx:120-183, EQSlider.test.tsx:68-80, Volume.test.tsx:48-73).
- **Tabs: correct APG pattern.** Roving tabindex (only selected tabbable), wrap-around arrows per orientation, Home/End, `aria-controls`/`aria-labelledby` id wiring via useId — tested (List.test.tsx:43-115).
- **VirtualList `semantics` restructure: right call, half delivered.** Grid rows for link-bearing rows fixed the axe nested-interactive violation (all 4 production mounts use `semantics="grid"`: AppShell.tsx:630, PlaylistScreen.tsx:330, MediaList.tsx:84, PlaylistPanel.tsx:260). But:
  - `aria-selected` hard-coded `false` on every row/option (Virtual.tsx:106, :112) with **no API to express selection** — the current queue track (PlaylistPanel), current media row (MediaList), selected playlist (PlaylistScreen:335) are visually selected but announced unselected forever. The consumer documents the seam as known: "aria-selected stays false (the shared VirtualList pins it — list-lane seam, logged)" (PlaylistScreen.tsx:77-78). (P2-1)
  - The primitive owns the tab stop (Virtual.tsx:124) but ships no row ids, no `aria-activedescendant` management, no arrow keys — PlaylistScreen had to build `useGridRoving`: a ~100-line imperative controller doing querySelector loops, `style.top` parsing to recover indices, post-React `setAttribute` writes and a 30-frame rAF settle loop (PlaylistScreen.tsx:105-170) to deliver the APG grid keyboard pattern. That workaround existing at all is an API failure of this lane's primitive. (P2-2)
  - Windowed rows lack `aria-rowindex` (Virtual.tsx:106, :177) — APG requires it when `aria-rowcount` is set and rows render dynamically; SR users can't perceive which slice is on screen. (P2-3)
  - Default `semantics="listbox"` path implements no listbox pattern (options unfocusable, no selection, no activedescendant) and has zero production consumers — a latent trap. (P3)

## Overall

**Mean: (9 + 6 + 7 + 7.5 + 9 + 8 + 6) / 7 = 7.5** — **VERDICT: KEEP** (fix-forward).

The interaction engine, controlled-value contract, windowing math and test honesty are genuinely strong; token discipline is the best in the repo so far. What keeps this out of the 8s: the flagship L8 flush formula was applied inconsistently — correct in the two horizontal EQ/dynamics scopes, regressed on the base scope (factually wrong comment, live-measured on every settings slider) and never applied vertically (live-measured on the EQ faders); and the `semantics="grid"` restructure shipped half-delivered (aria-selected pinned false with no API, no row identity, no aria-rowindex, zero primitive-level tests), forcing a consumer into 100 lines of rAF DOM surgery.
