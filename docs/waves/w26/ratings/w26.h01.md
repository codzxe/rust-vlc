## Top-5 defects by shamefulness

1. **Step 2 form anatomy is not the frame's form.** Bare raised #262626 r6 input (frame: inset
   #090909 rx5 + 2px #191919 stroke) + 60×32 "Open" (frame: 114×35 #1B1B1B "Browse") + the
   frame's visible field label hidden via `hideLabel`. Two waves of verification logged it; the
   Lead's form-lane arbitration still hasn't landed, and the first-run screen every new user
   types into is the one control that doesn't match its frame.
   `ui/src/screens/onboarding/OnboardingScreen.tsx:583-603`, `onboarding.css:195-207`; repro:
   /onboarding → Next.
2. **Body copy 14px vs frame ≈16px, every step** (g01 P3-3, open through gfix). The hero's
   primary reading surface is 12.5% undersized; `--font-size-label` (16px) exists and is unused
   here. `onboarding.css:174` (`--font-size-body`); repro: /onboarding, compare paragraph to
   Onboarding.png body block.
3. **Light-mode body contrast 3.62:1 — fails WCAG AA for 14px text.** Light tokens pair
   `--color-content-secondary` #4e4e4e with the wizard window `--color-surface-chrome` #ababab;
   measured on all six light shots. Cross-lane token issue (theme lane), but it ships on this
   screen. Repro: seed `interface.theme=light`, /onboarding.
4. **Window fill #161616 vs frame #0E0E0E.** The entire wizard card renders one step lighter
   than every reference frame (pixel: 22,22,22 vs frame 14,14,14). Wave-plan sanctioned
   (surface-chrome token), but a frame-measured raw value with a `frame:` comment was
   contract-legal and would have matched. `onboarding.css:75`.
5. **Keycap ink near-miss: cap #191919 vs frame #1B1B1B, inset stroke #404040 vs frame #373737**
   (step 2 hints; shared with the shortcuts lane). The 1.5px/4.5px two-layer inset geometry is
   an exact, clever port — then it's filled with the wrong token values, 2 hex off each.
   `onboarding.css:305-307`; repro: /onboarding → Next, compare caps to Onboarding-2.svg grammar.

Honorable mentions: footer accent-ring inset 52px vs frame 43px (9px, step 3); CTA label 14px
vs frame ≈16px (app-wide button.css, w26.a03); working-step headings #8f8f8f vs frame #969696.

## Would I ship

Steps 3–6: yes, today — post-gfix the appearance step is measurably frame-exact (pitch, rings,
palette, variants, full state matrix, roving keyboard), and the unframed steps are disciplined
token-clean Settings grammar with honest, schema-backed controls and a privacy step that
actually respects the user. Steps 1–2: not as a first impression. The hero under-sizes its body
copy and wastes a third of the window, and the library step's input/button anatomy is the only
place in the family where a user can feel the frame leaking through the spec conflict. Fix the
step-2 field anatomy (Lead arbitration), bump body to 16px, darken the window to the frame's
#0E0E0E class, and this is a 9+ family. Ship-blocking: none of it — but the first-run gate is
the one screen you never get to re-do with these users.
