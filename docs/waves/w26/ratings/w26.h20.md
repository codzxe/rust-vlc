What holds: the **video canvas is dark in both themes** — dark `#090909`, light
`#2b2b2b` (computed + pixel-verified on `.lumen-player__canvas`, and the light frame's
own canvas samples at (45,43,41)≈#2d2b29, so the value is frame-faithful), and the
accent is **not washed out in light** — orange-pixel share is identical between themes
on every route measured (0.90%/0.90% player, 0.35%/0.36% music, 0.01%/0.01%
playlist/miniplayer, 0.1%/0.1% settings, 0.62%/0.62% onboarding), with light accent
derivatives properly darkened (#b35f0d bright, #c2711a icon) rather than bleached.
Light mode is credible on 6 of 8 routes. Then the ledger:

1. **The light tertiary token ships split-brained.** `themes/tokens.json` pins
   gray.325 = **#767676** (line 110–113) with the claim it "clears [3:1] everywhere
   and 4.5:1 on panel/surface" — arithmetically false: #767676 measures **2.55:1 on
   #c2c2c2, 2.66:1 on #c6c6c6**, failing even the UI floor. The generated, shipped
   `ui/src/tokens/generated/tokens.css:118` carries **#5f5f5f** instead —
   3.58:1/3.74:1, which passes the 3:1 floor but fails AA body text. Source of truth
   and shipped artifact disagree, the documented deviation (#767676, per the wave
   briefing) does NOT hold in the build, and whichever value you pick, the in-file
   WCAG claim is wrong arithmetic nobody re-checked.
2. **The light accent-text token fails its own claim.** orange.450 = #B35F0D
   (`tokens.json:209-211`) is documented as "measures 4.2:1 surface / 4.6:1 panel";
   it measures **2.59:1 on #c2c2c2 and 2.70:1 on #c6c6c6** — below the 3:1 UI floor —
   and it ships as real text color in `.lumen-button--tinted:hover`
   (`button.css:129`).
3. **Light mode erases every recessed well** (h19's finding, re-verified live this
   wave): shortcuts keycaps render (194,194,194) on the (198,198,198) window — a
   4/255 step against dark's 15/255 — and the netstream header collapses the same way
   (#c2c2c2 on #c6c6c6, pixel-sampled). The light surface ramp
   (#c2c2c2/#c6c6c6/#bababa) simply has no room to express depth.
4. Dark tertiary **#828282 holds and clears AA** (5.18:1 on #090909, 4.58:1 on
   #191919) — the one documented deviation that survives contact with a calculator.

Layout does not shift between themes on any route (same rects, same grammar), theme
persists across every hop with no flash, and light hover/focus states remain visible
(#b4b4b4 hover, #acacac borders). This is a coherent light theme built on a token
ramp that cannot support it, with two published contrast claims that are simply
false. Theme coherence is the product's second-weakest axis and it is entirely a
token-layer problem.

## Would I ship (the WHOLE product)

**Not yet — 7.5/10, closer than the lane ratings suggest.** As one system this
product is genuinely coherent: one shell, one rail, one Inter scale with tabular
timecodes, one dialog grammar, one sparing orange accent that survives the light
theme intact, a video canvas that stays dark in both themes, dialogs and windows
that adapt cleanly at 1024×768, and — the stat I'd put on the ship-review slide —
**zero console errors across 22 flow hops, 32 captures and 12 small-viewport
routes.** What stops my signature is that the two systemic risks live in the layer
everyone trusts most: the token file publishes contrast claims that fail
third-grade arithmetic (two of them, both light-mode), the source and the generated
artifact disagree on a shipped text color, and the light surface ramp cannot express
depth (Δ4/255 wells). Fix the token layer (retune light tertiary/accent-text to
values that actually clear their claims, deepen the light ramp), put the gate around
the app instead of five routes, give the shortcuts window dialog semantics, and
re-unify hover — those four moves, none of them layout work, take the whole product
to an 8.5+. Ship after that; not before.
