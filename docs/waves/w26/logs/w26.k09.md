## j09-P1 · Bookmark wire-unit µs/ms mismatch (1000× off vs schema) — FIXED

The schema contract is µs (`$defs/Timestamp` "Microseconds since media
start"; `media.add-bookmark` arg `time`, `Bookmark.time`); the dialog
computed ms. My half (the bookmarks consumer) now crosses at a named
constant `US_PER_SECOND = 1_000_000` at all three sites:

- add: `state.position * 1_000_000` (seam seconds → wire µs);
- render: `bookmark.time / 1_000_000` (wire µs → tabular timecode);
- jump: `bookmark.time / 1_000_000` (wire µs → seam seconds for the shared
  `actions.seek` funnel).

Regression test (would have caught the bug — the old code fails it at all
three assertions): "wire unit is µs per the schema — 90 s adds as
90 000 000, renders 1:30, jumps back to 90 s". Runs at a NONZERO position
(j09's zero-only adds were unit-agnostic); the seeded time-tick carries
BOTH the fraction and the µs twin (`position: 90, time: 90_000_000`) so
the pin holds on either side of k17's seam-side fix. Natural-order seed
fixed from ms to µs (`300_000_000` → "5:00", was `300_000`) — the suite's
two files no longer disagree about the wire unit. naturalSort.test.ts was
already µs (unchanged).

**k17 coordination (family-wide half, NOT mine):** `context.tsx:358` reads
`timing.time-tick.position` — a 0..1 **fraction** per the same schema —
into `state.position` (documented seconds), and `:367` reads
`timing.duration-known.duration` (µs `Timestamp`) into `durationSeconds`.
My dialog code is correct against the seam's documented contract (seconds)
