## Findings fixed

### e03-F1 + e19-F1 — P1 — persisted `interface.theme` ignored on fresh load outside /settings — FIXED

**Root cause (confirmed):** `useSettingsThemeSync` mounted ONLY in `SettingsScreen.tsx:140`
+ `ThemeModePicker.tsx:20`; `ThemeProvider` hardcoded `modeSetting = "dark"`, so a persisted
`interface.theme:"light"` lost on every fresh load / deep link of all 10 non-settings routes.

**Seam chosen (per task instruction: "ThemeProvider's init … not post-mount flicker"):**

1. `ui/src/theme/settingsThemeSync.ts` — new exported **`readPersistedThemeMode()`**: a
   synchronous bootstrap read of the persisted override via the SAME persistence seam
   `SettingsProvider` hydrates from (`localStorageSettingsPersistence`, key
   `lumen.settings.overrides.v1`, corrupt-store tolerant). Validates dark/light/auto; null
   otherwise (never guesses). The settings↔theme knowledge stays in the seam file —
   ThemeProvider stays ignorant of storage.
2. `ui/src/theme/ThemeProvider.tsx` — `modeSetting` **lazy-initializes** from
   `readPersistedThemeMode() ?? "dark"`, and the `data-theme`/`data-accent` attribute effect
   moved from `useEffect` → **`useLayoutEffect`** (commits before first paint — no dark→light
   flash after mount).

**Why NOT the suggested "mount the sync in AppShell/App":** AppShell is absent on
`/onboarding` (full-bleed gate, e19-F1's failing list includes it) and `/dev/tokens`; a root
`SettingsProvider` would be a second instance duplicating the settings screen's own provider
(state divergence, no benefit — the settings screen's live-preview sync stays); and a
post-mount effect in AppShell re-introduces the flicker the task asked to avoid. The
provider-init seam covers EVERY route including full-bleed ones, on the first render.
`App.tsx` therefore needed no change (owned but untouched — decision recorded here).

- `data-accent`: nothing to hydrate — no `interface.accent` schema key exists (gap recorded
  in settingsThemeSync.ts header since 4.E2); accent honestly defaults to orange.
- In-session live preview / Apply behavior unchanged (`useSettingsThemeSync` still mounted in
  the settings screen; idempotent).
- Residual (honest): between HTML parse and React mount the raw `:root` CSS default (dark)
  paints — an inline pre-hydration script in `index.html` (not f08-owned) would be needed to
  kill that sub-frame flash for light users. Optional Lead follow-up, not part of the finding.

### e19-F5 — P3 — "System" (auto) unreachable from Settings — FIXED on the theme side (handoff for f03)

- `settingsThemeSync.ts`: `isThemeMode` now accepts **`"auto"`** — both the live sync and the
  bootstrap read honor it end-to-end (persisted `auto` hydrates and follows
  `prefers-color-scheme`, flipping live both directions — unit + Playwright `emulateMedia`
  verified below). `ThemeProvider` already resolved `auto` (4.A2).
- **NOTE FOR w26.f03 (ThemeModePicker owner — do NOT self-apply, file not mine):** the picker
  renders options straight from the schema enumeration, which is `["dark","light"]` only
  (`schemas/settings.toml:67-76` → `generated/schema.ts` `SETTING_INTERFACE_THEME.enumeration`).
  To surface "System": the schema owner/Lead must add the enum value (msgid pattern
  `settings.value.interface-theme.*`, e.g. `.system`); the picker then picks it up
  automatically (no code change needed in ThemeModePicker beyond the enum arriving). The
  theme side (sync + hydration + provider) is ready and tested for it. Persisting "auto"
  additionally unblocks e19-F2 (onboarding appearance step does not persist — onboarding lane).
