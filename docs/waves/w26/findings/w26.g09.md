## Findings

### [g09-P0-1] The customize panel is unreachable in the running app — all three documented triggers fire a dead seam
- **State + reproduce:** `/player` (onboarding complete), media open or not. (a) Right-click
  the canvas → click "Customize interface…" (`state5-t1-menu.png` → `state5-after-t1.png`);
  (b) `Ctrl+A` (`state5-after-t2.png`); (c) ControlBar application menu → "Customize Player"
  (`state5-t3-menu.png` → `state5-after-t3.png`). After every trigger the DOM has NO
  `[data-region-id="customize"]` and NO `.lumen-customize` (probes `after_t1/t2/t3`,
  script `capture.mjs`). Seam proof: dispatching `lumen:open-customize` fires the event
  (`fired:true`) and still mounts nothing (`panelAfterEvent:false`). `/player/music`
  cannot host it either — `MUSIC_LAYOUT_TOML` has no customize region (probe
  `musicRoute`: regions = playlist/album-art/controls-bar only).
- **Frame evidence:** frames 5/6/7 all show the panel; the trigger rows exist in the UI
  (canvas-menu row "Customize interface…" = w26.f09 lane key; app-menu row
  "Customize Player" = w26.f13) — 3 dead affordances with no listener.
- **Responsible files:** `ui/src/screens/player/PlayerScreen.tsx` (dispatches
  `PLAYER_OPEN_CUSTOMIZE_EVENT`; no host renders the region — `openPanels` is never
  non-empty on any route); `ui/src/screens/player/controls/ControlBar.tsx:569`
  (app-menu row, same dead seam); `ui/src/screens/player/customize/` (no dialog host/
  listener component); `ui/src/screens/player/variants/variantLayout.ts` (music layout
  drops the region). Known cross-lane dependency recorded in `logs/w26.f09.md` ("until
  then the seam fires with no listener") — still open at verification time.
- **Fix direction:** a compose lane must host the surface: either a
  `CustomizeDialogHost` listening for `lumen:open-customize` (mirroring
  `ToolsDialogHost` for `lumen:open-tools`) or `/player` route state passing
  `openPanels:["customize"]`. Until then ALL 9 customize states (0–8), not just 5–8,
  are unverifiable live.

### [g09-P1-2] Surface anatomy: the frames' centered modal vs the implementation's 320px right tool rail
- **State + reproduce:** any state with the panel open (unreachable live, so verified at
  code level): the surface is `.lumen-player__panel--right` — absolute right rail 320px,
  `--color-surface-panel` #191919, hairline #404040, r12, `--shadow-overlay`
  (`player.css:247–270`), inside which `customize.css` composes header/instruction/box/
  sections/footer.
- **Frame evidence:** every frame shows a **centered modal card 1048×655 rx14 #0E0E0E**
  (786×491 @1440) over the canvas — not a docked rail; modal fill #0E0E0E ≠ panel
  #191919; r14 vs `--radius-card-lg`; header band #090909; ✕ 10×10 (app: 16px Icon).
- **Responsible files:** `ui/src/screens/player/player.css` (`.lumen-player__panel`),
  `ui/src/screens/player/customize/customize.css`, `CustomizePanels.tsx`.
- **Fix direction:** Lead ruling required — contract §1 says the frames win: rehost as
  the centered r14 #0E0E0E modal (1048×655 @1920 scale), or explicitly ratify the rail
  interpretation in the wave plan. As shipped, no customize frame can pixel-match.
