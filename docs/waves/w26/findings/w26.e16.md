## Findings

### F1 — P2 — Suite runtime is ~4× the reference (~78s → 305.68s)

- **Evidence:** `npx vitest run --reporter=dot` → `Duration 305.68s (environment 60%…)`.
  First consecutive run emitted vitest's own perf tip: `jsdom was created 121 times ·
  104.37s total, 57% of tracked time… create it once per worker with pool: 'vmThreads'`.
  Both runs exceeded the 120s flag threshold (>180s each).
- **Location:** `ui/vite.config.ts` / `ui/vitest` config (test environment settings); 121 test files × fresh jsdom.
- **Suggested fix:** adopt `pool: 'vmThreads'` (keeps per-file isolation) or `isolate: false` per
  the vitest tip; re-baseline and record expected duration in the wave log.
- **Confidence:** high on the measurement (both runs >180s); medium that it's a regression
  vs. environmental load — but the task's own 78s reference and the >120s rule make it flaggable either way.

### F2 — P3 — Onboarding progress step NUMBER no longer asserted

- **Evidence (removed, w26.a era):**
  `- expect(progress.querySelector('[aria-current="step"]')).toHaveTextContent("1");` (and `"2"`)
- **Current state:** `ui/src/screens/onboarding/OnboardingScreen.test.tsx:70` —
  `expect(progress.querySelector('[aria-current="step"]')).toBeInTheDocument();` (presence only).
  The `aria-label "Onboarding step 1 of 8"` is still asserted (line 69), but the rendered step
  digit itself is no longer checked.
- **Suggested fix:** re-add `toHaveTextContent("1")` (and for a mid-flow step).
- **Confidence:** high (diff + current file both read).

## Verdict

The 1208/1208 claim is real and the suite is honest: no P0/P1 weakened assertions, no
hidden skips, snapshots regenerated in the new design language, coverage complete at
screen level. Four small P3 assertion losses (F2–F5) and one P2 runtime regression (F1)
are the only findings. The redesign-era test churn (116 removed assertion lines) is
overwhelmingly legitimate re-anchoring, much of it net-strengthening, per contract rule 8.
