## Findings

### [g06-P1-1] Hide-UI never reaches its frame: app-shell chrome (banner + rail + playlists sidebar) stays fully visible
- **State + reproduce:** `/player`, onboarding complete, park mouse, wait >3s
  (script `hideui.js`). `data-chrome="hidden"` fires — but only `[data-chrome-part]`
  elements INSIDE `.lumen-player` fade.
- **Frame evidence:** `Player - hide UI.svg` = 1920×1080 black + full-bleed artwork
  pattern + ONE r19 window stroke. No topbar, no rail, no sidebar — zero chrome.
  Measured after 3600ms idle: banner (0,0,1440×31, opacity 1), rail (0,31,52×869,
  opacity 1), shell playlists sidebar (52,31,208×869, opacity 1) all still painted;
  pixel samples of `hide-ui.png` at those regions confirm visible chrome.
- **Responsible files:** `ui/src/components/appshell/AppShell.tsx` (banner/rail/sidebar
  have no `data-chrome-part`, no listener for the player's chrome state);
  `ui/src/screens/player/useChromeAutoHide.ts` + `PlayerScreen.tsx` publish
  `data-chrome` only on `.lumen-player`. Cross-lane (appshell lane owns the shell chrome).
- **Fix direction:** appshell seam — AppShell already READS
  `.lumen-player[data-sidebar]` in its toggle; mirror the same probe (or a
  `lumen:chrome-visibility` event) for `data-chrome="hidden"` and fade
  banner/rail/shell-sidebar with the same 160ms opacity transition (keep them
  pointer-transparent while hidden). The r19 window stroke is host-owned (web shell has
  browser chrome) — document, don't fake.

### [g06-P1-2] An open menu does not lock the chrome — the fade fires under (and hides) open menus, stranding focus
- **State + reproduce A:** `/player`, right-click the canvas → "Player actions" context
  menu opens → rest 3.4s → `data-chrome="hidden"`, controls opacity 0, dock hidden,
  while the menu itself stays open and visible over a chrome-less UI (script `extra.js`).
  **Reproduce B:** open the ControlBar application menu → rest 3.2s → chrome hidden AND
  the open "Application menu" itself gets `visibility: hidden` with keyboard focus inside
  it (script `extra2.js`).
- **Frame/contract evidence:** `useChromeAutoHide.ts` header: "locked — a menu/panel is
  open: chrome must NOT hide (doc 08 §4.5 focus semantics; an open overlay that vanished
  would strand keyboard focus)". The wiring contradicts the hook's own contract.
- **Responsible files:** `ui/src/screens/player/PlayerScreen.tsx` (~line 650:
  `locked: openPanels.length > 0` — neither the `canvasMenu` state nor the ControlBar
  app-menu open state is folded in); `ui/src/screens/player/controls/ControlBar.tsx`
  (app-menu open state needs a lock seam).
- **Fix direction:** `locked: openPanels.length > 0 || canvasMenu !== null || <app-menu-open>`.
  The app menu needs either lifting its open state or a shared "overlay open" context the
  screen can read. Player-owned fix for the canvas menu half; ControlBar half needs a
  small seam from the controls lane.

### [g06-P1-3] First-run `/player/music` shows TWO left columns — matches neither music frame
- **State + reproduce:** fresh profile (onboarding complete, nothing else in
  localStorage), goto `/player/music` (script `music.js`). DOM: rail 52px (x=0) +
  shell playlists sidebar 208px (x=52) + player dock 300px (x=260) → stage only
  880px wide (x=560..1440), art centered at x=1000 instead of window-centered.
- **Frame evidence:** `Player - Music-1.svg` = rail 50 + exactly ONE 377px column
  (x=50, y=40..1026, `#0E0E0E`@0.95). `Player - Music.svg` = NO column and NO rail.
  Neither frame has a second playlists column. Consequence: the art (520×520,
  window-frame-scaled target ≈553) sits right of window center (frame centers it at
  960/1920), and the seek well is 581px vs the frame's 65%-of-window (≈936px at 1440).
- **Responsible files:** `ui/src/components/appshell/AppShell.tsx` —
  `loadSidebarOpen()` (line ~180) defaults OPEN with no route awareness. This is the
  documented f08 open item: w26.f09 log e02-F3 records the exact patch ("route-aware
  default: on `/player*` first-run with no stored preference, `setSidebarOpen(false)`").
  Not fixable from player-owned files (no player→shell seam exists).
- **Fix direction:** land the documented f08 patch. With it, music default = rail + dock
  (= Music-1), and the stage toggle alone reaches the true no-column state (the
  `:has()` rail rule in player.css then also hides the rail, matching `Player - Music`
  — verified composed via the shell toggle in capture 3).

### [g06-P2-1] Music transport row is an opaque #161616 band — the frames float it on the artwork backdrop
- **State + reproduce:** `/player/music` any sidebar state (scripts `music.js`).
  `.lumen-player__controls` = 45px `#161616` strip + 1px top hairline across the player
  root; pixel sample of the band between clusters: rgb(22,22,22).
- **Frame evidence:** `Player - Music.svg` Controls group contains NO background rect —
  transport buttons, the 1246×28 rx6 `#090909` seek well, timecodes and volume float
  directly on the full-bleed blurred artwork backdrop (band-zone reference sample
  rgb(23,23,23) = the art backdrop, not a panel). The theatrical screen has no strip.
- **Responsible files:** `ui/src/screens/player/player.css` (`.lumen-player__controls`),
  `ui/src/screens/player/variants/variants.css` (no music override for the band).
- **Fix direction:** under `.lumen-player[data-variant="music"]`: transparent band
  background, no top hairline. Keep the well's `#090909` (it reads against the art
  backdrop exactly as in the frame once artwork lands); while the stage is the honest
  `#090909` placeholder, give the well a hairline border so it stays legible without
  reintroducing the band.

## Lane summary

**Worst 3:**
1. **g06-P1-1** — hide-UI target state unreachable as framed: shell banner/rail/sidebar
   never fade (needs the appshell seam).
2. **g06-P1-2** — menu-open does not lock the idle fade; an open menu is hidden mid-use
   with focus inside (player-owned wiring + a small controls seam).
3. **g06-P1-3** — first-run music shows two stacked playlist columns (the documented f08
   route-aware-default patch, still unlanded).

**Verdict:** MECHANICS PASS, FRAMES NOT MET. The auto-hide state machine (3s idle,
cursor:none, pointer/key reveal, re-arm, music-mode fade set, no console errors, no
clipping at 1024×768) and the music seek/transport anatomy (tick field, playhead, pill,
timecodes) are frame-accurate. But the two headline states do not compose to their
reference frames: hide-UI keeps ~290px of shell chrome on screen, and music mode's
default carries an extra column plus an opaque control band. Two of the three P1s live
in AppShell.tsx (appshell/f08 lane); g06-P1-2 is player-fixable.
