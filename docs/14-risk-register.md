## 0. Purpose, scope, traceability

This is the single program-wide risk register. MP §14 requires known limits to be *recorded in the matrix, do not hide*; MP §17 requires a **Risks** field in every cycle report; doc 02 §8 explicitly defers the full register to this document. Nothing in this file hides a gap: every risk whose consequence is a missing capability carries the feature-matrix status it will produce (`blocked`, `partial`, `unsupported` — doc 02 §4.3 vocabulary), and every unverified fact carries `[VERIFY]` (AGENTS §3.4). Inventions — e.g. proposed thresholds, cadences, procedures — are marked `[PROPOSAL]` and need Lead confirmation.

Scope: the whole program (engine, UI, web, plugins, config, CI, legal, process), all phases 0–8 (MP §16). Out of scope: per-task operational issues (worklog), per-crate audit findings (doc 11, pending), benchmark deltas (doc 12, pending).

## 1. Register format

Each risk is one row with twelve fields. Because twelve columns are unreadable in one table, the register is rendered as **two synchronized views**: §2.1 (master table: identity, scores, ownership, status, cadence) and §2.2–§2.6 (detail tables: indicators, mitigations, contingency). Together they are the complete row; both views are sorted identically and carry the same IDs.

| Column | Definition |
|---|---|
| ID | `R-NN`, stable forever; retired IDs are never reused. |
| Category | `technical` / `legal` / `platform` / `process` / `scope` / `ecosystem` / `product`. |
| Risk | One sentence, **cause → consequence**. |
| Likelihood (L) | `L`/`M`/`H` — probability the risk materializes during the program if current mitigations were absent. |
| Impact (I) | `L`/`M`/`H` — damage to parity share (MP §1), fixed decisions (MP §2), schedule, or legality. |
| Exposure | L×I on the 1–3 scale → score 1–9. Tiers: **9 = critical** (can kill or redefine the program), **6 = severe** (major parity/schedule/legal damage), **3–4 = moderate**, **1–2 = minor**. |
| Early indicators | Observable signals that the risk is materializing — CI red gates, matrix statuses, audit findings, worklog patterns. |
| Mitigations | Owned and concrete: an artifact, decision, or test that exists or is scheduled, with its owner. |
| Contingency | The plan if it happens anyway. Contingencies must never silently relax MP §2 fixed decisions — those need the escalation path (§6). |
| Owner | `Lead` / `Phase-X-agent` / `User-decision` (only where MP §15 says stop and ask). |
| Status | `open` (no mitigation active yet) / `mitigating` (mitigation designed or running) / `closed` (contingency executed or risk retired, with worklog evidence). At inception no row is closed — this register starts in a planning wave. |
| Review | Cadence + trigger. Cadence: phase gates P0–P8 (MP §16), `per-wave` (planning), `monthly`, `per-release`, `continuous (CI)`. A *trigger* is an event that forces an out-of-cycle re-score. |

**Sorting rule:** exposure descending; within equal exposure: technical → legal → platform → process → scope → ecosystem → product, then earliest expected onset. **Re-scoring rule [PROPOSAL]:** the Lead re-scores the whole register at every phase gate; changes are logged in `worklog.md` (score deltas, new rows, retirements). Any new row may be added by any agent via their final report; only the Lead changes scores or closes rows.

### 2.6 Cross-cutting observations

1. Five of the severe technical codec risks (R-01, R-02, R-06, R-08, R-10) share one root cause: **the pure-Rust codec ecosystem does not cover VLC's codec surface** (doc 04 §4.5 "video codec hole"). They are managed individually but reported together in the feasibility report's headline (doc 02 §5 item 1).
2. The three web risks (R-12, R-13, R-14) are one platform's constraint set; doc 09 §10 already renders them as matrix rows — this register adds the process wrapper (re-score per release).
3. R-24/R-25/R-26 are the same program-integrity commitment in three costumes (matrix honesty, hw truthfulness, prose honesty); all trace to MP §1/§2 and are CI-enforced, not honor-system.

## 3. Top-10 exposure summary

**R-01 — H.264 software decode (9).** The codec that dominates real-world video has no production-grade pure-Rust decoder (doc 04 §4.2, verified 2026-10-19). The entire mitigation structure — ADR-001 hardware-first, the pure-Rust parser self-build, a possible Baseline-subset decoder — is already designed, but every path has a hole: hardwareless machines, exotic profiles (10-bit Hi10P), and the web build (no OS decoder; WebCodecs ADR pending). If ADR-001 lands and works, H.264 is `partial (hw-only)` and parity takes a bounded hit; if it does not, H.264 is `blocked` and the parity share drops by one of the largest P0 weights in the matrix (doc 02 §4.4). This risk defines the honest ceiling of the whole program.

**R-02 — HEVC software decode (9).** Same shape as R-01, "worse" (doc 04 §4.3): the self-build is XL and lower-value than H.264's, and the patent picture compounds it (R-03). Default plan is hw-only + parser, with software decode `blocked` and a recorded next step (MP §17 blocked-item rule). HEVC is the format where the program's three biggest risks (codec gap, patent, platform hw variance) intersect.

**R-03 — Codec patent exposure (9).** MP §14 separates patent risk from source licenses, and ADR-010 [PROPOSAL] owns it. The consequence is not a missing feature but a legal ceiling on *distribution*: a binary containing H.264/HEVC/AC-3/DTS decoders may be undistributable in some jurisdictions regardless of how clean the code is. The mitigation is procedural (open ADR-010 in P0, keep the patent matrix in doc 11, publish nothing until it passes); the contingency restructures the product (source-only or split codec builds). Only the user can accept patent risk — escalation matrix §6.

**R-04 — Video-in-webview on WebKitGTK (9).** MP §7 names Linux webviews the highest UI risk; ADR-003 exists precisely for it. If the Phase-2 prototype fails both candidates on WebKitGTK, the Linux product either ships a degraded canvas-streaming path or forces a shell-strategy change — which touches the OS-webview exception, a fixed decision (MP §2), and therefore escalates. Unlike the codec risks, this one is resolvable early and cheaply: the Phase-2 prototype is scheduled specifically to kill it.

**R-05 — Repository license undecided (9).** ADR-006 is planned but undated beyond "Phase 0" (doc 01 §7), and doc 02 §9 Q1 confirms nothing in the brief decides it. Until it is, every dependency approval is provisional (GPL-compatibility unknown), the R-07 design-asset question cannot be closed, and ecosystem decisions (plugin distribution, code reuse) block. It is the cheapest critical risk to close: one user decision. It should close first.

**R-06 — Opus decode (6).** The audio pillar of WebM-class content: `symphonia-codec-opus` is unpublished [VERIFY], so Opus is `missing` until the contribute-or-self-build path lands (doc 04 §3). Impact is bounded (Vorbis fallback exists for some content; the error is typed, never silent), but Opus is a P0/P1 matrix weight and a "usable player" signal (doc 02 §4.4).

**R-07 — Figma design package license (6).** The uploaded "VLC Redesign (Community)" package is the pinned visual source of truth (worklog 1.0), but Figma Community terms are unverified for commercial use and redistribution of derived assets, fonts are outlined (identity [VERIFY], licenses unknown), and the design's own title borrows VLC's mark (doc 08 §2). Worst case: the fidelity program's baseline assets are non-distributable and the UI must be re-derived from an internally-authored design. The fix is a user action (produce the file link/variables + license confirmation) — flagged for the current planning wave, before Phase-4 UI work makes it expensive.

**R-08 — rav1d asm-off purity and speed (6).** AV1 is the flagship *software* video codec of v1 (doc 04 §4.5), and rav1d complies with MP §9 only with `asm` off — unproven for build purity and speed [VERIFY-P0]. A failure demotes AV1 from "flagship" to "partial/later with measured numbers", weakening the one strong pure-Rust video story. The audit is already first on doc 04 §8.6's list.

**R-09 — ASS styling gap (6).** libass is C and forbidden; the pure-Rust subset [PROPOSAL] will not reach full typesetting parity (karaoke, complex positioning, font handling). Highly visible to the anime/fansub audience; mitigated by counting unsupported tags in the matrix rather than hiding them (doc 04 §7 gap 5).

**R-10 — DTS/TrueHD/AC-3/WMA family (6).** The surround-audio hole for movie files: no pure-Rust DTS/WMA, a young `truehdd`, AC-3 as a P6 self-build. Movie-file playback is the core VLC use case; partial audio coverage on that corpus is a real parity dent, honestly recorded (doc 04 §7 gap 7).
