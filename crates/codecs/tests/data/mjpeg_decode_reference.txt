# 2.B4 MJPEG decode-reference digests (card 2.B4 AC evidence).
#
# One sha256 per frame, over the decoder's I420 output for the
# 60-frame corpus carried (byte-identically) by both class-A parents:
#   tests/fixtures/generated/valid/avi_mjpeg_pcm.avi
#   tests/fixtures/generated/valid/mp4_mjpeg_pcm.mp4
# Frame order = stream order. Plane layout: Y 320x240 || Cb 160x120 || Cr 160x120
# (115200 bytes per frame). The codec-api path (MjpegDecoder, descriptor "mjpeg")
# and the free codecs::video::mjpeg::decode_image entry produce these same bytes.
#
# PROVENANCE (honesty rules, doc 03 sec.7 / AGENTS.md sec.3.4): the digests are
# Lumen's own decoder output, cross-checked against the ffmpeg 7.1.5 oracle
# (external, never a dependency) over all 60 frames:
#   - luma plane: BYTE-EXACT vs ffmpeg under both its default IDCT (-idct auto,
#     simple) and the reference integer IDCT (-idct int): 0 of 4,608,000 samples
#     differ.
#   - chroma planes: max |diff| = 1 vs both ffmpeg IDCT variants (an IDCT
#     rounding-boundary divergence, not a decode error). Affected samples:
#     24,600 of 2,304,000 (1.068%) vs -idct auto; 8,400 of 2,304,000 (0.365%)
#     vs -idct int. Divergence is confined to 12 of 300 chroma blocks per frame.
#   The choice recorded in worklog 2.B4: the reference is OUR output because the
#   in-house IDCT is the exact algebraic inverse of the 2.A3 in-repo encoder's
#   fixed-point FDCT (same Q16 basis, same round-half-away-from-zero), which is
#   the stronger truth than matching ffmpeg's own approximation.
#
# Regeneration (manual, oracle available): extract the 60 frames (e.g. via the
# test-side walkers in tests/common/mod.rs), decode each, sha256 the I420
# planes, and re-run the ffmpeg comparison to re-verify the tolerance above.
